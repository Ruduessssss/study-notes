今天做的是两块内容：**附近商户（GEO）** 和 **用户签到（BitMap）**。

一个把经纬度塞进 Redis 里按距离检索，一个把「这一天签没签」压成一个 bit。两件事的共同点是：**都用 Redis 存了一类「数据库不好做 / 做起来很贵」的数据**。

GEO 和 BitMap 的概念部分写在 `2026-10-02-Redis.md` 里，这篇只讲代码。

# 黑马点评09：附近商户（GEO）与用户签到（BitMap）

> **说明**：本文**只讲后端**，不涉及前端实现。
>
> 对照代码：`ShopController`、`ShopServiceImpl`、`IShopService`、`UserController`、`UserServiceImpl`、`HmDianPingApplicationTests`、`RedisConstants`、`SystemConstants`、`Shop`。

## 一、功能定位

两块互不相干的功能，但都是「用 Redis 替代 / 加速一次数据库查询」：

| 模块 | 需求 | Redis 数据结构 | 替代了什么 |
| --- | --- | --- | --- |
| **附近商户** | 点进「美食」后，按**距离**把附近 5000m 内的店铺排出来 | **GEO**（底层 ZSet） | 数据库做不了「按距离排序」 |
| **用户签到** | 记录用户本月每天签没签，能算**连续签到天数** | **BitMap**（底层 String） | 一行一条签到记录的宽表 |

> 两个功能都自然带出了一次「**结构选型**」：
>
> - 附近商户：不是「查得更快」，而是「**换一种存法**」——把坐标存成一种可排序、可范围检索的形式；
> - 用户签到：核心是**省空间**——1000 万用户一年 1 亿条记录的签到表，用位图只需要几十分之一。

   ↓                                            UserHolder（从登录拦截器的 ThreadLocal 取 userId）

   ├─ opsForGeo()                → Redis GEO（ZSet）
   └─ opsForValue().setBit/bitField → Redis BitMap（String）
   ↓

**分层上值得注意的一点**：`queryShopByType` 里「查 Redis GEO」和「查 MySQL」是**两段截然不同的路径**，靠一个 `if (x == null || y == null)` 分流：

- **无坐标**：走原来的 `query().eq("type_id", typeId).page(...)`（`ShopServiceImpl.java:298`）——和缓存章节之前一样。
- **有坐标**：先查 GEO 拿到「id + 距离」，**再用 id 回 MySQL 把完整店铺信息捞出来**（`ShopServiceImpl.java:340`）。

> GEO 里**只存了 id 和坐标**，没有店铺名字、图片、评分。所以要「列表里的完整信息」时，必须**回库一次**。
> 这就是为什么 `ids` 会被拼成 `in (...)` 去查 `tb_shop`。

### 4.1 `loadShopData`：把店铺灌进 GEO（预热）

写在测试类 `HmDianPingApplicationTests.java:34`，是个**手动跑一次的单元测试**，不是应用启动时自动执行：

```java
@Test
public void loadShopData()
{
    //获取数据列表
    List<Shop> shops = shopService.list();
    //将商铺按照商铺类型分类
    Map<Long, List<Shop>> map = shops.stream().collect(Collectors.groupingBy(Shop::getTypeId));
    //不同类型存到redis geo
    for (Map.Entry<Long, List<Shop>> entry : map.entrySet()) {
        //获取同类店铺和类型id
        List<Shop> shopList = entry.getValue();
        Long typeId = entry.getKey();

        String key = SHOP_GEO_KEY+typeId;
        //方法一:依次存入redis,每存入一个店铺发起一次请求,麻烦
        for (Shop shop : shopList) {
            stringRedisTemplate.opsForGeo().add(key,new Point(shop.getX(),shop.getY()), String.valueOf(shop.getId()));
        }

        //方法二:用另一种add,封装到list
        List<RedisGeoCommands.GeoLocation<String>> list = new ArrayList<>(shopList.size());
        for (Shop shop : shopList) {
            list.add(new RedisGeoCommands.GeoLocation<String>(String.valueOf(shop.getId()),new Point(shop.getX(),shop.getY())));
        }
        stringRedisTemplate.opsForGeo().add(key,list);
    }
}
```

要点：

- **先 `groupingBy(Shop::getTypeId)`，再按类型写 key**。为什么必须按 `typeId` 分 key？因为 **GEO 里不存业务类型**——一个 GEO 集合只是一个「member + 坐标」的大 ZSet，你没法在查询时按 type 过滤。
  把同一类型放进 `shop:geo:{typeId}`，就等价于给这批数据**贴上了类型标签**。查到哪个 key，就是哪个类型。
  key 前缀是 `SHOP_GEO_KEY = "shop:geo:"`（`RedisConstants.java:29`），最终 key 形如 `shop:geo:1`。
- **member 存的是 `shop.getId()` 的字符串**，不是店铺对象。原因见 4.3 的注释：Redis 是内存数据库，member 越短越好；存 id 就够了，完整信息回 MySQL 查。
- **`new Point(shop.getX(), shop.getY())` 的顺序是（经度, 纬度）**。`Shop.x` 是经度、`Shop.y` 是纬度（`Shop.java:64`、`Shop.java:69`），千万别写反 —— 写反了位置全错，但**不报错**，最难查。
- **这个方法把数据写了两遍**：`方法一`（循环单条 add）和 `方法二`（批量 add）**都真的在执行**，不是二选一。
  课程原版把方法一注释掉了，只留批量；这里两条都跑了 —— 写进去的 member 完全相同，第二次是**冗余写**（见「易错点 1」）。

### 4.2 `queryShopByType` 的 GEO 查询与分页

主方法在 `ShopServiceImpl.java:292`：

```java
@Override
public Result queryShopByType(Integer typeId, Integer current, Double x, Double y) {
    if(x==null||y==null)

    );
    if(geoResults==null)
    {
        return Result.ok();
    }
    // ...（下面接着讲）

```

**逐块拆开：**

**（1）无坐标分支** —— 退化成普通 `type_id` 分页，和缓存章节无关，一行注释就够。返回 `page.getRecords()`，是个真正的 List。

**（2）分页参数 `from` / `end`** —— `DEFAULT_PAGE_SIZE = 5`：

| current | from | end | limit(end) 取回 | skip(from) 之后 |
| --- | --- | --- | --- | --- |
| 1 | 0 | 5 | 前 5 条 | 5 条（第 1 页） |
| 2 | 5 | 10 | 前 10 条 | 后 5 条（第 2 页） |
| 3 | 10 | 15 | 前 15 条 | 后 5 条（第 3 页） |

**（3）`search(...)` 四个参数**：

| 参数 | 含义 | 翻译成 Redis 命令 |
| --- | --- | --- |
| `key` | `shop:geo:{typeId}` | 要搜的 GEO 集合 |
| `GeoReference.fromCoordinate(x, y)` | 以 (x,y) 为圆心 | `FROMLONLAT x y` |
| `new Distance(5000)` | 半径 5000 **米** | `BYRADIUS 5000 m` |
| `.includeDistance().limit(end)` | 结果带上距离、最多取 `end` 条 | `WITHDIST COUNT end` |

> `new Distance(5000)` 的单位默认是**米**（`Metrics.NEUTRAL` 在 GEO 场景按米处理）。5000 就是 5 公里。
> `includeDistance()` 是关键 —— 不带它，`GeoResult.getDistance()` 拿不到距离，前端就没法显示「距离你 320m」。
> 搜索结果**天生按距离升序排好**，这是 GEO 白送的（底层 ZSet 按 score 排）。

**（4）分页是「假分页」** —— 接着往下（`ShopServiceImpl.java:315`）：

```java
    //解析content
    //这个list封装的是店铺的综合信息; list.getcontent得到的是封装了店铺坐标,店铺id
    List<GeoResult<RedisGeoCommands.GeoLocation<String>>> content = geoResults.getContent();
    if(from>=content.size())
    {
        //防止后面stream流skip时越界
        return Result.ok();
    }
    //封装店铺id和距离
    Map<String,Distance> distanceMap = new HashMap<>(content.size());
    //用于查询数据库店铺
    List<Long> ids = new ArrayList<>(content.size());
    content.stream().skip(from).forEach(shop->{
        String shopId = shop.getContent().getName();
        ids.add(Long.valueOf(shopId));
        Distance distance = shop.getDistance();
        distanceMap.put(shopId,distance);
    });
    //查询数据库,保证数据排序一致
    String strId = StrUtil.join(",", ids);
    List<Shop> shopList = query().in("id", ids).last("ORDER BY FIELD (id," + strId + ")").list();

    for (Shop shop : shopList) {
        shop.setDistance(distanceMap.get(shop.getId().toString()).getValue());
    }

    return Result.ok(shopList);
}
```

这一段是本节**最该记清楚**的地方：

- **GEO 查询没有真正的分页**。`GEOSEARCH` 只有 `COUNT`（取多少条），**没有 `OFFSET`**。想要第 2 页，只能：
  1. **先取回前 `end` 条**（`limit(end)`），
  2. 再在 Java 里 **`stream().skip(from)`** 把这页要的 5 条切出来。
- **代价**：每翻一页，都要**重新把前面所有页的数据从 Redis 拉回来**（第 3 页就要拉 15 条）。页数越深，单次请求的传输和解析量越大 —— 是 **O(end)** 而不是 O(每页大小)。这就是为什么只做「前几页附近」体验还行，深翻页会很重。
- **还有一致性代价**：`skip` 是对「这次返回的整段结果」做偏移。如果两次请求之间 GEO 里的数据变了（新店开张、坐标更新），**第二页可能重复或漏掉** —— 典型的 offset 分页漂移。
- **`if(from>=content.size())` 是越界保护**：如果 GEO 里根本没有这么多条，`skip(from)` 会得到空流，提前返回。
- **`ORDER BY FIELD(id, ...)` 是为了「保证顺序」**：`in("id", ids)` 查 MySQL 时，**MySQL 不保证返回顺序和 `in` 里的顺序一致**。而前端要的是「按距离从近到远」。所以用 `ORDER BY FIELD(id, id1, id2, ...)` 把结果**强行按 GEO 的距离顺序重排**一遍。
  > `FIELD()` 返回该值在参数列表里的位置，`ORDER BY FIELD(...)` 就按这个位置升序 —— 于是顺序和 `ids` 一模一样。
- **`distanceMap` 单独存距离**：MySQL 里没有距离这个字段，它是 GEO 算出来的。回库之后，按 id 从 `distanceMap` 里把距离取回来 `setDistance(...)`，让每个 `Shop` 带上 `distance`。

### 4.3 `sign()`：写入签到

`UserServiceImpl.java:132`：

```java
@Override
public Result sign() {
    //获取用户id
    Long userId = UserHolder.getUser().getId();
    //获取当前时间
    LocalDateTime now = LocalDateTime.now();
    String format = now.format(DateTimeFormatter.ofPattern(":yyyyMM"));
    //拼接成key
    String key = USER_SIGN_KEY+userId + format;

    //获取今天;
    long today = now.getDayOfMonth();

    //存入redis
    stringRedisTemplate.opsForValue().setBit(key, today - 1, true);

    return Result.ok();
}
```

要点：

- **key 设计：`sign:{userId}:yyyyMM`**。`USER_SIGN_KEY = "sign:"`（`RedisConstants.java:30`），`format` 是 `":yyyyMM"`，拼出来例如 `sign:5:202610`。
  - **按「用户 + 月」分 key**：每个用户每个月一张独立的位图。
  - 为什么按月？因为**位图的位数是有限的**（最大 2^32 位），而且「连续签到」只关心当月。按月分 key，一个 key 只占 31 位，**用完即弃**（下个月自然换新 key），还方便设 TTL。
  - 注意 `format` 里带了个**冒号前缀** `":yyyyMM"`，是为了拼接出 `sign:5:202610` 这种带分隔的样子。
- **`setBit(key, today - 1, true)`**：`offset = 本月第几天 - 1`。
  - 第 1 天 → offset 0，第 9 天 → offset 8。**减 1 是因为 offset 从 0 开始计**。
  - 第三个参数 `true` = 置 1。置 1 表示「这天签到了」；没签的位是 0（Redis 新建位图时，未触碰的 bit 默认就是 0）。
- **不需要判断「今天是不是已经签过」**：重复 `SETBIT` 到同一位还是 1，天然幂等。
- **`UserHolder.getUser()` 可能为 null** —— 前提是 `/user/sign` 被登录拦截器保护，能取到当前用户。

### 4.4 `countDay()`：统计连续签到

`UserServiceImpl.java:151`：

```java
@Override
public Result countDay() {
    //获取用户id
    Long userId = UserHolder.getUser().getId();
    //获取当前时间
    LocalDateTime now = LocalDateTime.now();
    String format = now.format(DateTimeFormatter.ofPattern(":yyyyMM"));
    //拼接成key
    String key = USER_SIGN_KEY+userId + format;
    //获取今天;
    int today = now.getDayOfMonth();
    //redis取出
    List<Long> bitField = stringRedisTemplate.opsForValue().bitField(key,
            BitFieldSubCommands.create().get(BitFieldSubCommands.BitFieldType.unsigned(today)).valueAt(0));
    if(bitField==null||bitField.isEmpty())
    {
        return Result.ok();
    }
    //bitField里只存了一个Long
    Long l = bitField.get(0);
    if(l==null||l==0)
    {
        return Result.ok();
    }
    int count = 0;

    while (true)
    {
        if((l&1)==0)
        {
            break;
        }
        else
        {
            count++;
            l =l>>>1;
        }
    }
    return Result.ok(count);
}
```

**（1）用 `BITFIELD key GET u<today> 0` 一次读出「本月 1 号到今天」的所有签到位**：

```text
BITFIELD sign:5:202610 GET u9 0      ← 假设今天是 9 号
```

- `u9` = **无符号、宽 9 位**；`0` 是起始 offset。读出来是一个十进制整数，**低 9 位就是 1~9 号的签到记录**。
- **为什么要用 `BITFIELD` 而不是逐位 `GETBIT`**：一次网络往返就拿到 9 天（甚至 31 天）的记录，而不是发 9 次请求。
- **为什么宽度取 `today` 而不是固定 31**：`today` 号之前的位还没写（都是 0），多读也没用；只读「截止到今天」的部分，**让最低位正好落在「今天」上**。

**（2）位序（关键，容易搞反）**：

```text
offset:  0    1    2    3    4    5    6    7    8
天:      1号  2号  3号  4号  5号  6号  7号  8号  9号(今天)
u9 值:  [MSB ............................... LSB]

  ← MSB（高位）                             LSB（低位）→
```

- Redis 的 bit offset 从 0 开始，**offset 0 是最高位**（MSB）。所以 `u9` 读出来这个整数里：
  - **最高位 = 1 号**，**最低位 = 9 号（今天）**。
- 于是循环从 **`l & 1`（最低位 = 今天）** 开始判断，先看今天签没签，再 `l >>>= 1` 右移到「昨天」，一路往回 —— 正好是「**从最后一次签到向前统计**」。

**（3）连续天数算法**：

```text
l & 1 == 0  → 这一天没签 → break，结束统计
l & 1 == 1  → 这一天签了 → count++，右移一位看前一天
```

- **`l & 1`**：和 1 做按位与，只保留最低位（当天的签到状态）。
- **`l >>>= 1`**：把已统计的那一位挤出去，让「前一天」变成新的最低位。
- 循环到「第一个 0」为止 —— 中间断一天，连续计数就清零重来（这里是直接 break）。

> ⚠️ **`>>>` 必须用无符号右移，不能用 `>>`**。这一点下面单独讲，见「易错点 3」。

## 五、易错点

### GEO 相关

1. **`loadShopData` 把数据写了两遍**。方法一（循环单条 `add`）和方法二（批量 `add`）**都在执行**（`HmDianPingApplicationTests.java:49` 与 `HmDianPingApplicationTests.java:55`），写进去的 member 完全相同 —— 属于冗余写。
   课程原版**把方法一注释掉了**，只保留批量那一段。这里没注释，所以每跑一次 `loadShopData`，第一批数据被 `GEOADD` 了两次（值相同，最终结果一样，但白跑一遍网络请求）。

2. **`Point` 的（经度, 纬度）顺序不能反**。`new Point(shop.getX(), shop.getY())`（`ShopServiceImpl` 的预热、`HmDianPingApplicationTests.java:50`）——`x` 是经度、`y` 是纬度。写反了不报错，但所有距离全乱。

3. **GEO 是「假分页」，深翻页代价随页码线性增长**。`limit(end)` 取回前 `end` 条、再 `stream().skip(from)` 切页（`ShopServiceImpl.java:313`、`ShopServiceImpl.java:332`）。
   - 每页都要重取「前面所有页」的数据，越翻越慢；
   - 两次请求之间数据变动会导致**跨页重复 / 漏项**（offset 分页漂移）。
   - 课程同样这么写，是 Redis GEO 没有 `OFFSET` 的无奈之举，不是本项目引入的 bug。

4. **两处「空结果」返回的是 `Result.ok()` 而不是空列表**。课程原版是 `Result.ok(Collections.emptyList())`：
   - `ShopServiceImpl.java:317`：`if(geoResults==null) return Result.ok();`
   - `ShopServiceImpl.java:326`：`if(from>=content.size()) return Result.ok();`
   本项目返回 `Result.ok()` → `data` 为 `null`。前端若按「数组」处理（`list.length` / `for` 遍历）会拿到 `null` 出问题。**应该是空数组**。

### 签到相关

5. **`countDay` 里两处「没签到」返回的是 `Result.ok()`（`data=null`）而不是 `Result.ok(0)`**：
   - `UserServiceImpl.java:167`：`if(bitField==null||bitField.isEmpty()) return Result.ok();`
   - `UserServiceImpl.java:173`：`if(l==null||l==0) return Result.ok();`
   课程原版这里都是 `return Result.ok(0);`。当前实现下，**「一天没签」的用户拿到的是 `null`，而不是 `0`** —— 和「接口没数据」无法区分。

6. **`>>>` 无符号右移（本节重点）**。`UserServiceImpl.java:186` 用的是 `l = l>>>1;`。
   - 这一位运算的语义是：**把一个「位串」当无符号数处理**，右移时**高位补 0**。
   - 如果错用成**有符号右移 `>>`**，当 `l` 是负数（**符号位为 1**）时，右移会**高位补 1**，`l` 永远是负数、永远不变；`l & 1` 恒为 1 → `count` 无限自增、**死循环**。
   - **但要说清楚**：在**本段代码里** `l` 来自 `BitFieldType.unsigned(today)`，且 `today ≤ 31`，所以 `l` 一定 ≥ 0（第 63 位符号位为 0），此时 **`>>` 与 `>>>` 结果完全一致、并不会死循环**。
     真正会踩坑的是：**读有符号字段 `i<width>`、或字段宽度大到把符号位占满**的场景 —— 那时 `>>` 就会符号扩展出无穷多个 1。
   - 结论：**只要数据是「无符号位串」，就应该用 `>>>`** —— 本例恰好安全，但写法必须先对。

7. **方法名与课程不一致**：课程里统计方法是 `signCount()`、Controller 里是 `signCount`；本项目叫 `countDay()`（`UserServiceImpl.java:152`、`UserController.java:105`）。功能一样，只是命名不同。

8. **签到离不开登录态**。`sign()` 和 `countDay()` 都从 `UserHolder.getUser().getId()` 取 userId（`UserServiceImpl.java:135`、`UserServiceImpl.java:154`）。如果登录拦截器没覆盖这两个路径，`getUser()` 返回 null → NPE。

## 六、不依赖前端的验证方法

以下命令可以直接在 `redis-cli` 里跑通（前提：先跑过 `loadShopData` 单元测试、以及调过一次 `POST /user/sign`）。

### 6.1 验证 GEO（附近商户）

**第一步：确认 key 是 ZSet** —— 这一步是整个 GEO 章节的核心结论：

```text
127.0.0.1:6379> TYPE shop:geo:1
zset
127.0.0.1:6379> ZCARD shop:geo:1
11
```

> **`TYPE` 返回 `zset`** —— 证明 GEO 底层就是**有序集合**。成员是店铺 id，score 是经纬度编码出来的 geohash 整数。

**第二步：看 member 与 score**：

```text
127.0.0.1:6379> ZRANGE shop:geo:1 0 0 WITHSCORES
1) "1"
2) "4069959088505804"
```

> `1` 是店铺 id（member），后面那串就是 **52 位 geohash 被当成 score**（不可读，但正是它带来了「按距离排序」的能力）。

**第三步：坐标还原 / 算距离**：

```text
127.0.0.1:6379> GEOPOS shop:geo:1 1
1) 1) "121.45759499073028564"
   2) "31.249205128874554"
127.0.0.1:6379> GEODIST shop:geo:1 1 2 km
"1.2345"
```

**第四步：复现接口的圆形范围查询**（服务端 `FROMLONLAT ... BYRADIUS ... WITHDIST`）：

```text
127.0.0.1:6379> GEOSEARCH shop:geo:1 FROMLONLAT 121.4575 31.2492 BYRADIUS 5000 m WITHDIST COUNT 5
1) 1) "1"
   2) "0.0000"
2) 1) "2"
   2) "320.1521"
```

> 结果**按距离升序**排列，且带上了距离 —— 和 `includeDistance().limit(end)` 出来的顺序一致。
> 想验证「假分页」：把 `COUNT` 改成 10 再 `GEOSEARCH`，就是代码里 `limit(end)` 那一步。

### 6.2 验证签到 BitMap

**第一步：找到 key**：

```text
127.0.0.1:6379> KEYS sign:*
1) "sign:5:202610"
```

**第二步：看今天那一位**（假设今天是 9 号 → offset 8）：

```text
127.0.0.1:6379> GETBIT sign:5:202610 8
(integer) 1
```

**第三步：统计总共签了几天**：

```text
127.0.0.1:6379> BITCOUNT sign:5:202610
(integer) 3
```

**第四步：复现接口的 `BITFIELD`（读 1 号到今天）**：

```text
127.0.0.1:6379> BITFIELD sign:5:202610 GET u9 0
1) (integer) 7
```

> 返回 `7` = 二进制 `000000111` → 低 3 位是 1 → **7、8、9 号签了，连签 3 天**。
> 这正是 `countDay()` 里 `l` 的值：`l & 1 == 1` → count=1；`l >>>= 1` → `00000011`；再两次 → count=3；第 4 次 `l & 1 == 0` → break。**结果 = 3，和 `GET /user/sign/count` 一致。**
>
> 顺便验证 BitMap 底层是 String：`TYPE sign:5:202610` 会返回 `string`。

## 七、可以更好的地方

> 写法：**现状 → 问题 → 怎么改**。

### 7.1 「空结果」统一返回空列表 / 0

**现状**：GEO 两处、签到两处都用 `Result.ok()`，`data` 为 `null`。

**问题**：调用方拿到 `null` 无法区分「没有数据」和「接口异常」，前端遍历会崩。

**怎么改**：按课程原版返回语义正确的空值：

```java
// GEO：没有结果 → 空列表
if (geoResults == null) {
    return Result.ok(Collections.emptyList());
}
if (from >= content.size()) {
    return Result.ok(Collections.emptyList());
}
// 签到：连续天数为 0 → 返回 0
if (bitField == null || bitField.isEmpty()) {
    return Result.ok(0);
}
if (l == null || l == 0) {
    return Result.ok(0);
}
```

### 7.2 GEO 分页换成「游标 / 分片」

**现状**：`limit(end)` + `stream().skip(from)`，O(end) 深翻页。

**问题**：页数一深就慢，且跨页可能重复。

**怎么改**：真实系统一般**不做深翻页**，只给「附近前 N 家」；要么用 `GEOSEARCHSTORE` 把结果落到一个临时 key 再 `ZRANGE` 分页（一次搜索、多次分页），要么直接限制最大页码（比如只允许前 5 页）。

### 7.3 签到位图设 TTL

**现状**：`sign:{userId}:yyyyMM` **不设过期时间**，签到记录永久驻留。

**问题**：历史月份的数据越攒越多，虽然单个 key 小（31 位），但用户量大了仍是纯垃圾。

**怎么改**：写入时顺便给当月 key 设一个 2 个月左右的 TTL（跨月后还能查上月），到点自动回收：

```java
stringRedisTemplate.opsForValue().setBit(key, today - 1, true);
stringRedisTemplate.expire(key, 62, TimeUnit.DAYS);   // 留到「下下个月初」自然清掉
```

> 注意：`setBit` 本身无法带 TTL，得再发一次 `EXPIRE`（两次写非原子，但签到场景可接受）。

### 7.4 给 `loadShopData` 加幂等 / 去掉冗余写

**现状**：方法一、方法二都跑；且重复执行会重复 `GEOADD`。

**问题**：预热脚本应可反复安全执行，写两遍是浪费。

**怎么改**：**只保留批量那一版**（删掉循环单条 `add` 那段）；如果要求「重跑不残留旧数据」，在写之前先 `DEL shop:geo:{typeId}`。

### 7.5 优先级

| 改动 | 成本 | 收益 | 建议 |
| --- | --- | --- | --- |
| 空结果返回 `emptyList()` / `0` | 四行 | 高（接口语义正确、前端不崩） | **建议做** |
| 去掉 `loadShopData` 的冗余写 | 删四行 | 中（预热干净、可重跑） | 建议做 |
| 签到 key 加 TTL | 一行 | 中（长期省内存） | 建议做 |
| GEO 换游标 / 限页 | 中等 | 中（只在深翻页时暴露） | 看情况 |
| 统计方法补 `>>>` 注释 | 一行注释 | 低（但防止后来人改错） | 建议做 |
