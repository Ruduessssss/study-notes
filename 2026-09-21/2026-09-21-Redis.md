## 一、缓存是什么，为什么需要它

**缓存 = 数据交换的缓冲区。** 把「慢的地方」的数据，复制一份到「快的地方」。

本项目的场景：商铺详情来自 MySQL，但每次点进店铺都要查一次库，数据库扛不住。于是在 MySQL 前面加一层 Redis。

为什么是 Redis 而不是本地 Map（`static final ConcurrentHashMap`）？

| | 本地 Map | Redis |
| --- | --- | --- |
| 多实例共享 | ✗ 各存各的，数据不一致 | ✓ 共享一份 |
| 过期机制 | ✗ 要自己写 | ✓ `EXPIRE` 现成的 |
| 容量 | ✗ 吃 JVM 堆内存，撑大会拖垮 GC | ✓ 独立进程，内存单独规划 |
| 重启后 | ✗ 全丢 | ✓ 还在 |

> 本地 Map 唯一的优势是**没有网络开销**，快一个数量级。所以真实系统通常是**多级缓存**：
> 本地缓存放最热的一小撮数据（几秒过期），Redis 放次热的，MySQL 兜底。

## 二、缓存的三种「淘汰」方式

Redis 内存有限，数据不能无限往里塞。三种让缓存数据消失的方式：

| 方式 | 谁来做 | 触发时机 | 用途 |
| --- | --- | --- | --- |
| **内存淘汰** | Redis 自动 | 内存达到 `maxmemory` | 兜底，防止 OOM |
| **超时剔除** | Redis 自动 | 到了 TTL | 控制数据新鲜度 |
| **主动更新** | **业务代码** | 数据库被修改时 | **解决缓存与数据库不一致** |

> 前两种是「Redis 自己的事」，第三种是「你的事」。
> 三大缓存问题（穿透/击穿/雪崩）里，穿和崩靠前两种 + 代码兜底，
> **击穿和双写一致才是真正需要写代码解决的**。

## 三、双写一致性（本节是重点）

缓存的数据源是数据库。数据库变了、缓存没变，用户就会读到**过期数据**。

### 3.1 三种模式

| 模式 | 谁负责同步 | 特点 |
| --- | --- | --- |
| **Cache Aside**（旁路缓存） | **调用者手动写代码** | 简单可控，最常用 |
| Read/Write Through | 缓存层自己代理读写数据库 | 对业务透明，但组件复杂 |
| Write Behind | 只写缓存，异步刷回数据库 | 性能最好，但可能丢数据 |

本项目用 **Cache Aside**。

### 3.2 决定一：删缓存，还是更新缓存？

**先看反例：为什么不能「更新缓存」。**

假设每次改数据库都顺手把新值写进缓存。如果 1 秒内改了 10 次数据库，就会有 **10 次写缓存** —— 而其中 9 次写的值，在下一个请求到来前就被覆盖了，**完全是无效写**。

如果这期间根本没人来读，这 10 次写缓存一次都没被用上。

**所以选择「删除缓存」**：改数据库时把缓存**删掉**，等下次有人来查，再把最新值加载回去（**懒加载**）。

- 删缓存 = 一次 `DEL`，不管改几次都只删一次
- 代价是下次查询会「未命中」一次，多走一趟数据库

### 3.3 决定二：先删缓存，还是先改数据库？

这是本节最值得记的一段推演。

#### ❌ 先删缓存，再更新数据库

```text
线程1：删缓存 ──────────────────→ 更新数据库
线程2：      查缓存(未命中) → 查数据库(读到旧值) → 写回缓存
```

**时序**：线程1 删完缓存后、还没更新数据库时，线程2 进来查 —— 缓存没有，于是去数据库读，**读到的是旧值**，然后把这个旧值写回了缓存。

等线程1 更新完数据库，**缓存里躺着的却是旧值**，而且会一直错到 TTL 到期。

> 问题的根源：**「写回缓存」这个动作发生在「删缓存」之后**，
> 于是它把脏数据放了进去，没人再删它。

#### ✅ 先更新数据库，再删缓存

```text
线程1：更新数据库 ──────→ 删缓存
线程2：         查缓存(未命中) → 查数据库 → 写回缓存
```

要出错，需要同时满足：

1. 线程2 在缓存失效的瞬间去查数据库；
2. 并且**读到的还是旧值**（即发生在更新数据库之前）；
3. 并且**写回缓存发生在删除之后**。

这三件事要凑到一起，**窗口极窄** —— 因为写回缓存之前必然要先读数据库，而读数据库又必须先于更新数据库发生。概率上低得多。

**结论：先操作数据库，再删除缓存。**

> ⚠️ 注意它**不是绝对一致**，只是把概率压得极低。
> 要更稳可以再叠：给缓存设 TTL 兜底（最终一致）、延迟双删、或用 Canal 订阅 binlog 异步删缓存。

## 四、缓存三大问题

这三个名字特别容易混，先把区别拎清楚：

| | **穿透** | **击穿** | **雪崩** |
| --- | --- | --- | --- |
| **数据在哪** | 缓存和数据库**都不存在** | 数据库**存在** | 数据库**存在** |
| **什么没了** | 缓存里**从来没有**这条 | **热点 key** 刚好过期 | **大量 key 同时**过期 |
| **谁干的** | 恶意请求 / 无效查询 | 高并发访问同一个热点 key | 过期时间撞车 / Redis 宕机 |
| **DB 压力** | 每个请求都打 DB | 瞬间并发全打 DB | 大面积请求全打 DB |
| **解法** | 缓存空对象、布隆过滤器 | 互斥锁、逻辑过期 | TTL 加随机值、集群、降级限流、多级缓存 |

> **一句话区分**
>
> - **穿透**：查一个**压根不存在**的东西 —— 「骗」过去的
> - **击穿**：一个**热点** key 正好失效 —— 「戳」穿一个点
> - **雪崩**：**一大批** key 一起失效 —— 整面塌下来

### 4.1 缓存穿透

客户端查的数据**缓存和数据库都没有**。缓存永远不生效，每次请求都落到数据库。

如果被人拿脚本刷 `id = -1`，几十万 QPS 全打在 MySQL 上，直接打挂。

**两种解法：**

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **缓存空对象** | 数据库查不到，也往 Redis 写一个空值 | 实现简单 | 占内存；短期不一致 |
| **布隆过滤器** | 用位数组 + 哈希预判「是否存在」 | 省内存、无多余 key | 实现复杂；**有误判** |

> 布隆过滤器的误判是**单向**的：说「不存在」一定不存在，说「存在」**不一定**存在。
> 所以它只能挡住一部分，挡不住的那部分还是要靠缓存空对象兜底。

**本项目选了「缓存空对象」** —— 简单、够用。

### 4.2 缓存雪崩

**同一时段大量 key 同时失效**，或者 **Redis 直接宕机**。

典型成因：系统上线时批量预热缓存，都设了 30 分钟 TTL —— 30 分钟后**一起过期**，请求全砸到数据库。

**解法：**

- **给 TTL 加随机值**（最常用、成本最低）
- 用 Redis 集群提高可用性
- 加降级限流
- 多级缓存（本地缓存顶一阵）

### 4.3 缓存击穿（热点 Key 问题）

**一个被高并发访问、且重建代价高的 key 突然失效了。**

注意它和雪崩的区别：雪崩是「一大批」，击穿是「一个，但它是热点」。就像大坝上被戳了一个洞 —— 洞不大，但水全从那儿喷出来。

**两种解法**（下一节详细对比）：

- **互斥锁**：只让一个线程去重建
- **逻辑过期**：干脆不设物理过期，永远返回数据，后台异步重建

---

## 五、击穿的两种解法对比

| | **互斥锁** | **逻辑过期** |
| --- | --- | --- |
| **怎么保证只有一个人重建** | 缓存未命中时抢锁，抢不到就自旋重试 | 缓存里的时间戳过期时抢锁，抢不到直接返回 |
| **返回的数据** | 等到重建完成，**返回新数据** | **立刻返回旧数据**（脏数据） |
| **一致性** | ✓ 强 | ✗ 有一段时间是脏数据 |
| **性能** | 查询**串行化**，要等 | 不等待，吞吐高 |
| **实现复杂度** | 简单 | 复杂（要包装 value、要线程池） |
| **额外内存** | 无 | 要多存一个包装对象 |
| **风险** | 可能死锁 / 锁超时误删 | 重建期间全是脏数据 |
| **适合** | 一般热点数据 | 秒杀这类**对一致性要求低、对响应速度要求高**的场景 |

### 5.1 逻辑过期为什么要包装 value

普通缓存用**物理 TTL**：到期 Redis 自动删掉。

逻辑过期反过来 —— **不设物理 TTL**（`set` 时不带过期时间），把过期时间塞进 value 里：

```json
{
  "expireTime": "2026-09-21T10:30:00",
  "data": { "id": 1, "name": "..." }
}
```

读的时候自己判断 `expireTime`：

- **没过期** → 直接返回 `data`
- **过期了** → 抢锁，抢到就开异步线程去重建，**当前请求照样把旧 `data` 返回**

**关键点：过期时间被搬进了 value，Redis 不知道它过期，所以 key 永远不会被自动删除。** 这正是「逻辑过期」这个名字的来源。

代价是：**内存不会自动回收**，必须靠业务主动清理（或者一直留着，反正热点数据就是要常驻）。

### 5.2 为什么包装成 `RedisData` 而不是改实体类

两种做法：

1. 给 `Shop` 加一个 `expireTime` 字段；
2. **新建一个 `RedisData { expireTime, data }` 把 `Shop` 包起来**。

本项目选 2。理由是**对原实体类零侵入** —— `Shop` 是数据库表的映射，不该为了缓存的需求而多出一个数据库里不存在的字段。

```java
@Data
public class RedisData {
    private LocalDateTime expireTime;
    private Object data;      // ← Object 类型，所以谁都能装
}
```

> `data` 声明成 `Object` 是关键 —— 这样 `RedisData` 是**通用**的，
> 换成 `Voucher`、`Blog` 也能直接包，不用为每个实体建一个包装类。
>
> 代价是反序列化时拿到的其实是 `JSONObject`，**必须强转**：
> ```java
> Shop shop = JSONUtil.toBean((JSONObject) redisData.getData(), Shop.class);
> ```

## 六、本项目用到的 Redis 命令 / API

| Java（StringRedisTemplate） | Redis 命令 | 用在哪 |
| --- | --- | --- |
| `opsForValue().set(k, v, ttl, unit)` | `SET k v EX <ttl>` | 写缓存（带物理 TTL） |
| `opsForValue().set(k, v)` | `SET k v` | 写**逻辑过期**缓存（**故意不带 TTL**） |
| `opsForValue().get(k)` | `GET k` | 读缓存 |
| `opsForValue().setIfAbsent(k, v, ttl, unit)` | `SET k v NX EX <ttl>` | **互斥锁**（抢锁；也是做防刷限流的标准手段） |
| `delete(k)` | `DEL k` | 删缓存 / 释放锁 |

> **`SET NX` 为什么能当锁用**：`NX` 的语义是「key 不存在才设置」，
> 而 Redis 单线程执行命令，所以**同一时刻只有一个客户端能设置成功** —— 这就是互斥。

## 七、概念层面要注意的坑

1. **删缓存 ≠ 保证一致，只是把不一致的概率压到极低**。真正的兜底是 TTL（最终一致）。
2. **「删除缓存」要放在事务提交之后**，否则并发下会读到未提交的旧值再写回缓存 —— 详见实战笔记的 `updateShop`。
3. **逻辑过期方案没有物理 TTL，意味着内存不会自动回收**，数据被删除时也不会自动清理。
4. **缓存空对象要设一个较短的 TTL**（本项目 2 分钟），不能和正常数据一样长，否则数据库里新增了这条数据也读不到。
5. **雪崩和击穿都会表现为「DB 被打挂」，但根因不同** —— 一个要加随机 TTL + 集群，一个要加锁 / 逻辑过期，别治错。
6. **互斥锁的 `DEL` 必须校验锁的归属**，否则会误删别人的锁（这是分布式锁的核心问题，course 第 4 章才会展开）。
