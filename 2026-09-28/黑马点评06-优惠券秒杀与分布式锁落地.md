### 4.3 一人一单 + 乐观锁扣库存（**活代码**，`VoucherOrderServiceImpl.java:288-322`）

```java
@Transactional
    public void creatVoucherOrder(VoucherOrder order)
    {
        Long userId = order.getUserId();

        Long voucherId = order.getVoucherId();
        Integer count = query().eq("voucher_id", voucherId).eq("user_id", userId).count();

        if(count>0)
        {
             log.error("每个用户只能下一单!");
             return;
        }

        //扣减库存,考虑到超卖,使用乐观锁()
        //方法一,如果cas中stock和当前对象get的stock不一致就失败->导致多线程抢一个秒杀券会有高失败率
        //业务上我们只需要保证stock大于0,就可以继续购买,因此采用方案二
        //boolean success = iSeckillVoucherService.update()
        // .setSql("stock = stock - 1").eq("voucher_id", voucherId).eq("stock",voucher.getStock())
        // .update();

        boolean success = iSeckillVoucherService.update().
                setSql("stock = stock -1 ")
                .eq("voucher_id", voucherId).gt("stock", 0).update();
        if(!success)
        {
            log.error("库存不足");
           return;
        }

        //创建订单

        save(order);
        return ;
    }
```

这段是**活的**，也是今天的核心产出。要点：

- **`@Transactional` 在方法上**（`:288`）。生效前提是**外部经代理调用**——所以入口用 `AopContext.currentProxy()`，见 4.4
- **一人一单**（`:294-300`）：`query().eq("voucher_id",...).eq("user_id",...).count()`，查 `tb_voucher_order`，`count > 0` 就 `return`
- **乐观锁方案二**（`:309-311`）：SQL 是 `UPDATE tb_seckill_voucher SET stock = stock - 1 WHERE voucher_id = ? AND stock > 0`
- **方案一被注释**（`:305-307`）：`eq("stock", voucher.getStock())` —— 要求「扣减时的库存 == 查询时的库存」

**为什么方案一不行、方案二行？**

| 方案 | WHERE 条件 | 失败场景 | 结论 |
| --- | --- | --- | --- |
| 一 | `stock = 100`（查到的值） | 100 个线程都查到 100，只有 1 个成功，其余 99 个**库存其实够却全失败** | 成功率太低 |
| **二** | `stock > 0` | 只要还有货就能扣，串行扣到 0 | **采用** |

> 一句话：方案一锁「**值没变过**」，方案二锁「**业务约束（还有货）**」。我们要保证的是后者。
>
> **顺带提一个课程笔误**：课程原文 `Redis实战篇.md:1397` 写的是 `.update().gt("stock",0)` —— `gt` 写到了 `update()` **后面**，MyBatis-Plus 里不成立。学生写的 `.gt("stock", 0).update()`（`:310-311`）**顺序正确**，课程那份才是错的。

### 4.4 `@EnableAspectJAutoProxy(exposeProxy = true)` + `AopContext.currentProxy()`（为什么必需）

`HmDianPingApplication.java:8-11`：

```java
@MapperScan("com.hmdp.mapper")
@SpringBootApplication
@EnableAspectJAutoProxy(exposeProxy = true)
public class HmDianPingApplication {
```

**这是整篇最容易被忽略、也最容易踩的地方。** 四步拆开：

**第一步：`@Transactional` 靠「代理」生效。** Spring 给带 `@Transactional` 的 Bean 生成**代理对象**。外部调用先打代理 → 代理开事务 → 再调真实方法。你自己 `new` 的对象没有事务能力。

**第二步：同类内部调用会绕过代理。** `this.creatVoucherOrder(...)` 走的是**原始对象的方法**，没经过代理，所以 `@Transactional` 形同虚设（`this` 是真实对象，不是代理）。

**第三步：`exposeProxy = true` 把代理对象挂到当前线程，供手动取出。** 它让 Spring 把代理存进 `AopContext`（本质是 `ThreadLocal`），`AopContext.currentProxy()` 就能取出来：

```java
IVoucherOrderService o = (IVoucherOrderService) AopContext.currentProxy();
return o.creatVoucherOrder(voucherId);   // ✅ 经代理，事务生效
```

> **不配 `exposeProxy = true` 的后果**：`AopContext.currentProxy()` 抛 `IllegalStateException: Cannot find current proxy`。
> 「`@EnableAspectJAutoProxy(exposeProxy = true)`」和「`AopContext.currentProxy()`」是**配套的一对**，缺一不可。

**第四步：为什么非要把 `creatVoucherOrder` 拆出来？** 因为**锁必须包住整个事务**，不能包在事务里面：

```text
✅ 正确：锁在外、事务在内（当前写法）
   加锁 → [ 开启事务 → 查重 → 扣库存 → 建单 → 提交事务 ] → 解锁

❌ 错误：事务在外、锁在内
   开启事务 → [ 加锁 → 查重 → 扣库存 → 建单 → 解锁 ] → 提交事务
                                   ↑ 锁已释放，但事务还没提交
                                     另一线程查重读不到未提交的订单 → 重复下单
```

课程（`Redis实战篇.md:1571`）原话：*「如果你在方法内部加锁，可能会导致当前方法事务还没有提交，但是锁已经释放」*。所以**锁加在入口、事务加在下单方法**。

### 4.5 `SimpleRedisLock` 完整实现（活代码，但**当前无人调用**）

`SimpleRedisLock.java:12-54`：

```java
public class SimpleRedisLock implements ILock{

    private String name ;

    private StringRedisTemplate stringRedisTemplate;

    private static final String KEY_PREFIX = "lock:";

    //每个jvm的threadid都是自增的,如果多线程操控同一个用户购买,有可能导致threadid相等
    //加上UUID是为了避免两个jvm的线程id对上导致误删锁
    //UUID保证每个JVM唯一,getid保证每个JVM内部的线程id唯一
    private static final String ID_PREFIX = UUID.randomUUID().toString(true)+"-";

    private static final DefaultRedisScript<Long> UNLOCK_SCRIPT;
    static {
        UNLOCK_SCRIPT = new DefaultRedisScript<>();
        UNLOCK_SCRIPT.setLocation(new ClassPathResource("unlock.lua"));
        UNLOCK_SCRIPT.setResultType(Long.class);
    }


    public SimpleRedisLock(String name, StringRedisTemplate stringRedisTemplate) {
        this.name = name;
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public boolean tryLock(Long timeout) {
        String key = KEY_PREFIX+name;

        String id = ID_PREFIX + Thread.currentThread().getId();

        Boolean success = stringRedisTemplate.opsForValue().setIfAbsent(key, id, timeout, TimeUnit.SECONDS);

        return Boolean.TRUE.equals(success);
    }

    @Override
    public void releaseLock() {
        stringRedisTemplate.execute(UNLOCK_SCRIPT,
                Collections.singletonList(KEY_PREFIX+name),
                ID_PREFIX + Thread.currentThread().getId());
    }
```

配套接口 `ILock.java:3-10` 只有两个方法：`boolean tryLock(Long timeout)` 和 `void releaseLock()`。

要点：

| 点 | 说明 |
| --- | --- |
| `setIfAbsent(key, id, timeout, SECONDS)` | **一条命令**完成「抢锁 + 设 TTL」= `SET key id NX EX timeout`，原子 |
| `ID_PREFIX + threadId` | value = 「哪台 JVM（UUID）」+「哪个线程（id）」，全局唯一，释放时认领 |
| `Boolean.TRUE.equals(success)` | `setIfAbsent` 返回**包装类型**，pipeline / 事务里是 `null`，直接拆箱会 NPE |
| `releaseLock` 用 Lua | 「GET 比对 + DEL」封装在 `unlock.lua`，整段原子，杜绝「判断完的瞬间锁易主」 |
| `ID_PREFIX` 是 `static final` | 每个 JVM 只生成**一个** UUID；写在方法里则同线程两次调用标识不同，**自己的锁永远删不掉** |

| 方面 | `SimpleRedisLock` | Redisson |
| --- | --- | --- |

| 看门狗续期 | ✗ | ✓（不传 leaseTime 时生效） |
| 重试等待 | ✗（只试一次） | ✓（`tryLock(waitTime, ...)`） |

> 注释代码里还留着 `//SimpleRedisLock simpleRedisLock = new SimpleRedisLock(...)` 和下一行的 `RLock lock = redissonClient.getLock(...)`（`:261-262`）——**两行并排，一眼看出从手写锁切到 Redisson 的现场**。

## 五、易错点

1. **`seckillVoucher` 有三套，别认错。** `:186-208`（活，Lua+Stream）、`:210-239`（注释，Lua+阻塞队列）、`:242-286`（注释，DB 版）。今天讲的是**第三套，注释状态**。把 `:242-286` 说成「已实现」就是错的。
2. **注释掉的 DB 版和当前接口不兼容。** `:271` 调 `o.creatVoucherOrder(voucherId)` 传 `Long`；但 `creatVoucherOrder`（`:289`）和 `IVoucherOrderService.java:19` 收的是 `VoucherOrder`。**放开注释会编译失败。**
3. **`@Transactional` 不配 `exposeProxy` 会失效。** 同类内部 `this.xxx()` 绕过代理；而 `AopContext.currentProxy()` 又要求 `@EnableAspectJAutoProxy(exposeProxy = true)`（`HmDianPingApplication.java:10`）。**缺一不可。**
4. **`synchronized` 在多机下必然失效。** 它是 JVM 级锁，两台 Tomcat 各有一把，互相看不见。注释代码里「根据用户id加锁,intern保证引用是同一个对象」（`:281-285`）只是**单机**的正确做法，到集群就废——这正是分布式锁存在的理由。
5. **锁的 key 只带 `userId`，不带 `voucherId`。** `getLock("order:" + order.getUserId())`（`:167`）、`getLock("order:" + userId)`（`:262`）意味着同一用户抢任何券都共用一把锁。「一人一单」是按券算的，锁却按人算——**粒度偏大**，同一用户抢 A 券会阻塞抢 B 券。正确粒度应是 `order:{userId}:{voucherId}`。
6. **`throw new RuntimeException(e)` 丢了原始异常语义。** `:179` 和 `:274`。日志里只看到 `RuntimeException`；不过它靠 `@Transactional` 默认「`RuntimeException` 才回滚」的规则，能回滚。
7. **`if (voucher.getStock() < 1)` 是「读后判」的竞态。** 注释版 `:254` 和课程版都有它，**本身不防超卖**——真正的防线是扣减时的 `gt("stock", 0)`（`:311`）。它只是「快速失败」。
8. **`new SingleThreadExecutor()` 没关、字段名还拼错了。** `:74`：`SECKILL_ORDER_EXCUTOR`（`EXCUTOR` 拼错），非 `static final`、无 `@PreDestroy`，用的是**无界队列**，任务堆积会 OOM。
9. **`RedisIdWorker` 的起点时间戳和课程不一致。** `RedisIdWorker.java:16`：`BEGIN_TIMESTAMP = 1767225600L`（**2026-01-01 UTC**），课程是 `1640995200L`（2022-01-01）。`nextId` 的 key 还多一个**尾冒号**（`:31`），课程没有。
10. **`tb_voucher_order` 没有唯一索引。** `hmdp.sql:1266-1278` 只有 `PRIMARY KEY (id)`，**没有 `UNIQUE(user_id, voucher_id)`**。所以「一人一单」全靠**代码 + 锁**，数据库层没有兜底——某条路径漏加锁，重复数据就能落库。
11. **配置 / 常量 / import 的整洁问题。** `RedissonConfig.java:17` 硬编码 IP 和密码、和 `application.yaml` 重复一份；`LOCK_SHOP_KEY`/`LOCK_HOT_SHOP_KEY`（`RedisConstants.java:19/21`）只被 `ShopServiceImpl` 里**注释掉的**代码引用，实际已是死常量，而 `SimpleRedisLock.java:18` 又自己写了一份 `"lock:"`（`CacheClient` 用的是 `LOCK_KEY`，`RedisConstants.java:17`）—— 同一个前缀在两处各定义了一遍；`VoucherOrderServiceImpl.java:17` 的 `import com.sun.xml.internal.bind.v2.TODO;` 是 **JDK 9+ 不可访问的内部包**（IDE 手滑），`:5/:22/:31` 的 import 只被注释引用或没用。

## 六、不依赖前端的验证方法

前提：MySQL（`application.yaml:8`）+ Redis（`:12`）都在，应用起在 **8081**（`application.yaml:2`）。

### 6.1 curl 走一遍全链路

```bash
BASE=http://localhost:8081

# 1) 发验证码（打印在后端日志）；2) 登录拿 token
curl -s -X POST "$BASE/user/code?phone=17300001111"

# 3) 新增一张秒杀券（库存 100），记下返回的 data = voucherId
curl -s -X POST "$BASE/voucher/seckill" -H "authorization: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"shopId":1,"title":"测试秒杀","payValue":100,"actualValue":1000,"type":1,"status":1,
       "stock":100,"beginTime":"2026-01-01T00:00:00","endTime":"2030-01-01T00:00:00"}'
```

> 第 4 步验证「一人一单」；第 5 步看 Redis 库存少 1。
> 但**这两个都验证不了并发**——单用户串行请求，超卖复现不出来。要压并发用 6.2。

### 6.2 JUnit 并发压测（真正能暴露超卖）

`CountDownLatch` 让 N 个线程**同时**抢同一张券，跑完核对库存不为负。

```java
@SpringBootTest
class SeckillConcurrencyTest {
    @Resource private IVoucherOrderService voucherOrderService;
    @Resource private StringRedisTemplate stringRedisTemplate;

    @Test
    void testSeckillOverSell() throws InterruptedException {
        int threads = 200;
        Long voucherId = 1L;
        stringRedisTemplate.opsForValue().set("seckill:stock:" + voucherId, "100");

        CountDownLatch start = new CountDownLatch(1);       // 发令枪
        CountDownLatch done  = new CountDownLatch(threads); // 都跑完
        ExecutorService pool = Executors.newFixedThreadPool(threads);
        for (int i = 0; i < threads; i++) {
            pool.submit(() -> {
                try { start.await(); } catch (InterruptedException ignored) { }
                try { voucherOrderService.seckillVoucher(voucherId); }
                finally { done.countDown(); }
            });
        }
        start.countDown();     // 一起冲
        done.await();
        pool.shutdown();

        System.out.println("剩余库存 = " +
            stringRedisTemplate.opsForValue().get("seckill:stock:" + voucherId));   // 期望 0
    }
}
```

**判读标准**：剩余库存 = `0` → ✓ 无超卖；= 负数 → ✗ 超卖（锁/乐观锁没挡住）。

> **注意**：直调 `seckillVoucher` 会走 `UserHolder.getUser()`，压测线程没有登录态会 **NPE**——要先塞 `UserHolder.saveUser(...)`，
> 或改成只验数据库 `SELECT stock FROM tb_seckill_voucher WHERE voucher_id = 1;`（`>= 0` 即无超卖）。

## 七、可以更好的地方

> 同 09-21 篇的写法：**现状 → 问题 → 怎么改**。

### 7.1 锁的 key 加上 voucherId

**现状 → 问题**：`getLock("order:" + userId)`（`VoucherOrderServiceImpl.java:167`）按用户维度加锁，同一用户抢 A 券会阻塞他抢 B 券；而「一人一单」的语义本就是**按券**的。
**改法**：`redissonClient.getLock("order:" + userId + ":" + voucherId);`

### 7.2 给 `tb_voucher_order` 加唯一索引做兜底

**现状 → 问题**：`hmdp.sql:1266-1278` 没有 `(user_id, voucher_id)` 唯一索引，全靠代码判重，任何绕过锁的路径（将来加别的下单入口、用 MQ）都可能插入重复订单。
**改法**：

```sql
ALTER TABLE tb_voucher_order ADD UNIQUE INDEX uniq_user_voucher (user_id, voucher_id);
```

> 加上之后，代码层 `count() > 0` 从「唯一防线」降级为「友好提示」——即使并发漏过，也会被数据库拒绝（`DuplicateKeyException`），**数据永远干净**。

### 7.3 Redis 库存与 MySQL 库存「各扣各的」要对齐

**现状 → 问题**：`addSeckillVoucher` 往 MySQL 和 Redis 各写一份库存（`VoucherServiceImpl.java:55-57`）；注释版 `creatVoucherOrder` 扣的是 **MySQL**（`:309`），Lua 版 `seckillOrder.lua:25` 扣的是 **Redis**。两套库存**独立**，一旦不一致（重启丢 Redis、手工改库）就会出现「Redis 说没货、DB 还有」或反之。
**改法**：选一条**唯一权威**来源，另一侧只做展示，并明确同步策略（如定时对账）。别让两边都当真理。

### 7.4 `seckillVoucher` 里的时间检查拆成两条

**现状 → 问题**：注释版 `:249` 把「未开始」和「已结束」合并成一个 `if`、统一报「秒杀时间不符合当前」，用户无法区分是哪种，体验差、排障难。
**改法**：按课程原版（`Redis实战篇.md:1283-1291`）拆开：`isAfter` → 「秒杀尚未开始！」；`isBefore` → 「秒杀已经结束！」。

### 7.5 配置外置 + 清理死代码

**现状**：`RedissonConfig.java:17` 硬编码 IP 和密码，且和 `application.yaml` 重复一份；`SimpleRedisLock` / `ILock` 全工程只在注释里被引用；`VoucherOrderServiceImpl` 有 `com.sun.xml.internal.bind.v2.TODO`（JDK9+ 编译隐患）等无用 import。
**改法**：Redisson 用 `@Value("${spring.redis.host}")` 等从配置读地址密码，和 Spring Redis 共用一个来源；删掉不再使用的类与 import。

```java
config.useSingleServer().setAddress("redis://" + host + ":" + port).setPassword(password);
```

> 「演进痕迹」留着学习可以，但**别让它影响编译**——尤其 `com.sun.xml.internal.*`，换个 JDK 就编不过。

| 改动 | 成本 | 收益 | 建议 |
| --- | --- | --- | --- |

| `tb_voucher_order` 加唯一索引 | 一条 SQL | 高（数据层兜底） | **建议做** |
| 锁 key 加 `voucherId` | 一行 | 中（锁粒度正确） | 建议做 |
