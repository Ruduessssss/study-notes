### 1. AQS (AbstractQueuedSynchronizer) 原理

AQS 是阻塞式锁和相关的同步器工具的框架。它的核心设计思想包含以下几个要点：  

- **状态维护 (State)：** 使用一个 32 位的 `int` 类型的 `state` 属性来表示资源的状态，分为独占模式和共享模式。`state` 使用 `volatile` 配合 CAS 机制来保证修改时的原子性。  
- **阻塞等待队列：** 提供了一个基于 FIFO 的单向无锁队列（借鉴了 CLH 队列的设计）。队列中有 `head` 和 `tail` 两个指针节点，第一个节点通常是 Dummy（哑元/哨兵）节点用来占位。  
- **线程阻塞与恢复：** 底层使用 `park` 和 `unpark` API 来实现线程的精确暂停和恢复。  
- **获取与释放逻辑：** 当线程获取锁失败时，会被封装成 Node 加入等待队列并阻塞；当持有锁的线程释放锁时（`state` 状态允许），会唤醒（`unpark`）队列中的下一个阻塞线程。  
- **扩展性：** 子类需要重写 `tryAcquire`、`tryRelease`、`tryAcquireShared` 等方法来定义如何维护状态以及获取/释放锁的逻辑。

### 1.核心机制：两次“插队”机会

非公平锁之所以“非公平”，是因为新来的线程在进入阻塞队列排队之前，有两次无视队列排队情况、直接抢占锁的机会：

- **第一次插队（抢先 CAS）：** 当线程调用 `lock()` 方法时，非公平锁会直接且霸道地执行一次 CAS 操作 `compareAndSetState(0, 1)`。如果此时刚好锁被释放（`state` 为 0），这个新来的线程就能瞬间抢到锁，完全无视 AQS 队列中是否还有几百个线程在苦苦等待。
- **第二次插队（`tryAcquire` 盲抢）：** 如果第一次 CAS 失败，线程会走入正常的获取流程（调用 AQS 的 `acquire(1)`）。在底层的 `nonfairTryAcquire` 方法中，线程会再次检查 `state`。如果发现 `state == 0`，它会**再次直接执行 CAS 抢锁**，依然不检查队列中是否有其他等待者。

### 2. 公平与非公平的代码级差异

公平锁与非公平锁在实现上绝大部分代码是共用的（都基于 AQS），唯一的本质区别在于 `tryAcquire` 抢锁逻辑中的一行代码：

- **公平锁：** 在发现 `state == 0` 可以抢锁时，会先调用 `hasQueuedPredecessors()` 方法。这个方法会去 AQS 队列里看一眼，如果前面有人排队，自己就乖乖去后面排队。
- **非公平锁：** 根本没有 `hasQueuedPredecessors()` 这个判断。只要看到 `state == 0`，上去就是一把 CAS 抢占。

### 3. 排队后的行为 (FIFO)

**非公平锁的“非公平”仅发生在线程进入队列之前**。 一旦这两次插队机会都失败了，线程依然会被封装成 Node 加入到 AQS 的双向阻塞队列中，并调用 `park` 挂起。进入队列后，这些线程只能老老实实地遵循 FIFO（先进先出）的原则，按顺序被前驱节点唤醒，不能再在队列内部插队。

### 4. 为什么默认使用非公平锁？

在 `ReentrantLock` 中，无参构造函数默认创建的就是非公平锁。

- **优点（极高的吞吐量）：** 线程被挂起（`park`）和唤醒（`unpark`）需要进行系统级的上下文切换，开销很大。非公平锁大概率能让新来的（处于活跃状态的）线程直接拿到锁，省去了大量的上下文切换开销，整体性能极高。
- **缺点（线程饥饿风险）：** 在极端高并发且锁竞争激烈的场景下，可能导致 AQS 队列中的某些老实排队的线程一直被新来的活跃线程抢走锁，长时间无法运行（即“饥饿”现象）。

读写锁的特点是读读共享、读写互斥、写写互斥。它在底层使用的是同一个 AQS `Sync` 同步器。  

- **State 划分：** 读写锁巧妙地将 32 位的 `state` 拆分为两部分：低 16 位用来表示写锁状态（独占计数），高 16 位用来表示读锁状态（共享计数）。  
- **写锁上锁：** 尝试获取写锁时，如果 `state` 不为 0 且存在读锁，或者持有写锁的不是当前线程，则获取失败并进入 AQS 队列阻塞。  
- **读锁上锁：** 获取读锁时，如果发现有其他线程持有写锁，则获取失败并封装为 `Node.SHARED` 模式的节点进入队列等待。如果没有写锁阻碍，则通过 CAS 增加 `state` 的高 16 位计数。  
- **链式唤醒 (传播机制)：** 当一个读锁成功获取后（或写锁释放后唤醒了第一个读线程），如果它发现 AQS 队列紧跟在后面的节点也是共享模式（读锁），它会调用 `setHeadAndPropagate` 和 `doReleaseShared` 触发连续唤醒，让排队的读线程都能恢复运行。

条件变量的实现类是 AQS 内部的 `ConditionObject`，类似于 Monitor 的 WaitSet。  

- **独立的等待队列：** 每个条件变量都对应着一个独立的等待队列，包含 `firstWaiter` 和 `lastWaiter` 指针。  
- **await (等待) 流程：**
  - 当线程调用 `await` 时，会创建一个状态为 `-2` (`Node.CONDITION`) 的新 Node，并加入到条件变量的等待队列尾部。  
  - 随后调用 `fullyRelease` 释放该线程在 AQS 同步器上持有的所有锁，并唤醒 AQS 队列中的下一个竞争节点。  
  - 最后，该线程调用 `park` 阻塞自己。  
- **signal (唤醒) 流程：**
  - 当其他线程调用 `signal` 时，会取得条件等待队列中的第一个节点 (`firstWaiter`)。  
  - 执行 `transferForSignal` 将该节点从条件等待队列转移到 AQS 的同步等待队列尾部，并将其状态从 `-2` 更改为 `0`。  
  - 被转移的线程将在后续被 `unpark` 唤醒，然后重新在 AQS 队列中竞争锁。

Semaphore 的原理类似停车场，`permits` 许可数量就对应 AQS 中的 `state` 值。  

- **acquire (获取资源)：**

  - 底层调用 `acquireSharedInterruptibly`。  
  - 尝试获取时，计算 `available - acquires`。如果剩余许可量 `< 0`，说明资源已耗尽，获取失败，线程封装为节点进入 AQS 队列并 `park` 阻塞。  
  - 如果剩余许可量 `>= 0`，则通过 CAS 成功修改 `state`。  

- **release (释放资源)：**

  - 底层调用 `releaseShared`。  
  - 利用 CAS 操作将 `state` 增加对应的释放量。  
  - 如果释放成功，调用 `doReleaseShared()` 唤醒 AQS 队列中等待的下一个头节点。  

- **PROPAGATE 状态解决 Bug：** 在早期的 JDK 版本中，连续快速的 `releaseShared` 可能会导致后继节点无法被正常唤醒。为了解决这个 Bug，引入了值为 `-3` 的 `Node.PROPAGATE` 状态，确保释放信号量的操作能够向后传播，成功唤醒后续排队的线程。

  `LinkedBlockingQueue` 是一种基于链表实现的、可选有界的**阻塞队列**，其核心设计思想在于“锁分离”。
  
  - **双锁机制 (Two-Lock Queue)：** 这是它高并发的核心。内部使用了两把独立的 `ReentrantLock`：`putLock` 控制入队，`takeLock` 控制出队。这意味着生产者和消费者可以**真正地并发执行**，互不干扰（相比之下，`ArrayBlockingQueue` 只用了一把锁，存取互斥）。
  - **条件变量阻塞：** 配合双锁，使用了两个 `Condition` 条件变量。`notFull` 挂在 `putLock` 上，当队列满时阻塞生产者；`notEmpty` 挂在 `takeLock` 上，当队列空时阻塞消费者。
  - **原子化计数：** 队列的元素数量 `count` 使用的是 `AtomicInteger`。因为入队和出队分别持有不同的锁，却又都要修改总数，所以必须依靠底层的 CAS 原子操作来保证计数的线程安全。
  - **节点结构：** 采用单向链表结构，并且初始化时会创建一个哑元节点（Dummy Node，`head.item == null`）作为头节点，简化了链表首尾操作的临界状态处理。
  
  ### 6、 ConcurrentLinkedQueue 原理 (非阻塞并发)
  
  `ConcurrentLinkedQueue` 是一种基于链表实现的、无界的**非阻塞并发队列**，其核心设计思想是“无锁化 (Lock-Free)算法”。
  
  - **完全基于 CAS 机制：** 全程不使用任何互斥锁，而是采用 Michael-Scott 非阻塞队列算法。通过死循环（自旋）结合 CAS (Compare-And-Swap) 和 `volatile` 变量来保证多线程环境下的节点入队和出队安全。
  - **HOPS 延迟更新策略：** 频繁的多线程 CAS 竞争会导致严重的性能损耗。为了优化，它的 `head` 和 `tail` 节点指针**并非每次入队或出队都立刻更新**，而是允许指针滞后于真实的队首或队尾（通常相差超过 1 个节点时才触发 CAS 更新）。这极大地减少了争用。
  - **入队逻辑 (offer)：** 线程入队时，会顺着 `tail` 指针向后遍历寻找真正的尾节点（即 `next` 为 null 的节点），然后通过 CAS 尝试将新节点挂接在末尾。
  - **出队逻辑 (poll)：** 线程出队时，顺着 `head` 指针寻找第一个包含非空数据的节点，通过 CAS 将其数据域 (`item`) 修改为 null 实现**逻辑删除**，随后再推进头指针并断开废弃节点协助 GC 垃圾回收。
