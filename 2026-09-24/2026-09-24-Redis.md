# Redis 知识点：Lua 脚本与原子性

## 一、问题的起点：「多条命令」不是原子的

Redis 单线程只能保证**一条命令**原子。一旦业务需要「先读、判断、再写」三步，中间就可能被别的请求插进来：

```text
线程A: GET lock  →  "A的标识"
                            ← 线程B 的请求插进来了
线程B: GET lock  →  "A的标识"
       DEL lock
线程A:               DEL lock      ← 删掉了 B 的锁！
```

这就是**分布式锁误删**的根源。`GET` 和 `DEL` 各自原子，但**合起来不是**。

### 1.1 为什么不能靠 Java 加锁解决

你可能会想：「在 Java 里给这段代码加个 `synchronized` 不就行了？」

不行。因为这个场景是**多台 Tomcat**，`synchronized` 是 JVM 级别的锁，管不住别的进程。
**要保证「跨进程的多条 Redis 命令」的原子性，就必须让这几条命令在 Redis 内部执行。**

## 二、Lua 脚本：把多条命令打包成一条

Redis 从 2.6 开始支持执行 Lua 脚本。核心价值就一句话：

> **Redis 会把整个 Lua 脚本当成一条命令来执行 —— 期间不会插入任何其他客户端的命令。**

所以只要把「读 + 判断 + 删」写进一个脚本，它们就天然是原子的。

### 2.1 为什么是 Lua

| 方案 | 问题 |
| --- | --- |
| `MULTI` / `EXEC` 事务 | **不能根据中间结果做判断** —— `EXEC` 之前读不到值，做不到「如果值等于 X 才删」 |
| 客户端加锁 | 跨进程无效 |
| **Lua 脚本** | ✓ 能读、能判断、能写，且整体原子 |

> `MULTI/EXEC` 的关键短板是**命令在 `EXEC` 之前只是入队、不会执行**，所以没法「先看结果再决定下一步」。
> 而 Lua 是在服务端真正跑起来的代码，有条件分支、有循环。这是它不可替代的地方。

### 2.2 一个最简单的 Lua 脚本

```lua
-- 返回 Redis 当前的版本号（`redis.call` 是调用 Redis 命令的唯一入口）
return redis.call('set', KEYS[1], ARGV[1])
```

```text
EVAL "return redis.call('set', KEYS[1], ARGV[1])" 1 name jack
     └─────────────── 脚本 ──────────────────┘  ↑  ↑     ↑
                                                │  │     └─ ARGV[1] = jack
                                                │  └─────── KEYS[1] = name
                                                └────────── 后面跟几个 KEYS
```

## 三、`KEYS` 和 `ARGV`：参数必须从这两个数组拿

**这是一个硬性约定，也是个高频考点。**

Lua 脚本里**绝对不能直接写死 key 的名字**，必须通过 `KEYS` 数组传入。

### 3.1 为什么要这么设计

根本原因是 **Redis 集群**。

集群会把 key 分散到不同的节点上。如果一个脚本操作了 `KEYS[1]` 和 `KEYS[2]`，Redis 需要先确认这两个 key **在同一个槽（slot）**，才能放心地把脚本发给那个节点执行。

如果 key 是写死在脚本字符串里的，Redis 就**没法提前分析**这个脚本会碰哪些 key —— 那就没法保证路由正确。

> 所以 `KEYS` 的存在意义不是「好看」，而是**让 Redis 能在执行前校验 key 的分布**。
>
> **推论**：在集群模式下，一个 Lua 脚本里涉及的所有 key **必须落在同一个槽**。
> 兜底办法是用 hash tag：`{order}:1` 和 `{order}:2` 会被强制分到同一个槽。

### 3.2 约定

| 位置 | 含义 | Java 侧对应 |
| --- | --- | --- |
| `KEYS[1]`、`KEYS[2]`… | 脚本要操作的 **key** | `execute(script, List<K> keys, ...)` |
| `ARGV[1]`、`ARGV[2]`… | 其他**参数**（不是 key 的） | `execute(script, keys, Object... args)` |

**Lua 的下标从 1 开始**，不是 0 —— 写惯了 Java 很容易栽在这。

## 四、在 Java 里调用 Lua

### 4.1 用 `DefaultRedisScript` 加载脚本文件

```java
private static final DefaultRedisScript<Long> UNLOCK_SCRIPT;

static {
    UNLOCK_SCRIPT = new DefaultRedisScript<>();
    UNLOCK_SCRIPT.setLocation(new ClassPathResource("unlock.lua"));   // 从 resources 读
    UNLOCK_SCRIPT.setResultType(Long.class);                          // 返回值类型
}
```

三个要点：

1. **`static` 块里初始化** —— 脚本只需要加载一次，是全局共享的常量
2. **`setLocation` 从 `resources` 目录读文件**，脚本和 Java 代码分开维护，比把 Lua 字符串塞在 Java 里可读性好得多
3. **`setResultType(Long.class)` 必须设**。Lua 的返回值要反序列化成 Java 对象，Redis 返回的整数在 Java 里可能是 `Integer` 也可能是 `Long`，不指定的话会 **`ClassCastException`**

### 4.2 执行

```java
stringRedisTemplate.execute(
        UNLOCK_SCRIPT,
        Collections.singletonList(KEY_PREFIX + name),                  // KEYS
        ID_PREFIX + Thread.currentThread().getId()                     // ARGV
);
```

签名是 `execute(RedisScript<T> script, List<K> keys, Object... args)`。

> `Collections.singletonList(...)` 是**只含一个元素的不可变 List** —— 比 `Arrays.asList()` 更轻量，
> 用在「只有一个 key」这种最常见的场景。

## 五、Lua 里能写什么

| 能力 | 说明 |
| --- | --- |
| `redis.call('cmd', ...)` | 调用任意 Redis 命令，返回值和命令一致 |
| `redis.pcall('cmd', ...)` | 同上，但**出错时返回错误对象而不中断脚本** |
| `if / else / while / for` | 完整的条件与循环 |
| `tonumber(x)` | 字符串转数字（**`ARGV` 里拿到的都是字符串**） |
| `return` | 返回值会传给调用方；`return nil` 会被转成 Java 的 `null` |

### 5.1 几条硬性限制

1. **`redis.call` 出错会直接中断整个脚本**，已经执行过的命令**不会回滚**（Lua 脚本不是事务）
2. **不能访问系统时间、不能有随机性**。Lua 环境下 `os.time`、`math.random` 被封了，因为主从复制时脚本要在各节点重放，结果必须一致
3. **脚本要短**。整个 Redis 在脚本执行期间是**被阻塞**的，长脚本会卡死所有请求
4. **不要 `KEYS *`**。Lua 里禁止执行会遍历全库的命令

## 六、命令 / API 对照

| Java | 对应 | 说明 |
| --- | --- | --- |
| `stringRedisTemplate.execute(script, keys, args...)` | `EVAL <script> <numkeys> <keys...> <args...>` | 每次传完整脚本 |
| （Spring 内部自动优化） | `EVALSHA <sha1> ...` | 脚本内容按 SHA1 缓存，后续只传哈希值 |
| `redis-cli SCRIPT LOAD "<lua>"` | — | 手动预加载，返回 sha1 |
| `redis-cli EVALSHA <sha1> ...` | — | 用哈希执行已加载的脚本 |

> **`EVAL` vs `EVALSHA`**：`EVAL` 每次都把整段 Lua 发给 Redis（浪费带宽）。
> 客户端一般会先 `SCRIPT LOAD` 拿到 sha1，之后用 `EVALSHA` 只传 40 字节的哈希。
> Spring Data Redis 的 `DefaultRedisScript` **已经帮你做了这层优化**，所以你只写 `execute` 就行。

## 七、概念层面要注意的坑

1. **Lua 保证的是「不被其他命令插入」，不是「失败自动回滚」**。脚本里前半段成功、后半段报错时，前半段是**真的生效了**。
2. **`KEYS` 和 `ARGV` 都是字符串**。`ARGV` 里拿到的是 `"123"` 不是 `123`，做数值比较前要 `tonumber()`。
3. **Lua 下标从 1 开始**。
4. **`redis.call` 的返回值类型要清楚**：`GET` 不存在时返回 **`false`**（Lua 里），转成 Java 是 `null`；`SISMEMBER` 返回 `0/1`。
5. **脚本里不要拼 key**。`KEYS[1]` 传什么用什么，自己拼字符串在集群模式下会直接报错。
6. **`ClassCastException` 是高发错误**：忘了 `setResultType`，或者 Lua 返回了「多个值」而 Java 侧只要一个 `Long`。
