# ☕ 共享变量的可见性与 volatile 关键字

### 1. 共享变量的可见性问题 (退不出的循环)

在多线程中，如果一个线程通过 `while(run)` 循环等待，另一个线程修改了 `run = false`，循环可能永远不会停止。

**代码演示：**

Java

```
static boolean run = true; // 解决此死循环问题，需改为：static volatile boolean run = true;

public static void main(String[] args) throws InterruptedException {
    Thread t = new Thread(() -> {
        while(run) {
            // ... 疯狂空转，不打印任何内容
        }
    });
    
    t.start();
    Thread.sleep(1000); // 确保 t 线程已经运行并缓存了 run 的值
    
    run = false; // 主线程修改了值，但 t 线程由于缓存机制，根本停不下来
}
```

- **底层原因 (JIT 优化)**：为了减少对主存的频繁访问，JIT 编译器会将共享变量 `run` 缓存到当前线程（t 线程）的**工作内存**（高速缓存）中。主线程将主存中的 `run` 改为 `false` 后，t 线程依然在傻傻地读取自己缓存中的旧值 `true`。
- **解决方案**：引入 `volatile` 关键字修饰共享变量。它的核心作用是**禁用缓存优化**，强制要求线程每次读取该变量时，必须直接从主内存中获取最新值。

### 2. 核心考点：可见性 vs 原子性 (极易混淆)

面试中经常会问 `volatile` 能不能保证线程安全？答案是**不能完全保证**。

- **可见性**：`volatile` 能保证一个线程修改变量后，其他线程立刻**看见**最新值。
- **原子性**：`volatile` **无法保证**代码块的原子性。比如 `i++` 和 `i--`，即使加了 `volatile`，底层依然对应着多条指令。一旦发生线程上下文切换，指令依然会交错，导致结果被相互覆盖。

**字节码指令交错演示（假设 `i` 初始值为 0，已被 `volatile` 修饰）：**

Plaintext

```
// 线程 1 执行 i++，线程 2 执行 i--，由于非原子操作，出现以下交错：

getstatic i    // 线程2-获取静态变量i的最新值，线程内 i=0
getstatic i    // 线程1-获取静态变量i的最新值，线程内 i=0
iconst_1       // 线程1-准备常量 1
iadd           // 线程1-执行自增，线程内 i=1
putstatic i    // 线程1-将修改后的值存入主存，此时主存 i=1
iconst_1       // 线程2-准备常量 1
isub           // 线程2-执行自减，基于之前读取的 0 进行计算，线程内 i=-1
putstatic i    // 线程2-将修改后的值存入主存，此时主存 i=-1 (直接覆盖了线程1的正确结果！)
```

### 3. volatile 与 synchronized 的权衡

- **`synchronized` (重量级)**：既能保证代码块内操作的**原子性**，同时在获取锁和释放锁时会自动同步主存，因此也能保证**可见性**。缺点是会导致线程排队阻塞、发生上下文切换，性能开销相对较高。
- **`volatile` (轻量级)**：只能保证**可见性**（和有序性），无法保证原子性。但由于它绝不会引发线程阻塞，所以在“一写多读”的场景下（比如上面例子中简单的状态标志位 `run` 切换），性能远高于 `synchronized`。





## 有序性

### 1. 有序性与指令重排

- **指令重排**：JVM 和 CPU 会在不影响单线程程序正确性的前提下，调整语句的执行顺序，这种优化被称为“指令重排”。  
- **原理解析 (指令级并行)**：现代 CPU 为了提高效率，采用了流水线技术。如果多条指令相互之间没有依赖关系，CPU 会通过打乱原本的代码顺序，让多条指令并行处理，从而减少 CPU 的闲置和等待时间。

### 2. 多线程下的“诡异结果”

在多线程环境下，指令重排会导致致命的逻辑错误。 **场景分析**：  

Java

```
int num = 0;
boolean ready = false; 

// 线程1 执行
public void actor1(I_Result r) {
    if(ready) {
        r.r1 = num + num;
    } else {
        r.r1 = 1;
    }
}

// 线程2 执行
public void actor2(I_Result r) { 
    num = 2;
    ready = true; 
}
```

正常逻辑下，结果可能是 `1`（线程1先执行）或 `4`（线程2先执行完）。 **诡异结果 `0` 的产生**： 线程 2 内部发生了指令重排，先执行了 `ready = true`。此时发生了上下文切换，线程 1 运行，发现 `ready` 为 `true`，进入 `if` 分支执行 `num + num`，但由于此时 `num` 还未被赋值，所以算出来是 `0 + 0 = 0`。接着再切回线程 2 执行 `num = 2`。  

- **解决方法**：使用 `volatile` 关键字修饰 `ready` 变量，可以禁用指令重排。  

### 3. volatile 底层原理：内存屏障

`volatile` 的底层实现原理是**内存屏障 (Memory Barrier / Memory Fence)**。  

- **写屏障 (sfence)**：对 `volatile` 变量的写指令**之后**会加入写屏障。  
- **读屏障 (lfence)**：对 `volatile` 变量的读指令**之前**会加入读屏障。  

#### 3.1 如何保证“可见性”？

- **写屏障**：保证在该屏障之前的，所有对共享变量的改动，都会立刻被同步到主存当中。  
- **读屏障**：保证在该屏障之后的，所有对共享变量的读取，加载的都是主存中的最新数据（使得本地高速缓存失效）。  

#### 3.2 如何保证“有序性”？

- **写屏障**：确保指令重排序时，**不会将写屏障之前的代码排在写屏障之后**。  
  - *示例*：`num = 2; ready = true; // 写屏障`。`num=2` 绝对不会被重排到 `ready=true` 之后。  
- **读屏障**：确保指令重排序时，**不会将读屏障之后的代码排在读屏障之前**。  
  - *示例*：`// 读屏障 if(ready) { r.r1 = num + num; }`。`num+num` 绝对不会跑到读取 `ready` 之前去执行。  

### 4. ⚠️ 核心局限性 (易错点)

- **无法解决指令交错（不能保证原子性）**：写屏障仅仅是保证“之后”的读能够读到最新的结果，但它不能阻止其他线程在写入之前抢占 CPU。  
- **有序性的局限**：`volatile` 提供的有序性保证，仅仅是保证了**本线程内**的相关代码不被重排序，无法阻止多线程之间指令的微观交错执行。  



### 5. 经典实战：Double-Checked Locking (DCL) 单例模式与 volatile

**Double-Checked Locking (双重检查锁)** 是一种非常经典的单例模式实现方式。它的特点是**懒汉式实例化**，并且为了提高性能，只在首次创建对象时才使用 `synchronized` 加锁，后续访问均无锁。

#### 5.1 存在隐患的 DCL 实现（未加 volatile）

Java

```
public final class Singleton {
    private Singleton() { }
    
    // 致命缺陷：缺少 volatile 修饰
    private static Singleton INSTANCE = null; 

    public static Singleton getInstance() { 
        if(INSTANCE == null) { // 第一次检查：在同步块之外，不受 monitor 控制
            synchronized(Singleton.class) {
                if (INSTANCE == null) { // 第二次检查：在同步块之内
                    INSTANCE = new Singleton(); 
                } 
            }
        }
        return INSTANCE;
    }
}
```

**🔥 致命缺陷分析（指令重排引发的灾难）：** 问题的核心出在 `INSTANCE = new Singleton();` 这行代码上。在 JVM 字节码层面，创建一个对象并赋值主要包含以下三步：

1. `new`：分配对象内存空间。
2. `invokespecial`：调用构造方法，初始化对象。
3. `putstatic`：将 `INSTANCE` 引用指向分配好的内存地址。

由于 JVM 会进行**指令重排优化**，真实的执行顺序极有可能是 **1 -> 3 -> 2**。

- **交错场景**：假设线程 t1 执行了步骤 1 和 3（此时 `INSTANCE` 已经被赋了地址，不再是 `null`，但**构造方法尚未执行完毕**，是一个“半成品”）。
- **越界读取**：就在此时，线程 t2 进来了，执行最外层的 `if(INSTANCE == null)`。由于这行代码**在 `synchronized` 保护范围之外**，t2 发现引用不为空，直接将这个未初始化完毕的“半成品”对象返回去使用了，从而引发难以排查的 Bug！

#### 5.2 完美的 DCL 解决方案

解决方法非常简单，只需给 `INSTANCE` 加上 `volatile` 修饰符即可（注意：此特性在 JDK 5 及以上版本才真正完善生效）。

Java

```
public final class Singleton {
    private Singleton() { }
    
    // 完美方案：加入 volatile 修饰，禁用指令重排
    private static volatile Singleton INSTANCE = null; 
    
    public static Singleton getInstance() { 
        if (INSTANCE == null) { 
            synchronized (Singleton.class) { 
                if (INSTANCE == null) { 
                    INSTANCE = new Singleton();
                }
            }
        }
        return INSTANCE;
    }
}
```

**🛡️ volatile 的底层救赎（内存屏障）：** 加上 `volatile` 后，JVM 会在字节码层面插入**内存屏障 (Memory Barrier)**，底层还会利用 `lock` 指令来保证多核 CPU 之间的可见性与有序性：

- **保证有序性**：在给 `INSTANCE` 赋值的指令之后，会加入**写屏障**。它强制要求：写屏障之前的代码（即对象的构造和初始化 `invokespecial`）**绝对不能**被重排到写屏障之后执行。这保证了 t1 必须先老老实实把对象完全建好，才能把地址暴漏给 `INSTANCE`。
- **保证可见性**：写屏障保证了 t1 实例化完毕后的改动立刻同步到主存；而读屏障保证了 t2 在外层执行 `if(INSTANCE == null)` 检查时，必须从主存加载最新的状态。





### happens-before 规则总结

happens-before 规定了对共享变量的写操作对其它线程的读操作可见，它是可见性与有序性的一套规则总结。掌握以下 7 条核心规则，就能判断并发代码中是否存在可见性问题：

#### 📍 规则 1：Monitor 锁规则 (synchronized)

- **规则**：线程解锁（unlock）某个 monitor 之前对变量的写，对于接下来去加锁（lock）同一个 monitor 的其它线程对该变量的读**可见**。

Java

```
static int x;
static Object m = new Object();

new Thread(()->{
    synchronized(m) { x = 10; } // 解锁前写 x=10
},"t1").start();

new Thread(()->{
    synchronized(m) { System.out.println(x); } // 加锁后读 x，必定是 10
},"t2").start();
```

#### 📍 规则 2：volatile 变量规则

- **规则**：线程对 `volatile` 变量的写，对接下来其它线程对该变量的读**可见**。

Java

```
volatile static int x;

new Thread(()->{ x = 10; },"t1").start(); // 写 volatile
new Thread(()->{ System.out.println(x); },"t2").start(); // 读 volatile，必定是 10
```

#### 📍 规则 3：线程 start 规则

- **规则**：线程调用 `start()` 之前对变量的写，对该线程开始运行后对该变量的读**可见**。

Java

```
static int x;
x = 10; // 主线程在 t2 start 前写 x=10
new Thread(()->{
    System.out.println(x); // t2 线程启动后读 x，必定是 10
},"t2").start();
```

#### 📍 规则 4：线程终止规则 (join)

- **规则**：线程结束前对变量的写，对其它线程得知它结束后（例如调用 `t1.join()` 或 `t1.isAlive()` 为 false）的读**可见**。

Java

```
static int x;
Thread t1 = new Thread(()->{ x = 10; },"t1"); // t1 内部写 x=10
t1.start();

t1.join(); // 主线程等待 t1 结束
System.out.println(x); // 得知 t1 结束后读 x，必定是 10
```

#### 📍 规则 5：线程打断规则 (interrupt)

- **规则**：线程 t1 打断 t2（调用 `t2.interrupt()`）前对变量的写，对于 t2 得知自己被打断后（通过 `isInterrupted()`）对变量的读**可见**。

Java

```
static int x;

Thread t2 = new Thread(()->{
    while(true) {
        if(Thread.currentThread().isInterrupted()) {
            System.out.println(x); // 得知被打断后读 x，必定是 10
            break;
        }
    }
},"t2");
t2.start();

new Thread(()->{
    x = 10;          // 打断前写 x=10
    t2.interrupt();  // 发出打断信号
},"t1").start();
```

#### 📍 规则 6：默认值规则

- **规则**：对变量默认值（`0`, `false`, `null`）的写，对其它线程对该变量的读**可见**。即无论何时，线程绝不会读到未经过默认初始化的垃圾数据。

#### 📍 规则 7：传递性规则 (结合 volatile)

- **规则**：如果 A happens-before B，且 B happens-before C，那么 A happens-before C。
- **实战意义**：经常配合 `volatile` 的防指令重排特性，实现**普通变量的可见性**。

Java

```
volatile static int x; // 必须是 volatile
static int y;          // 普通变量

new Thread(()->{ 
    y = 10;  // 步骤 A (写普通变量)
    x = 20;  // 步骤 B (写 volatile 变量，带写屏障)
},"t1").start();

new Thread(()->{
    // 步骤 C (读 volatile 变量，带读屏障)
    // 根据传递性：如果 t2 读取到了 x=20，那么它必定也能看到 y=10 
    System.out.println(x); 
},"t2").start();
```
