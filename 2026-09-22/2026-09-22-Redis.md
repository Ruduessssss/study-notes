## 一、为什么需要「全局唯一 ID」

订单表的主键，看起来随手列都行，实际上是个很讲究的东西。它至少要满足：

| 要求 | 说明 |
| --- | --- |
| **唯一性** | 这是底线，重复了就出事故 |
| **递增趋势** | 用 `AUTO_INCREMENT` 的好处是 B+ 树索引插入快；完全随机的 ID 会导致页分裂 |
| **信息安全** | **不能让别人从 ID 推出业务量** |
| **高可用** | 生成 ID 的服务不能是单点 |
| **高性能** | 秒杀场景下 QPS 极高 |

### 1.1 为什么不能用数据库自增主键

`AUTO_INCREMENT` 看着最省事，但：

1. **会暴露信息**。今天下单拿到 `1001`，明天拿到 `1002` —— 竞对不用爬数据，光看 ID 就知道你昨天的成交量。**这本身就是商业情报泄漏**。
2. **分库分表后就没法用了**。一个库一个自增序列，两张表都会出现 `1001`。
3. **性能压在数据库上**。每次下单都要先跟 MySQL 要一个 ID。

### 1.2 四种方案对比

| 方案 | 唯一性 | 有序性 | 信息泄漏 | 性能 | 评价 |
| --- | --- | --- | --- | --- | --- |
| 数据库自增 | ✓（单库） | ✓ | ✗ **暴露** | 差 | 分表就废 |
| `UUID` | ✓ | ✗ **完全无序** | ✓ | 好 | 无序 → 索引页分裂；还太长（36 位） |
| 雪花算法 | ✓ | ✓ | ✓ | 好 | 依赖机器时钟，时钟回拨会重复 |
| **Redis 自增** | ✓ | ✓ | ✓ | 极好 | **本项目采用** |

> **一句话**：我们想要的不是一个「自增数」，而是一个**看起来无规律、但内部仍然递增**的数。

## 二、Redis 自增：`INCR` / `INCRBY`

### 2.1 基本命令

```text
SET num 1              # 设置初始值
INCR num               # 自增 1  → 2
INCRBY num 5           # 自增 5  → 7
INCRBYFLOAT num 1.5    # 自增 1.5（浮点）
```

- `INCR` 是**整数**自增，等价于 `INCRBY key 1`
- `INCRBYFLOAT` 是浮点自增，Redis 内部用 `long double` 存，没有精度问题
- 这几个命令**都是原子操作**

### 2.2 为什么 `INCR` 天然适合生成 ID

**Redis 处理命令是单线程的。** 所以 `INCR` 这个「读出来、加一、写回去」的动作，中间不会被别的请求插进来。

这正是并发编程里说的「原子性」，但 Redis 是**用单线程换来的** —— 不需要加锁、不需要 CAS 重试，一行命令解决。

> 对比一下：如果用「GET 出当前值 → 在 Java 里加一 → SET 回去」，三个线程并发就会拿到同一个 ID。
> 这就是典型的**竞态条件**。

### 2.3 多个业务怎么区分

不同业务（订单、优惠券、用户）不能共用一个自增序列，否则互相污染。所以 key 上带业务前缀：

```text
icr:order:2026:09:22:     →  订单的今日序号
icr:voucher:2026:09:22:   →  优惠券的今日序号
```

> **注意 key 最后那个冒号**。它不是手滑写多了，是为了让 `prefix + date` 拼出来的结构一致 ——
> 代码里是 `"icr:" + keyPrefix + ":" + date + ":"`，前缀和日期各自带冒号，拼出来整齐。

### 2.4 为什么按「天」分 key

如果所有订单共用一个 `icr:order`，这个 key 会一直涨到几百亿，而且：

- 单 key 的计数会越来越大（无所谓，但不好看）
- **没法用日期做统计**（今天的单量是多少？得做差）

按天分，每天一个 key，而且可以给这些 key 设置过期时间（比如只保留 3 天），**避免 Redis 里堆一堆再也不会用的历史计数**。

## 三、位运算：把「时间戳」和「序号」拼成一个数

光有自增序号不够 —— 它每天从 1 重新开始，`1`、`2`、`3` 在不同天是重复的。所以要**把日期信息也编进去**。

本项目的做法：**高位存时间戳，低位存自增序号**。

```java
return timeStamp << COUNT_BITS | count;
```

### 3.1 拆解这条语句

假设 `COUNT_BITS = 32`：

```text
timeStamp = 1000        // 二进制 ...0001111101000
count     = 5           // 二进制 ...0000000000101

timeStamp << 32          // 把时间戳整体左移 32 位，低 32 位空出来全是 0
                         // ...0001111101000_00000000000000000000000000000000

再 | count               // 按位或，把序号填进低 32 位
                         // ...0001111101000_00000000000000000000000000000101
```

- **`<<` 左移**：整体往高位挪，低位补 0。相当于「乘 2 的 n 次方」，并且**腾出低位**。
- **`|` 按位或**：因为左移后低位全是 0，所以「或」就等于**直接填入**。

### 3.2 为什么必须是 32 位

`Long` 是 64 位。切一半：

| 位段 | 存什么 | 容量 |
| --- | --- | --- |
| **高 32 位** | 时间戳（相对某个基准点的秒数） | 2^32 秒 ≈ **136 年** |
| **低 32 位** | 当天的自增序号 | 2^32 ≈ **42.9 亿** |

> 42.9 亿 / 天，秒杀也够用了。
>
> 但要注意：**这个方案假设「一天之内不会超过 42.9 亿单」**。
> 一旦超了，低位就会进位污染到高位的时间戳 —— 这在实际业务里不可能发生，但面试时值得说清楚。

### 3.3 为什么时间戳不能直接用当前秒数

```java
private static final Long BEGIN_TIMESTAMP = 1767225600L;
Long timeStamp = epochSecond - BEGIN_TIMESTAMP;
```

`1767225600` 换算过来是 **2026-01-01 00:00:00 UTC**。

直接存 Unix 秒数的话，高 32 位很快就不够用了（`2^32` 秒 ≈ 136 年，但 `System.currentTimeMillis()/1000` 已经是 17 亿，只剩 25 亿秒 ≈ 8 年）。所以**换一个基准点**，从 2026 年元旦开始算，又能撑很多年。

> 这是个很实用的技巧：**时间戳字段永远存「相对某个约定起点的差值」**，而不是绝对纪元值。

## 四、本项目用到的命令 / API

| Java（StringRedisTemplate） | Redis 命令 | 用在哪 |
| --- | --- | --- |
| `opsForValue().increment(key)` | `INCR key` | 生成全局唯一 ID 的序号部分 |
| `opsForValue().increment(key, n)` | `INCRBY key n` | （等价写法） |
| `opsForValue().setIfAbsent(k, v, ttl, unit)` | `SET k v NX EX <ttl>` | **互斥锁**（见下一篇） |

> `INCR` 有个细节：**如果 key 不存在，会先把它当成 0 再自增**，所以第一次调用 `increment` 返回 `1`，
> 不需要先 `SET` 一个初始值。这也是为什么代码里只有一行 `increment` 就完事了。

## 五、概念层面要注意的坑

1. **`INCR` 的原子性来自 Redis 单线程**，不是某种锁机制。所以它**不能被用在需要「多步原子」的场景**（比如「先判断库存再扣减」），那种要用 Lua。
2. **ID 里嵌了时间戳，就意味着 ID 本身能反解出生成时间**。这是设计目标（可读、可统计），但如果业务要求「生成时间也不能泄漏」，就得换方案。
3. **位运算要用 `<<` 和 `|`，不能用 `+`**。用 `+` 在低位不进位时结果一样，但一旦进位就会污染高位 —— 这是个隐蔽的 bug。
4. **`INCR` 的 key 建议设过期时间**，否则历史计数会一直堆在 Redis 里。
5. **雪花算法依赖机器时钟**，时钟回拨会导致生成重复 ID。Redis 方案没有这个问题（时间戳只影响高位，且 Redis 是外部统一时钟），但代价是多一次网络往返。
