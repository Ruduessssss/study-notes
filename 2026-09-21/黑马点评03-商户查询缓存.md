# 商户查询缓存

> **说明**：本文**只讲后端**，不涉及前端实现。
>
> 对照代码：`ShopController`、`ShopServiceImpl`、`CacheClient`、`RedisData`、`RedisConstants`、`HmDianPingApplicationTests`。

## 一、功能定位

给商铺详情查询加一层 Redis 缓存，把 MySQL 的压力卸下来。

顺带解决加缓存之后引出的三个问题：

| 问题 | 本项目的解法 | 状态 |
| --- | --- | --- |
| 缓存与数据库不一致 | **改库后删缓存**（Cache Aside） | ✅ 已启用 |
| **缓存穿透**（查不存在的数据） | **缓存空对象** | ✅ 已启用 |
| **缓存击穿**（热点 key 失效） | 互斥锁 / 逻辑过期 | ⚠️ 写了但**注释掉**（见第四节） |

## 二、接口契约

### 接口 1：根据 id 查商铺（读，走缓存）

```text
GET /shop/{id}
参数位置：路径变量 id                            → @PathVariable("id") Long id
返回：200 {"success":true,"data":{...Shop...}}
```

> ⚠️ **这里少了一个分支**：course 原版在 `shop` 为空时会返回
> `200 {"success":false,"errorMsg":"店铺不存在！"}`，本项目直接 `Result.ok(shop)` ——
> 查不到的商铺会返回 `{"success":true}`（`data` 是 null，被 Jackson 的 `non_null` 策略省掉了）。
> 见「易错点 1」。

### 接口 2：修改商铺（写，触发缓存失效）

```text
PUT /shop
Content-Type: application/json
参数位置：JSON body {...Shop...}                → @RequestBody Shop shop
返回：200 {"success":true}
     200 {"success":false,"errorMsg":"店铺id不能为空!"}
副作用：删除 Redis 里 cache:shop:{id}
```

## 三、后端分层调用链

```text
HTTP 请求
   ↓
ShopController
   ├─ GET  /shop/{id}  → shopService.queryById(id)
   └─ PUT  /shop       → shopService.updateShop(shop)
   ↓
IShopService (接口)
   ↓
ShopServiceImpl
   ├─ queryById()      → CacheClient（通用缓存读写）
   ├─ updateShop()     → ShopMapper + StringRedisTemplate.delete
   └─ saveShop2Redis() → 缓存预热
   ↓
CacheClient（工具类）
   ├─ StringRedisTemplate → Redis
   └─ dataFallBack 函数   → 回调回 Service 查数据库
   ↓
ShopMapper → MySQL: tb_shop
```

**分层上值得注意的一点**：`CacheClient` 是**通用工具类**，它不认识 `Shop`。
「缓存里没有时该去哪查」这件事，是通过**函数参数**传进去的：

```java
cacheClient.get(CACHE_SHOP_KEY, id, Shop.class, id2 -> getById(id2), CACHE_SHOP_TTL, TimeUnit.MINUTES);
//                                             ↑ 这个 lambda 就是「查数据库」这一步
```

所以工具类只负责「缓存逻辑」，业务查询留在 Service 里 —— 边界很干净。

## 四、`queryById` 的实现演进

`ShopServiceImpl` 里现在**同时躺着三套手写实现，全部被注释掉**；真正在用的是 `CacheClient` 里的封装版。靠注释切换 —— 这是学习过程的轨迹，也是这次最该记清楚的地方：

```java
@Override
public Result queryById(Long id) {

    //缓存空对象来解决缓存穿透
    //Shop shop = queryWithPassThrough(id);

    Shop shop = cacheClient.get(CACHE_SHOP_KEY, id, Shop.class, id2 -> getById(id2), CACHE_SHOP_TTL, TimeUnit.MINUTES);
    //互斥锁来解决缓存击穿
    //Shop shop = queryWithMutex(id);

    //缓存过期来解决缓存击穿
    //Shop shop = queryWithLogicExpire(id);
    return Result.ok(shop);
}
```

| 版本 | 解决的问题 | 写在哪 | 状态 |
| --- | --- | --- | --- |
| `queryWithPassThrough` | 穿透 | `ShopServiceImpl`（手写版） | 注释 |
| `queryWithMutex` | 击穿 | `ShopServiceImpl`（手写版） | 注释 |
| `queryWithLogicExpire` | 击穿 | `ShopServiceImpl`（手写版） | 注释 |
| `cacheClient.get` | 穿透 | **`CacheClient`（通用版）** | ✅ **启用** |
| `cacheClient.getWithLogicExpire` | 击穿 | `CacheClient`（通用版） | 未启用 |

> **演进路线**：先在 `ShopServiceImpl` 里手写一遍（`queryWithPassThrough` → `queryWithMutex` → `queryWithLogicExpire`），
> 走通之后再把「缓存穿透 + 击穿」的通用套路抽到 `CacheClient`。
>
> **当前线上跑的只有最后封装的 `cacheClient.get`** —— 也就是「缓存空对象」这一个解法。
> 击穿的两个方案（互斥锁、逻辑过期）代码都还在，但**没接上**。

## 五、`CacheClient` 工具类

```java
@Slf4j
@Component
public class CacheClient {

    private ExecutorService pool = Executors.newFixedThreadPool(10);

    @Resource
    private StringRedisTemplate stringRedisTemplate;

    // 1. 任意对象写入 Redis（带物理 TTL）
    public <ID> void set(String keyPrefix, ID id, Object value, Long time, TimeUnit unit)

    // 2. 任意对象写入 Redis（带逻辑过期，不设物理 TTL）
    public <ID> void setWithLogicExpire(String keyPrefix, ID id, Object value, Long time, TimeUnit unit)

    // 3. 读缓存 —— 缓存空对象解决穿透
    public <R, ID> R get(String keyPrefix, ID id, Class<R> type, Function<ID, R> dataFallBack, Long time, TimeUnit unit)

    // 4. 读缓存 —— 逻辑过期解决击穿
    public <R, ID> R getWithLogicExpire(String keyPrefix, ID id, Class<R> type, Function<ID, R> dataFallBack, Long time, TimeUnit unit)

    public Boolean tryLock(String key)
    public void releaseLock(String key)
}
```

> 注意 `tryLock` / `releaseLock` 在 `CacheClient` 里是 **`public`** 的
> （`ShopServiceImpl` 里那份注释掉的老版本才是 `private`，而且用的是 `LOCK_SHOP_TTL`）。

### 5.1 泛型签名是怎么做到通用的

```java
public <R, ID> R get(String keyPrefix, ID id, Class<R> type, Function<ID, R> dataFallBack, Long time, TimeUnit unit)
```

四个类型相关的参数各司其职：

| 参数 | 作用 | 换成商铺时 |
| --- | --- | --- |
| `ID id` | 主键，类型不定（Long / String / …） | `1L` |
| `Class<R> type` | **反序列化回哪个类** | `Shop.class` |
| `Function<ID, R> dataFallBack` | **缓存没命中时，去哪查** | `id2 -> getById(id2)` |
| `String keyPrefix` | key 前缀 | `"cache:shop:"` |

> 关键设计是 **`dataFallBack` 传函数而不是传 Mapper**。
> 工具类因此完全不需要知道 `ShopMapper` 的存在，「查数据库」这个动作由调用方提供。
> 这就是它能同时服务 `Shop`、`Voucher`、`Blog` 的原因。

### 5.2 `get()` 的完整逻辑（缓存空对象 / 穿透）

```java
public <R,ID> R get(String keyPrefix, ID id, Class<R> type, Function<ID,R> dataFallBack, Long time, TimeUnit unit)
{
    String key = keyPrefix+id;
    String json = stringRedisTemplate.opsForValue().get(key);

    if(StrUtil.isNotBlank(json))
    {
        // 找到且不是空对象了,直接返回
        return JSONUtil.toBean(json,type);
    }
    if(json!=null)
    {
        // 空对象,返回空值
        return null;
    }

    // redis 不存在,查数据库
    R r = dataFallBack.apply(id);

    if(r==null)
    {
        // 为空,存空对象
        stringRedisTemplate.opsForValue().set(key,"",CACHE_NULL_TTL, TimeUnit.MINUTES);
        return null;
    }

    // 不为空,存入redis
    this.set(keyPrefix,id,r,time,unit);
    return r;
}
```

**这段的三次判断是这个方案的全部精华**，顺序不能乱：

| 判断 | `json` 的值 | 含义 | 动作 |
| --- | --- | --- | --- |
| `isNotBlank(json)` | `"{...}"` | 真·缓存命中 | 反序列化返回 |
| `json != null`（且为空串） | `""` | **命中「空对象」** | 直接返回 null，**不打数据库** |
| `json == null` | `null` | 缓存里没有 | 查数据库 |

> **第 2 条就是「缓存穿透」的解法**：数据库里查不到时，往 Redis 写一个**空串**占位。
> 下次再有人查这个不存在的 id，会在第 2 条就被拦下，**不会再落到数据库**。
>
> 为什么用空串而不是存 `null`？因为 Redis 存不了 `null`，而 `""` 反序列化不出对象 ——
> `isNotBlank` 判断就能把「有值」和「占位空值」区分开。

**空对象的 TTL 是 `CACHE_NULL_TTL = 2`（分钟）**，短得多：

- 太长 → 数据库里后来**新增**了这条数据，但缓存里还占着「不存在」的坑，读不到
- 太短 → 挡不住持续的攻击流量

## 六、逐条落地

### 1. 互斥锁解决缓存击穿（已注释，但逻辑要懂）

注释在 `ShopServiceImpl` 里的 `queryWithMutex`，核心是**抢锁 + 双重检查**：

```java
while (true) {
    if (tryLock(lockKey)) {                  // 4.1 抢锁
        try {
            // 再查一次缓存 —— double check
            // （可能前一个拿到锁的线程已经把缓存建好了）
            shopJson = stringRedisTemplate.opsForValue().get(key);
            if (shopJson != null) { ... return shop; }

            Shop shop = getById(id);          // 真的只有我一个人查库
            ...
            return shop;
        } finally {
            releaseLock(lockKey);             // 必须在 finally 里放锁
        }
    }
    Thread.sleep(1000);                       // 没抢到 → 睡一会再试
}
```

要点：

- **抢到锁之后必须再查一次缓存**（double check）。因为在你拿到锁的瞬间，前一个持锁线程可能刚把缓存重建完 —— 不重查就白查一次库了
- **`releaseLock` 必须放 `finally`**，否则中间抛异常锁就永远不释放（虽然 `setIfAbsent` 带了 10 秒 TTL 兜底）
- **`tryLock` 就是 `SET NX EX`**：

```java
public Boolean tryLock(String key) {
    Boolean flag = stringRedisTemplate.opsForValue().setIfAbsent(key, "1", LOCK_TTL, TimeUnit.SECONDS);
    return BooleanUtil.isTrue(flag);     // ← 注意这里
}
```

> `BooleanUtil.isTrue(flag)` 而不是直接 `return flag` —— 因为 `setIfAbsent` 返回的是**包装类型 `Boolean`，可能为 null**
> （在 pipeline / 事务里必然为 null）。直接拆箱会 NPE，`isTrue` 把 `null` 当成 `false`。

- **注意注释版里有个单位不一致**：`queryWithMutex` 写空对象用的是
  `stringRedisTemplate.expire(key, CACHE_NULL_TTL, TimeUnit.SECONDS)` —— 是 **2 秒**；
  而 `queryWithPassThrough` 和 `CacheClient.get` 用的都是 `TimeUnit.MINUTES`（**2 分钟**）。
  当前生效的是 `CacheClient.get`，所以线上是 2 分钟，但读注释代码时要知道这两处不一样。

### 2. 逻辑过期解决缓存击穿（未启用）

两处实现要分清：

- `ShopServiceImpl.queryWithLogicExpire` —— **是注释掉的**（学习时的手写版）
- `CacheClient.getWithLogicExpire` —— **是活代码，只是没人调用它**（封装后的通用版，等着被 `queryById` 接上）

下面讲的是 `CacheClient` 里的那一版。

```java
String json = stringRedisTemplate.opsForValue().get(key);
if(json==null) {
    return null;                              // 没有就直接返回，不查库
}

RedisData redisData = JSONUtil.toBean(json, RedisData.class);
LocalDateTime expireTime = redisData.getExpireTime();
Object data = redisData.getData();

if(expireTime.isAfter(LocalDateTime.now())) {
    return JSONUtil.toBean((JSONObject) data, type);    // 没过期，直接返回
}

// 过期了：抢锁 → 开异步线程重建 → 当前线程照样返回旧数据
if(tryLock(LOCK_KEY+keyPrefix+id)) {
    pool.submit(() -> {
        try {
            R r = dataFallBack.apply(id);
            this.setWithLogicExpire(keyPrefix,id,r,time,unit);
        } finally {
            releaseLock(LOCK_KEY+keyPrefix+id);
        }
    });
}

return JSONUtil.toBean((JSONObject) data, type);   // ← 立即返回旧数据，不阻塞
```

要点：

- **命中之后才判断逻辑过期**；没命中直接返回 null，**绝不查库**（所以这个方案**不解决穿透**，只解决击穿）
- **重建是异步的**：`pool.submit(...)` 提交完立刻往下走，当前请求拿的是**旧数据**
- **必须强转 `(JSONObject)`**：`RedisData.data` 声明成 `Object`，Hutool 反序列化后实际是 `JSONObject`
- **`setWithLogicExpire` 不设物理 TTL**（`opsForValue().set(key, json)` 没有 ttl 参数），过期时间靠 value 里的 `expireTime` 字段判断

### 3. 缓存预热

逻辑过期方案要求缓存里**提前就有数据**（否则第一波请求全返回 null）。所以有个预热方法：

```java
public void saveShop2Redis(Long id, Long time, TimeUnit unit) {
    Shop shop = getById(id);
    RedisData redisData = new RedisData();
    redisData.setData(shop);
    redisData.setExpireTime(LocalDateTime.now().plusSeconds(unit.toSeconds(time)));
    stringRedisTemplate.opsForValue().set(CACHE_HOT_SHOP_KEY+id, JSONUtil.toJsonStr(redisData));
}
```

配合单元测试手动触发：

```java
@Test
public void testSaveHotShop() {
    shopService.saveShop2Redis(1L, 1L, TimeUnit.SECONDS);
}
```

> 项目里**没有定时任务**去自动预热，只有这个手动测试方法。
> 真实场景会用定时任务在低峰期刷一遍热点数据。

### 4. 双写一致：`updateShop`

```java
@Override
@Transactional
public Result updateShop(Shop shop) {

    if(getById(shop.getId())==null) {
        return Result.fail("店铺id不能为空!");
    }

    updateById(shop);                                    // 1. 先改数据库

    stringRedisTemplate.delete(CACHE_SHOP_KEY+shop.getId());   // 2. 再删缓存

    return Result.ok();
}
```

要点：

- **顺序是「先改库、再删缓存」**，这是 09-21 知识点篇第三节推演出来的结论
- 用的是**删除**而不是更新 —— 下次查询未命中时再懒加载最新值
- `@Transactional` 让「改库」这一步是原子的

> 但这里有个**并发隐患**：`delete` 是在**事务提交之前**执行的。详见「易错点 2」。

## 七、易错点

### 缓存逻辑相关

1. **`queryById` 少了「查不到」的分支**。course 原版是：

   ```java
   if (shop == null) {
       return Result.fail("店铺不存在！");
   }
   return Result.ok(shop);
   ```

   本项目直接 `return Result.ok(shop)`。而 `Result.ok(null)` 会返回 `{"success":true}`（`data` 被 `non_null` 策略省掉），
   **前端无法区分「商铺不存在」和「接口正常但没数据」**。缓存穿透的「空对象」在接口层被彻底掩盖了。

2. **`delete` 在事务提交前执行，并发下会不一致**。
   `updateShop` 上标了 `@Transactional`，但 `stringRedisTemplate.delete(...)` 走的是 Redis、**不参与数据库事务**，它会在**事务提交之前**就执行完。
   并发场景：
   ```text
   线程1：改库(未提交) → 删缓存 ──────────────→ 事务提交(库=新值)
   线程2：              查缓存(未命中) → 查库(读到旧值!) → 写回缓存
   ```
   线程2 把**未提交的旧值**写回了缓存，而事务提交后缓存没人再删 → 缓存里是旧值。
   **改法见第八节**。

3. **只删了 `CACHE_SHOP_KEY`，没删 `CACHE_HOT_SHOP_KEY`**。逻辑过期那份缓存用的是另一个前缀，改库后不会被失效。当前因为逻辑过期路径没启用，问题没暴露 —— **一旦启用就会踩**。

4. **`getWithLogicExpire` 里 `r` 可能为 null**。
   ```java
   R r = dataFallBack.apply(id);
   this.setWithLogicExpire(keyPrefix, id, r, time, unit);   // r 可能是 null
   ```
   如果商铺在数据库里已经被删了，`data` 就会是 `null` —— 于是一条**没有物理 TTL、永远清不掉**的缓存被写了进去。
   下次读到它，`redisData.getData()` 返回 `null`，整条缓存既给不出数据、又永远不会自己消失，只能手动删。

5. **`releaseLock` 不校验锁的归属**。
   ```java
   public void releaseLock(String key) {
       stringRedisTemplate.delete(key);
   }
   ```
   经典问题：线程 A 的锁因超时（10 秒）被 Redis 自动删掉 → 线程 B 抢到了锁 → 此时线程 A 执行完 `finally` 里的 `releaseLock`，**把 B 的锁删了**。
   锁 TTL 设得太短、或者业务执行时间超过 TTL 时就会触发。course 第 4 章有解法（value 存标识 + Lua 判断再删）。

### 工具类 / 线程池

6. **`Executors.newFixedThreadPool(10)` 有三个问题**：用的是**无界队列**（任务堆积会 OOM）、**没有 `@PreDestroy` 关闭**（应用停机时线程池不会优雅退出）、字段不是 `static final`。

7. **`CacheClient` 的注入方式**用的是 `@Resource` 字段注入，course 用的是构造器注入。两种都能跑，但构造器注入能保证 `final` 且依赖不为空 —— 见 `RefreshInterceptor` 那篇的讨论，那里是**不得不**用构造器（手动 `new` 的类）。

### 通用

8. **`updateShop` 的校验提示词不匹配**。`getById(shop.getId()) == null` 检查的是「商铺是否存在」，报错却是「店铺id不能为空!」。而且 `shop.getId()` 真的为 null 时，`getById(null)` 的行为也要单独考虑。

9. **`set` + `expire` 两步写非原子**。注意 `ShopServiceImpl` 里**注释掉的** `queryWithPassThrough` 是两步：

   ```java
   stringRedisTemplate.opsForValue().set(key,JSONUtil.toJsonStr(shop));
   stringRedisTemplate.expire(key,CACHE_SHOP_TTL,TimeUnit.MINUTES);
   ```

   而抽到 `CacheClient` 之后变成了一步 —— **这是封装带来的一个实际改进**：

   ```java
   stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(value), time, unit);   // SET k v EX ttl
   ```

## 八、可以更好的地方

> 和 09-19 那篇同样的写法：**现状 → 问题 → 怎么改**。

### 8.1 `updateShop` 的删缓存挪到事务提交之后

**现状**：`delete` 在 `@Transactional` 方法体内，事务提交前执行。

**改法**：用事务同步回调，把删缓存**挂到「提交成功」这个时刻**：

```java
@Override
@Transactional
public Result updateShop(Shop shop) {
    if (getById(shop.getId()) == null) {
        return Result.fail("店铺不存在!");
    }

    updateById(shop);
    Long id = shop.getId();

    // 事务提交成功后再删缓存
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            stringRedisTemplate.delete(CACHE_SHOP_KEY + id);
        }
    });

    return Result.ok();
}
```

> 另一种更解耦的写法是发事件 + `@TransactionalEventListener(phase = AFTER_COMMIT)`。

### 8.2 把「查不到」的分支补回来

**现状**：`Result.ok(null)` 让前端无法区分「不存在」和「空」。

**改法**：按 course 原版加回：

```java
if (shop == null) {
    return Result.fail("店铺不存在！");
}
return Result.ok(shop);
```

### 8.3 锁的释放要校验归属

**现状**：`releaseLock` 无脑 `DEL`，可能删掉别人的锁。

**改法**：抢锁时把 value 设成自己的唯一标识，释放时「判断是不是自己的，再删」，且**两步必须原子**：

```java
// 抢锁：value 存自己的标识
stringRedisTemplate.opsForValue().setIfAbsent(key, token, LOCK_TTL, TimeUnit.SECONDS);

// 释放：用 Lua 保证「判断 + 删除」原子
// if redis.call('GET', KEYS[1]) == ARGV[1] then
//     return redis.call('DEL', KEYS[1])
// else
```

### 8.4 线程池换成 Spring 管理的

**现状**：`Executors.newFixedThreadPool(10)`，无界队列、不关闭。

**改法**：用 `ThreadPoolTaskExecutor`（交给 Spring 管生命周期），或者至少：

```java
private static final ExecutorService POOL = new ThreadPoolExecutor(
        10, 20,
        60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(100),                    // 有界队列
        new ThreadPoolExecutor.CallerRunsPolicy());       // 满了让调用线程自己跑

@PreDestroy
public void shutdown() {
    POOL.shutdown();
}
```

### 8.5 逻辑过期路径要补 null 防护

**现状**：`getWithLogicExpire` 重建时 `r` 为 null 会写入 `data: null` 且无 TTL。

**改法**：重建前判断，`r == null` 就**删掉缓存**而不是写 null：

```java
R r = dataFallBack.apply(id);
if (r == null) {
    stringRedisTemplate.delete(keyPrefix + id);      // 数据没了，缓存也清掉
} else {
    this.setWithLogicExpire(keyPrefix, id, r, time, unit);
}
```

### 8.6 优先级

| 改动 | 成本 | 收益 | 建议 |
| --- | --- | --- | --- |
| 补回「店铺不存在」分支 | 三行 | 高（接口语义正确） | **建议做** |
| `delete` 挪到 `afterCommit` | 十行 | 中（并发下才暴露） | 建议做 |
| 锁释放校验归属 | 引入 Lua | 中（启用了互斥锁才需要） | 启用前必做 |
| 线程池换 Spring 管理 | 十行 | 中（避免 OOM / 停机泄漏） | 建议做 |
| 逻辑过期 null 防护 | 五行 | 中（启用逻辑过期才需要） | 启用前必做 |
| 失效时同时删热点缓存 | 一行 | 低（当前路径未启用） | 看情况 |
