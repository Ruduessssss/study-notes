## 一、从「一条命令原子」到「一个动作原子」

先回顾底座：

- Redis **单线程**，所以**单条命令**天然原子
- 多条命令要原子 → **Lua**（Redis 把整段脚本当一条命令跑）

分布式锁要的「抢锁」动作恰好可以**用一条命令表达**——这是 Redis 做锁的先天优势。这条命令就是 `SET NX EX`。

## 二、`SET NX EX`：抢锁必须是一条命令

### 2.1 `SETNX` 的语义

```text
SETNX key value      # SET if Not eXists
                     # key 不存在 → 写入并返回 1
                     # key 已存在 → 什么都不做，返回 0
```

「只有不存在才能写」= **互斥**：谁写进去谁持锁，别人写不进。

### 2.2 但 `SETNX` 单独用会死锁

如果 `SETNX` 成功、持锁线程却崩了，那把锁**永远删不掉**，其他人全部卡死。所以必须给锁一个**过期时间兜底**。

于是有了两种写法，**优劣关键在原子性**：

```text
❌ 两步（不是原子的）
   SETNX lock 1        → 成功
   EXPIRE lock 10      ← 如果这一步之前进程挂了，锁没 TTL = 死锁

✅ 一步（原子）
   SET lock 1 NX EX 10
```

> **`EXPIRE` 和 `SETNX` 是两条命令**，中间有空隙。所以要用 `SET` 的扩展参数
> `NX`（不存在才设）+ `EX`（同时设秒级 TTL），**一条命令完成抢锁 + 兜底**。

Java 侧（`SimpleRedisLock.java:44`）对应的就是：

```java
Boolean success = stringRedisTemplate.opsForValue()
        .setIfAbsent(key, id, timeout, TimeUnit.SECONDS);   // = SET key id NX EX timeout
```

### 2.3 value 里放什么：标识，不是 `"1"`

```text
SET lock:order:1  "1"                     ← 最朴素，但释放时无法认领
SET lock:order:1  UUID-threadId           ← 推荐，释放时能判断「是不是我的锁」
```

value 存**唯一标识**是为了解决「**误删别人的锁**」——释放时先比 value，是自己的才删。
这个「比 + 删」又是多命令，回到 Lua（`unlock.lua`）。见 `2026-09-24-Redis.md`。

| 参数 | 作用 | 对应文档 |
| --- | --- | --- |
| `NX` | 互斥（不存在才写） | 本节 |
| `EX` | 防死锁（自动过期） | 本节 |
| **value = 标识** | 防误删（认领） | 09-24 篇 |
| **Lua 释放** | 认领 + 删除的原子性 | 09-24 篇 |

## 三、乐观锁 vs 悲观锁：在 DB 和 Redis 上的不同落地

### 3.1 两种思路

| | 悲观锁 | 乐观锁 |
| --- | --- | --- |
| 假设 | 冲突**一定会发生** | 冲突**很少发生** |
| 做法 | 先加锁，别人排队 | 先干活，提交时校验 |
| 代表 | `synchronized`、`SELECT ... FOR UPDATE`、分布式锁 | CAS、版本号 |
| 代价 | 并发度低、要等 | 失败要重试 |

### 3.2 项目里两类东西各用哪种

**扣库存（`UPDATE`）= 更新已有数据 → 用乐观锁：**

```sql
UPDATE tb_seckill_voucher
   SET stock = stock - 1
 WHERE voucher_id = ? AND stock > 0     -- ← 这就是乐观锁：把「校验」写进 WHERE
```

它不是「先查再比对」那种 CAS，而是把约束**下推给数据库**，让数据库在**行锁**里一次性完成「检查 + 更新」。
这是本项目防超卖的关键（`VoucherOrderServiceImpl.java:309-311`）。

**「一人一单」= 插入新数据（`INSERT`）→ 没法用乐观锁，用悲观锁：**

> 课程原话（`Redis实战篇.md:1485`）：*「乐观锁比较适合更新数据，而现在是插入数据，所以我们需要使用悲观锁操作」*。
>
> 为什么插入不能用乐观锁？乐观锁要校验「有没有被人改过」，而**一条还不存在的记录没有可校验的状态**。
> 只能靠「先锁住，再查，再插」把它串起来。

### 3.3 一个反直觉的点：`stock > 0` 比 `stock = 100` 成功率高得多

课程 3.6 先给出的方案是「前后库存相等才扣」：

```sql
... WHERE voucher_id = ? AND stock = 100     -- 方案一
```

100 个线程同时拿到「库存 = 100」，**只有 1 个能扣，其余 99 个全失败**——它们库存其实还够，却被乐观锁挡了。

改成只要求「还有货」：

```sql
... WHERE voucher_id = ? AND stock > 0       -- 方案二（采用）
```

> **本质**：乐观锁的「校验条件」要贴着**业务约束**写，而不是贴着「值没变过」写。
> 我们真正要保证的是「不超卖」（`stock >= 0`），不是「没人动过 stock」。

## 四、用 Redis 的 Set 结构做「一人一单」

除了数据库查重，Redis 侧还有一个更快的办法：**用 `SET` 存「下过单的用户」，用 `SISMEMBER` 判断是否下过**。

`seckillOrder.lua` 就是这么写的（`seckillOrder.lua:11-27`）：

```lua
local stockKey = "seckill:stock:"..voucherId
local orderKey = "seckill:order:"..voucherId

if (tonumber(redis.call("get", stockKey))<=0) then
    ---库存小于0
    return 1
end

if(redis.call("sismember",orderKey,userId)==1) then
    ---用户已经下过单
    return 2
end

redis.call("incrby",stockKey,-1)          -- 库存 -1
redis.call("sadd",orderKey,userId)        -- 记下「这个用户下过单」
redis.call("xadd","stream.orders","*","voucherId",voucherId,"userId",userId,"id",orderId)
return 0
```

对照 Redis 命令：

| 命令 | 含义 | 返回值 |
| --- | --- | --- |
| `GET stockKey` | 读库存 | 字符串（要 `tonumber`） |
| `INCRBY stockKey -1` | 库存减 1（**原子**） | 减完后的值 |
| `SISMEMBER orderKey userId` | 该用户在集合里吗 | `1` 有 / `0` 无 |
| `SADD orderKey userId` | 用户加入集合 | 新增 `1` / 已存在 `0` |

> - 用 **Set** 而不是 String：天然去重，`SADD` 同一个用户第二次返回 `0`，连判重都省了
> - 用 `INCRBY ... -1` 而不是 `DECR`：一样，`DECR` 就是 `INCRBY key -1` 的语法糖
> - **整段仍然靠 Lua 保原子**：`GET → SISMEMBER → INCRBY → SADD` 四步，任何一步被别人插进来都会出错

## 五、Redisson 可重入锁：Hash + `HINCRBY`

手写锁「不可重入」——同一线程第二次 `tryLock` 会失败。Redisson 用 **Hash** 解决。

不是 `SET key value`，而是：

```text
HSET lock:order:1  <id>:<threadId>  1        # 小 key = 「谁」，值 = 重入次数
```

加锁的 Lua（课程 `Redis实战篇.md:2094-2105`）：

```lua
-- KEYS[1]=锁名  ARGV[1]=leaseTime  ARGV[2]=id:threadId
if (redis.call('exists', KEYS[1]) == 0) then          -- 锁没人持有
    redis.call('hset', KEYS[1], ARGV[2], 1);
    redis.call('pexpire', KEYS[1], ARGV[1]);
    return nil;                                        -- nil = 抢到了
end;
if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then -- 锁是我的（重入）
    redis.call('hincrby', KEYS[1], ARGV[2], 1);        -- 次数 +1
    redis.call('pexpire', KEYS[1], ARGV[1]);           -- 刷新过期
    return nil;                                        -- nil = 抢到了
end;
return redis.call('pttl', KEYS[1]);                    -- 别人持有 → 返回剩余 TTL
```

**两个 `return nil` = 成功**（首次获得 / 重入），**返回数字 = 失败**（数字是剩余 TTL，供重试时决定等多久）。

| 分支 | 条件 | 动作 |
| --- | --- | --- |
| 锁不存在 | `exists == 0` | `HSET` 建锁，次数 = 1 |
| 锁是我的 | `hexists == 1` | `HINCRBY` 次数 +1（**重入**） |
| 锁是别人的 | 否则 | 返回 `PTTL`，让调用方自旋等待 |

释放时对称地 `HINCRBY ... -1`，**减到 0 才真正 `DEL`** —— 这就和 `synchronized` / `ReentrantLock` 的 state 计数一致了。

> **Java 类比**：`ReentrantLock` 用 `volatile int state` 记重入次数；
> Redisson 把 state 挪到 Redis 的 Hash value 里，就「分布式可重入」了。

## 六、看门狗（WatchDog）：把「续期」自动化

第 2.2 节的 `EX` 是**双刃剑**：

- 有 TTL → 防死锁 ✓
- 但业务跑得比 TTL 慢 → **锁提前过期** → 两个线程同时持锁 ✗

手写锁只能靠「人肉估 TT L」，估不准。Redisson 的办法是**自动续期**：

```text
加锁成功 → 起一个定时任务（看门狗）
   每 (leaseTime / 3) 毫秒执行一次「把 TTL 重置回 leaseTime」
   续期成功 → 递归再排一个定时任务
进程挂了 → 定时任务没了 → 锁到期自动释放（正合我意）
```

课程源码（`Redis实战篇.md:2202`）：

```java
}, internalLockLeaseTime / 3, TimeUnit.MILLISECONDS);
```

> - **默认 `leaseTime = 30s`，看门狗每 `10s` 续一次**（周期是 1/3）
> - **只有不传 `leaseTime` 时才启用看门狗**。一旦写了 `tryLock(10, TimeUnit.SECONDS)` 这种显式租期，
>   Redisson **不会**帮你续期——到期就释放。这是个高频误区。
> - 「续期」的前提是**进程还活着**；机器宕了没人续，锁自然到期释放，**不会死锁**

## 七、锁重试：`tryLock(waitTime, leaseTime, unit)`

手写锁 `setIfAbsent` 失败就返回 false，**只试一次**。Redisson 支持在 `waitTime` 内自旋重试：

```java
// 最多等 1 秒（期间不断重试），锁自动释放时间 10 秒
boolean isLock = lock.tryLock(1, 10, TimeUnit.SECONDS);
```

| 重载 | 行为 |
| --- | --- |
| `tryLock()` | 等 0 秒（只试一次），**启用看门狗** |
| `tryLock(wait, unit)` | 在 `wait` 内重试，**启用看门狗** |
| `tryLock(wait, lease, unit)` | 在 `wait` 内重试，**显式租期，不看门狗** |

> 本项目的 `HandleVoucherOrder` 用的就是**无参** `lock.tryLock()`（`VoucherOrderServiceImpl.java:169`）——
> 「抢不到就立刻失败」，不等待，并且享受看门狗。对秒杀场景是合理的（失败就告诉用户再抢）。

## 八、MultiLock：跨多个 Redis 节点的一致性

单节点 / 主从的问题：写主库还没同步到从库，主库宕机 → 从库升主 → **锁丢了**。

Redisson 的 **MultiLock** 思路：把锁同时写到**多个独立节点**上，**全部成功才算加锁成功**。

```java
RLock lock1 = redissonClient.getLock("lock1");   // 连 Redis 节点 A
RLock lock2 = redissonClient.getLock("lock2");   // 连 Redis 节点 B
RLock lock3 = redissonClient.getLock("lock3");   // 连 Redis 节点 C
RLock multiLock = redissonClient.getMultiLock(lock1, lock2, lock3);
multiLock.lock();
```

> - **每一个锁必须是「不同的节点 / 不同的主从」**，都连同一个实例是没意义的
> - 加锁总耗时上限 = `锁个数 × 1500ms`；期间没全部成功就重试
> - 这是 RedLock 的工程化实现。**成本高**，只有对一致性要求极高的场景才用；
>   本项目的秒杀下单**没有用** MultiLock

## 九、概念层面要注意的坑

1. **`SETNX` 必须配 `EX`，而且要在一条命令里**。`SETNX` + `EXPIRE` 两步写，第二步没执行就是死锁。

2. **锁的 value 一定要放唯一标识**，否则无法安全释放（会误删别人的锁）。只存 `"1"` 是错的。

3. **「比 + 删」必须用 Lua**。`GET` 完再 `DEL` 是两条命令，中间锁可能易主 —— 单条命令原子 ≠ 多命令原子。

4. **TTL 不是越长越好，也不是越短越好**。太长 → 万一持锁方挂得慢，别人等太久；太短 → 业务没跑完锁就没了。
   **本质问题是「预估业务时长」，看门狗才根治**。

5. **显式租期会关掉看门狗**。`tryLock(wait, lease, unit)` 里的 `lease` 一旦传了，Redisson 就不续期了。
   想用看门狗就**别传 leaseTime**。

6. **`PTTL` 返回值在 Lua 里是数字，不等于「失败」**。Redisson 的 Lua 用 `return nil` 表示成功、`return <数字>` 表示失败——
   这个「反直觉」约定在课程源码里很显眼（详见第五节）。

7. **锁的粒度**。key 设计要贴着「业务唯一性」的维度。本项目 `order:{userId}` 只锁了用户，
   「一人一单」其实是按券算的，**偏粗**（同一用户抢不同券会互相阻塞）。

8. **`SISMEMBER` 返回值是 `0/1` 数字**，不是布尔。Lua 里写 `== 1` 判断，不能当 true/false 用。

9. **Redisson 的锁是「单 Redis 实例」保证的**。要跨「主从切换」的强一致，得用 MultiLock（或 RedLock），
   但那是**另一套成本**——别默认「用了 Redisson 就万无一失」。

10. **Lua 里 `redis.call('get', ...)` 取不到时返回 `false`（Lua 视角），不是 `nil`**。
    所以 `tonumber(false)` 会得到 `nil`，直接比较会出错 —— `seckillOrder.lua:15` 之所以要 `tonumber(...)`，
    一半原因就在这。
