## 一、Key 命名规范：从 `code` 到 `login:code:{手机号}`

09-17 记的规范是 `[项目名]:[业务名]:[类型]:[id]`。落到登录业务上：

| 用途 | key 模板 | 实例 |
| --- | --- | --- |
| 短信验证码 | `login:code:{手机号}` | `login:code:13456789001` |
| 登录令牌 | `login:token:{token}` | `login:token:a1b2c3d4-...` |
| （对比）缓存商铺 | `cache:shop:{id}` | `cache:shop:1` |

常量集中在 `RedisConstants` 里，业务代码只引用常量、不写字面量：

```java
public static final String LOGIN_CODE_KEY = "login:code:";
public static final Long   LOGIN_CODE_TTL = 2L;        // 单位：分钟
public static final String LOGIN_USER_KEY = "login:token:";
public static final Long   LOGIN_USER_TTL = 36000L;    // 单位：秒（= 10 小时）
```

> **⚠️ 这两个 TTL 的单位不一样，是这份代码里最容易踩的坑之一。**
> `RedisConstants` 里只有裸数字，**单位完全由调用方传的 `TimeUnit` 决定**，常量本身不过问：
>
> ```java
> set(LOGIN_CODE_KEY + phone, code, LOGIN_CODE_TTL, TimeUnit.MINUTES);  // 2 分钟
> expire(key, LOGIN_USER_TTL, TimeUnit.SECONDS);                        // 36000 秒
> ```
>
> 所以 `LOGIN_USER_TTL` 是 **36000 秒 = 10 小时**。
> 如果照抄 `2L` 的手感顺手写个 `10L` 再配 `TimeUnit.SECONDS`，登录态就只有 **10 秒** —— 一登录就掉线。
> course 原版这里用的是 `TimeUnit.MINUTES`，本项目改成了 `SECONDS`：**改单位时，值和调用点必须一起改。**
>
> 另外，course 原版的登录态 TTL 是 30 分钟，本项目给到 10 小时。
> 差别是：TTL 越长越不容易被强制重登，代价是一个废弃的 token 会在 Redis 里多躺很久。

### 1.1 为什么验证码的 key 必须带手机号

这是**Session → Redis 迁移中最容易漏掉的一个语义变化**：

- **Session 方案**：每个客户端一个独立 session，key 只写 `"code"` 就够了 —— 天然隔离。
- **Redis 方案**：所有用户共用同一份 Redis，key 全局唯一。如果还写 `"code"`，**所有用户的验证码会互相覆盖**，A 的验证码能把 B 顶掉。

> **一句话本质**
>
> Session 的隔离性来自「每个客户端一个容器」；Redis 没有这个容器，
> 所以**原本由容器提供的隔离维度（用户、手机号）必须显式编进 key 里**。
> key 设计不是命名好看，是在补回丢失的隔离维度。

### 1.2 为什么登录态用 token 而不是手机号当 key

course 1.7.2 讲了 key 要满足两点：**唯一性** + **方便携带**。

理论上 `login:token:13456789001` 也行，但：

- **手机号是敏感信息**，明文出现在每次请求的头里、出现在前端 localStorage 里、出现在 nginx access log 里，都不合适；
- 服务端生成随机 `token` 后，前端只需要携带这串无意义的随机串。

```java
String token = UUID.randomUUID().toString();
```

> 注意：本项目用的是 `toString()`，**带横线，36 位**。course 原版是 `UUID.randomUUID().toString(true)`，`true` 表示去横线，32 位。两种都能用，只是长度和格式不同 —— 对接前端时两边要一致。

## 二、String 类型：验证码的存储

```java
stringRedisTemplate.opsForValue()
        .set(LOGIN_CODE_KEY + phone, code, LOGIN_CODE_TTL, TimeUnit.MINUTES);
```

对应 Redis 命令（一条带过期时间的 SET）：

```text
SET login:code:13456789001 482913 EX 120
```

三个要点：

1. **验证码天然适合 String**：一个手机号对应一个 6 位数，没有结构可言，无脑 String。
2. **必须带过期时间**。验证码是「有有效期的一次性凭据」，不给 TTL 就会永久留在 Redis 里 —— 既浪费内存，又意味着几个月前的验证码还能用来登录。
3. **写入和设置过期一步完成**（`SET ... EX`），而不是 `SET` 之后再 `EXPIRE`。见第四节。

## 三、Hash 类型：登录用户信息的存储

```java
Map<String, Object> map = BeanUtil.beanToMap(userDTO, new HashMap<>(),
        CopyOptions.create()
                .setIgnoreNullValue(true)
                .setFieldValueEditor((fieldName, fieldValue) -> fieldValue.toString()));

stringRedisTemplate.opsForHash().putAll(LOGIN_USER_KEY + token, map);
```

对应 Redis 命令：

```text
HSET login:token:a1b2c3d4-... id 5 nickName user_abc123 icon ""   # 批量写，等价于 HMSET
HGETALL login:token:a1b2c3d4-...                                  # 读取，对应 entries(key)
```

> `icon` 之所以是 `""` 而不是缺失：`User` 实体上写了 `private String icon = ""`，
> 所以即使是新注册用户，`BeanUtil.copyProperties` 拷出来的 `icon` 也是空串而非 `null`。

### 3.1 String 还是 Hash？（course 1.7.1 的取舍）

同样的用户信息，两种存法：

```text
# 方案 A：String + JSON
SET login:token:xxx '{"id":5,"nickName":"user_abc123","icon":""}'

# 方案 B：Hash
HSET login:token:xxx id 5 nickName user_abc123 icon ""
```

| 维度 | String + JSON | Hash |
| --- | --- | --- |
| 读全量 | 一次 GET，反序列化整个 JSON | 一次 HGETALL |
| **读单个字段** | 必须全量取出再解析 | `HGET key field`，**只读一个字段** |
| 改单个字段 | 必须全量覆盖 | `HSET key field value`，**只写一个字段** |
| 内存占用 | 要额外存一份 JSON 的括号、引号、字段名（每个 key 都重复一遍） | 字段名只在 Hash 内部存一次 |

> course 的结论：数据简单、不在意内存时，String 也可以。
> 登录态这里选了 Hash，因为它**后续可能要单独更新某个字段**（比如改了昵称），Hash 不用全量覆盖。

### 3.2 为什么存 `UserDTO` 而不是 `User` 实体

```java
public class UserDTO {
    private Long id;
    private String nickName;
    private String icon;
}
```

`User` 实体里有 `phone` 和 `password`。**敏感字段根本不进 Redis，也不随响应回到前端。** 这是 09-17 就定下来的原则，迁移到 Redis 后同样成立。

## 四、EXPIRE 与 TTL：两种过期语义

### 4.1 基本原理

```text
EXPIRE key seconds      # 设置/重置过期时间
TTL key                 # 查看剩余秒数；-1 = 永不过期，-2 = key 不存在
PERSIST key             # 移除过期时间，变成永久
```

Java 侧：

```java
stringRedisTemplate.expire(key, LOGIN_USER_TTL, TimeUnit.SECONDS);
```

### 4.2 登录态用的是「滑动过期」

验证码和登录态的过期策略是**不一样的**，这是本节最值得记的一点：

| | 验证码 | 登录态 |
| --- | --- | --- |
| 命令 | `set(k, v, ttl, unit)` 一步写入 | `putAll` 写入，**再单独** `expire` |
| 策略 | **固定 TTL**：2 分钟，到点必死 | **滑动 TTL**：每次请求都重新 `EXPIRE` 续命 |
| 语义 | 验证码过期了就该重新发 | 只要还在操作，就不该被踢下线 |

滑动续期就发生在 `RefreshInterceptor` 里：

```java
// 有请求,说明用户在操作,刷新有效期
stringRedisTemplate.expire(key, RedisConstants.LOGIN_USER_TTL, TimeUnit.SECONDS);
```

> **一句话本质**
>
> `EXPIRE` 的语义是**重置**，不是「在原有基础上加」。
> 所以「每次请求都调一次 `EXPIRE`」天然就实现了滑动续期 —— 不需要读剩余时间、也不需要自己算差值。

### 4.3 `putAll` + `expire` 不是原子的（隐患）

```java
stringRedisTemplate.opsForHash().putAll(LOGIN_USER_KEY + token, map);
stringRedisTemplate.expire(LOGIN_USER_KEY + token, LOGIN_USER_TTL, TimeUnit.SECONDS);
```

这两条是**两次独立的 Redis 往返**。如果中间进程挂了 / 网络断了，key 写进去了但**没设过期 → 这条登录态永久驻留 Redis**。

course 原版就是这个写法。要修的话有两条路：

- 用 Lua 脚本把「写 Hash + 设过期」合成一次原子操作（见 course 4.7 的 Lua 部分）；
- 或者接受这个极小概率，靠定时任务扫无 TTL 的 `login:token:*` 兜底。

## 五、Java API ↔ Redis 命令对照表

本项目登录业务用到的全部映射：

| Java（StringRedisTemplate） | Redis 命令 | 本项目用在哪 |
| --- | --- | --- |
| `opsForValue().set(k, v, ttl, unit)` | `SET k v EX <ttl>` | 存验证码 |
| `opsForValue().get(k)` | `GET k` | 读验证码 |
| `opsForHash().putAll(k, map)` | `HSET k f1 v1 f2 v2 ...` | 存登录用户 |
| `opsForHash().entries(k)` | `HGETALL k` | 读登录用户 |
| `expire(k, ttl, unit)` | `EXPIRE k <ttl>` | 刷新登录态 |
| `delete(k)` | `DEL k` | （登出用，本项目未实现） |

> 规律：`opsForValue()` → String、`opsForHash()` → Hash、`opsForList()`/`opsForSet()`/`opsForZSet()` 以此类推。
> 方法名基本是命令名的小驼峰（`entries` ↔ `HGETALL` 是个例外，`entries` 取的是「所有键值对」这个语义）。

### 5.1 返回值约定（09-17 已记，这里回顾）

- **单值查询查不到 → `null`**：`opsForValue().get(不存在的key)` 返回 `null`
- **集合查询查不到 → 空集合**：`opsForHash().entries(不存在的key)` 返回**空 Map**

这直接决定了拦截器里的判空写法 —— `entries` 是集合操作，**只能用 `isEmpty()` 判断，不能判 `null`**：

```java
Map<Object, Object> entries = stringRedisTemplate.opsForHash().entries(key);

// 匹配用户
if (entries.isEmpty()) {
    return true;      // 注意：这里不是 401，是放行 —— 见项目笔记
}
```

## 六、序列化约束：StringRedisTemplate 的两条铁律

`StringRedisTemplate` 的 key 和 value 序列化器都是 **`StringRedisSerializer`**，这意味着 **写进去的东西必须真的是 String**。而 Hash 的读写踩了两个坑，代码里都用 `CopyOptions` 处理了：

### 6.1 铁律一：Hash 的 field/value 都必须是 String

`BeanUtil.beanToMap(userDTO)` 会把 `id` 变成 **`Long` 类型**。直接 `putAll` 会抛 **`ClassCastException`**（`java.lang.Long cannot be cast to java.lang.String`）。

> 具体炸在哪：`StringRedisSerializer` 声明的是 `RedisSerializer<String>`，接口方法 `serialize(String)` 在泛型擦除后会生成一个 `Object` 入参的桥接方法并强转成 `String`。所以它拿到的**必须**是 `String`，是 `Long` 就在这一步直接强转失败。

```java
.setFieldValueEditor((fieldName, fieldValue) -> fieldValue.toString())
```

这个方法把每个 value 统一 `toString()`，**写进去的全是 String**。

> 设计上有点别扭（明明是 Long 却存成 `"5"`），但读回来的时候 Hutool 会自动把 `"5"` 转回 `Long`，所以功能上没问题：
>
> ```java
> UserDTO userDTO = BeanUtil.fillBeanWithMap(entries, new UserDTO(), false);
> ```
>
> `fillBeanWithMap` 按字段类型做转换（String → Long），最后一个参数 `false` 表示**不忽略转换错误**。

### 6.2 铁律二：null 值不要写进去

```java
.setIgnoreNullValue(true)
```

作用顺序是：**先过滤掉 `null`，再对剩下的值调 editor**。所以 `setIgnoreNullValue(true)` 实际上是在保护 `fieldValue.toString()` 不 NPE。

不过要说明的是，**这一行在本项目里目前是个防御性设置、而非必需**：

- `UserDTO` 的三个字段恰好都不会是 `null` —— `icon` 在 `User` 实体上就初始化成了 `""`，`id` 是自增回填的，`nickName` 建号时赋了值；
- 所以真正每天都在生效的是 `setFieldValueEditor`，`setIgnoreNullValue` 是为「`UserDTO` 将来加了可空字段」预留的。

> 两条铁律合并起来记：**`setFieldValueEditor(...toString())` 是必需的（`id` 是 `Long`）；`setIgnoreNullValue(true)` 是防御性的（挡住 null 引发的 NPE）。**

## 七、为什么登录态要放 Redis（对比 09-17 的 Session 方案）

09-17 那篇的第七节从「Session 共享问题」的角度推过一遍，这里从 **Redis 提供的能力**角度再收一次：

| 能力 | Session | Redis |
| --- | --- | --- |
| **多实例共享** | ✗ 各存各的，用户随机掉线 | ✓ 天然共享 |
| **跨服务共享** | ✗ 只有这个 Tomcat 能读 | ✓ 别的服务也能读同一份登录态 |
| **精确 TTL** | ✗ 只有「30 分钟不活动」这一档 | ✓ 每个 key 单独设，秒级 |
| **滑动续期** | 半自动（Tomcat 管） | ✓ 自己 `EXPIRE`，逻辑完全可控 |
| **主动失效** | 难（拿不到别的节点的 session） | ✓ `DEL login:token:xxx` 即刻生效 |
| **查看/排查** | 看不到 | ✓ `redis-cli` 直接 `HGETALL` |

> 最后两条是**运维视角**的价值，容易被忽略但很实际：
> 线上有人反馈「莫名掉线」时，`TTL login:token:<token>` 一眼就能看出到底是没登录上、还是过期了。

## 八、可以更好的地方

> 每条都按「**现状 → 为什么不行 → 怎么改**」写。
> 这些**都没有改代码**，只是对照现有实现记下来的改进方向。

### 8.1 安全

#### (1) 验证码校验通过后没有删除 —— 可重放

**现状**：`login()` 里 `get` 出验证码比对完之后，就直接往下走查用户了：

```java
String cachedcode = stringRedisTemplate.opsForValue().get(LOGIN_CODE_KEY + phone);
if (cachedcode == null || !cachedcode.equals(code)) {
    return Result.fail("验证码错误!");
}
// ← 验证码还躺在 Redis 里，2 分钟内可以无限次复用
```

**问题**：同一个验证码在 TTL 内可以重复登录，等于把「一次性凭据」变成了「2 分钟有效的密码」。

**改法**：校验通过后立刻删掉，一行的事：

```java
stringRedisTemplate.delete(LOGIN_CODE_KEY + phone);
```

#### (2) 验证码被明文写进了日志

**现状**：`application.yaml` 里开着 `logging.level.com.hmdp: debug`，而代码里有这两行：

```java
log.debug("已成功发送验证码 {}", code);              // sendCode
log.debug("redis:{},请求:{}", cachedcode, code);     // login
```

**问题**：**验证码是明文打进日志文件的**。任何能看日志的人（运维、日志采集平台、不小心提交上去的日志文件）都能拿到任意手机号的验证码，直接绕过短信验证。

**改法**：调试期留着没问题，**上线前必须删掉或脱敏**（比如只打手机号后四位 + 验证码长度）。

#### (3) 没有发送频率限制 —— 会被当成短信轰炸机

**现状**：`sendCode` 除了校验手机号格式，不设任何限制，同一手机号可以无限调。

**改法**：用 `SET NX EX` 做 60 秒冷却，**一条命令、天然原子**：

```java
public static final String LOGIN_CODE_LIMIT_KEY = "login:code:limit:";

Boolean sent = stringRedisTemplate.opsForValue()
        .setIfAbsent(LOGIN_CODE_LIMIT_KEY + phone, "1", 60, TimeUnit.SECONDS);

if (Boolean.FALSE.equals(sent)) {
    return Result.fail("发送过于频繁，请稍后再试");
}
```

> **判空写法是个坑**：`setIfAbsent` 返回的是包装类型 `Boolean`，**可能为 `null`**（在 pipeline / 事务里必然为 null）。
> 写 `if (!sent)` 会直接 NPE，必须写 `Boolean.FALSE.equals(sent)`。

#### (4) 没有错误次数限制 —— 6 位验证码可以被爆破

**现状**：验证码只有 6 位数字（100 万种），2 分钟窗口内**不限次数**地试。

**改法**：失败计数 + 超限作废。

```java
public static final String LOGIN_CODE_FAIL_KEY = "login:code:fail:";

// 校验失败分支里：
Long fails = stringRedisTemplate.opsForValue().increment(LOGIN_CODE_FAIL_KEY + phone);
stringRedisTemplate.expire(LOGIN_CODE_FAIL_KEY + phone, LOGIN_CODE_TTL, TimeUnit.MINUTES);
if (fails > 5) {
    stringRedisTemplate.delete(LOGIN_CODE_KEY + phone);   // 直接作废，必须重新获取
    return Result.fail("尝试次数过多，请重新获取验证码");
}
```

> 注意 `INCR` 会**保留**已有 key 的 TTL，但首次创建时 key 是没有 TTL 的，
> 所以 `expire` 每次都要跟着调。想更稳还是用 Lua 把两条合成一次。

### 8.2 正确性

#### (1) `putAll` + `expire` 不是原子的

**现状**（4.3 已讲过）：两次独立往返。

```java
stringRedisTemplate.opsForHash().putAll(LOGIN_USER_KEY + token, map);
stringRedisTemplate.expire(LOGIN_USER_KEY + token, LOGIN_USER_TTL, TimeUnit.SECONDS);
```

**问题**：中间挂掉 / 断网，就留下一个**永不过期的 token** —— 而且是带着完整用户信息的，等于一个永久后门。

**改法**：用 Lua 把两条合成一次原子操作。

```lua
-- KEYS[1] = login:token:<token>
-- ARGV[1] = ttl（秒）
-- ARGV[2..] = field1, value1, field2, value2 ...
redis.call('HSET', KEYS[1], unpack(ARGV, 2))
redis.call('EXPIRE', KEYS[1], ARGV[1])
return 1
```

```java
private static final RedisScript<Long> SAVE_LOGIN_SCRIPT = new DefaultRedisScript<>(
        "redis.call('HSET', KEYS[1], unpack(ARGV, 2)) " +
        "redis.call('EXPIRE', KEYS[1], ARGV[1]) " +
        "return 1", Long.class);

// 把 map 摊平成 [ttl, field1, value1, field2, value2, ...]
List<String> args = new ArrayList<>();
args.add(String.valueOf(LOGIN_USER_TTL));
map.forEach((k, v) -> { args.add(k); args.add(String.valueOf(v)); });

stringRedisTemplate.execute(SAVE_LOGIN_SCRIPT,
        Collections.singletonList(LOGIN_USER_KEY + token),
        args.toArray());
```

> 不想引入 Lua 的话，退一步可以用 `executePipelined` 把两条压成**一次网络往返** ——
> 能省 RTT，但**仍不保证原子性**，中间挂掉照样留下无 TTL 的 key。

#### (2) `HttpSession` 参数残留

**现状**：`sendCode` / `login` 从 Controller 到 `UserServiceImpl` 一路都带着 `HttpSession session`，方法体里完全没用。

**问题**：**它不是无害的化石**。Spring MVC 见到 `HttpSession` 参数会调 `request.getSession()` —— 于是每个登录 / 发码请求都会**凭空建出一个 Tomcat session**，还顺带下发一个没人用的 `JSESSIONID` cookie。这是在白白占服务端内存。

**改法**：三处签名一起删掉即可（`UserController` → `IUserService` → `UserServiceImpl`）。

### 8.3 性能

#### 每个请求一次 `EXPIRE` 的写放大

**现状**：`RefreshInterceptor` 对每个带 token 的请求都调一次 `expire`。

**问题**：`EXPIRE` 是**写命令** —— 会进 AOF、会走主从复制。用户逛街时一路点，每个请求都产生一次写，这是实打实的写放大。

**改法**：本地记「上次刷新时刻」，只在接近过期时才真正刷。

```java
private static final long REFRESH_THRESHOLD_MS = RedisConstants.LOGIN_USER_TTL * 1000 / 2;

long now = System.currentTimeMillis();
Long last = lastRefresh.get(token);          // 生产建议用带过期时间的 Caffeine 缓存
if (last == null || now - last > REFRESH_THRESHOLD_MS) {
    stringRedisTemplate.expire(key, RedisConstants.LOGIN_USER_TTL, TimeUnit.SECONDS);
    lastRefresh.put(token, now);
}
```

> 多实例下每个实例各判各的，**不会错** —— 「刷新」这个动作是幂等的，
> 最坏情况只是多刷几次，不会刷错。

### 8.4 完整性

#### (1) 登出没有实现

**现状**：`/user/logout` 直接 `return Result.fail("功能未完成")`。

**改法**：Redis 方案下登出的语义非常直接 —— `DEL login:token:<token>`。

```java
@PostMapping("/logout")
public Result logout(@RequestHeader(value = "authorization", required = false) String token) {
    if (StrUtil.isNotBlank(token)) {
        stringRedisTemplate.delete(RedisConstants.LOGIN_USER_KEY + token);
    }
    return Result.ok();
}
```

> 这里有个小麻烦：Controller 里**拿不到 token** —— `UserHolder` 里只存了 `UserDTO`，token 没被留下来。
> 所以最省事的做法是 `@RequestHeader` 自己取；另一种做法是让 `RefreshInterceptor` 顺手把 token 也塞进 ThreadLocal。

#### (2) 多端登录会留下僵尸 token

**现状**：同一个用户每登录一次就新建一个 `login:token:<uuid>`，**旧的全部继续有效**（直到各自 10 小时过期）。既登不掉，也收不回。

**改法**：如果要「后登录踢掉先登录」，额外维护一份 `userId → 当前 token`：

```java
String oldToken = stringRedisTemplate.opsForValue().get(LOGIN_USER_ID_KEY + user.getId());
if (StrUtil.isNotBlank(oldToken)) {
    stringRedisTemplate.delete(LOGIN_USER_KEY + oldToken);   // 把上一个踢下线
}
stringRedisTemplate.opsForValue()
        .set(LOGIN_USER_ID_KEY + user.getId(), token, LOGIN_USER_TTL, TimeUnit.SECONDS);
```

反过来，如果要**允许多端并存**，就把这里的单个 token 换成 Set，登出时逐个删。

> 这两种语义（单端 / 多端）必须二选一，**默认什么都不做其实是最差的一种** —— 它既不能踢人，也不记录谁在线。

### 8.5 优先级

| 改动 | 成本 | 收益 | 建议 |
| --- | --- | --- | --- |
| 删掉验证码日志 | 一行 | 高（防绕过） | **必做** |
| 验证码用完即删 | 一行 | 高（防重放） | **必做** |
| 发送频率限制 | 三行 | 高（防刷/省钱） | **必做** |
| 删 `HttpSession` 参数 | 三处签名 | 中（省内存） | 建议做 |
| 登出实现 | 五行 | 中（功能完整） | 建议做 |
| 错误次数限制 | 十行 | 中（防爆破） | 建议做 |
| `putAll`+`expire` 原子化 | 引入 Lua | 低（概率极小） | 看情况 |
| TTL 刷新节流 | 需本地缓存 | 低（只在高压下才有意义） | 看情况 |
| 多端登录语义 | 十行 | 中（取决于产品） | 看情况 |
