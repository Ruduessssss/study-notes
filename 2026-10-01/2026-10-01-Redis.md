## 一、先做选择题

社交场景里，我们要存的东西几乎都是「**一个集合**」：

| 需求 | 集合元素 | 要不要去重 | 要不要排序 |
| --- | --- | --- | --- |
| 谁关注了我 | 用户 id | 要 | 不要 |
| 我给谁点过赞 | 用户 id | 要 | 不要 |
| 某篇笔记的点赞人 TOP5 | 用户 id | 要 | **要（按点赞时间）** |
| 我的收件箱（Feed 流） | 笔记 id | 要 | **要（按发布时间）** |

- **需要去重** → 排除 List（List 允许重复）。
- **只去重、不排序** → **Set**。
- **既要去重、又要排序** → **ZSet（Sorted Set）**。

一句话：**Set 是「谁」，ZSet 是「谁、以及什么时候 / 多少」**。

## 二、Set：无序、去重的集合

### 2.1 常用命令

| 命令 | 作用 | 项目里的用法 |
| --- | --- | --- |
| `SADD key m [m...]` | 加入成员（已存在则忽略） | 关注后 `SADD Follow:{我} {对方id}` |
| `SREM key m [m...]` | 移除成员 | 取关后 `SREM Follow:{我} {对方id}` |
| `SISMEMBER key m` | 是否是成员 → `1`/`0` | 8.3 早期的「是否点过赞」（后被 `ZSCORE` 取代） |
| `SMEMBERS key` | 全部成员，**顺序不保证** | 调试用 |
| `SCARD key` | 成员个数 | 统计 |
| `SINTER k1 k2` | **交集** | **共同关注** |
| `SUNION k1 k2` | 并集 | — |
| `SDIFF k1 k2` | 差集 | — |

### 2.2 `SINTER` 就是「共同关注」的天然答案

「我和他共同关注了谁」= `SINTER Follow:{我} Follow:{他}`。

为什么不是 SQL？如果用表存关注关系，共同关注要写成 `SELECT ... JOIN` 或多次 `IN` 子查询；
而 Set 的**交集是内置运算**，两边集合都在 Redis 里，一次命令拿到结果。

```text
Follow:1 = {2, 3, 5}      # 1 关注了 2、3、5
Follow:7 = {3, 5, 9}      # 7 关注了 3、5、9

SINTER Follow:1 Follow:7  # → {3, 5}  ← 共同关注
```

变体：

- `SINTERSTORE dest k1 k2` —— 把交集**存到新 key**，适合结果要复用/缓存。
- `SINTERCARD numkeys k1 k2 [LIMIT n]`（Redis 7.0+）—— **只要个数、不要成员**，大集合下比 `SINTER` 省内存。

> **复杂度**：`SINTER` 的时间复杂度是 O(N×M)（N 是最小集合基数，M 是集合个数）。
> 关注列表一般几百到几千，没问题；但如果要做「亿级用户求交集」的推荐，就不能直接 `SINTER` 了。

### 2.3 Set 的坑

1. **无序**：`SMEMBERS` 返回的顺序**不可依赖**。所以本项目的共同关注返回给前端时不要求顺序，可以接受；反过来，一旦业务要求按时间排，Set 就出局了。
2. **不能存分数**：Set 只能表达「在不在集合里」，**表达不了「什么时候进的」**。这正是点赞从 Set 升级到 ZSet 的原因。
3. **没有「过期时间戳」**：Set 成员没有附加字段。

## 三、ZSet：带分数的有序集合

ZSet = 「不重复的成员」+「每个成员一个 `double` 分数」，**按分数排序**。

### 3.1 写入类命令

| 命令 | 作用 |
| --- | --- |
| `ZADD key score member [score member ...]` | 加入/更新成员及其分数 |
| `ZINCRBY key increment member` | **对成员分数自增**（成员不存在则从 0 开始），返回新分数 |
| `ZREM key member [member ...]` | 移除成员 |
| `ZREMRANGEBYRANK k start stop` | 按下标删除（**用来给收件箱封顶**，见 5.2） |
| `ZREMRANGEBYSCORE k min max` | 按分数删除 |

重点：**`ZADD` 同一个 member 再写一次，是「更新 score」，不是新增一条**。这就是 ZSet 也天然去重的原因
（本项目的点赞：`ZADD blog:liked:1 <timestamp> 8` —— 再点一次是同 member 覆盖，靠这个特性天然一人一赞）。

### 3.2 读取类命令

| 命令 | 语义 |
| --- | --- |
| `ZSCORE key member` | 取某成员分数；**成员不存在返回 `nil`** |
| `ZCARD key` | 成员数 |
| `ZCOUNT key min max` | 分数在 `[min,max]` 内的成员数 |
| `ZRANK` / `ZREVRANK key member` | 升序 / 降序排名（从 0 开始） |
| `ZRANGE key start stop [WITHSCORES]` | **按下标**取，**升序** |
| `ZREVRANGE key start stop [WITHSCORES]` | 按下标取，**降序** |
| `ZRANGEBYSCORE key min max [WITHSCORES] [LIMIT offset count]` | **按分数**取，升序 |
| `ZREVRANGEBYSCORE key max min [WITHSCORES] [LIMIT offset count]` | 按分数取，**降序** |

> Redis 6.2 起给 `ZRANGE` 加了 `REV` / `BYSCORE` / `BYLEX` 选项，官方把 `ZREVRANGE`、`ZRANGEBYSCORE`、
> `ZREVRANGEBYSCORE` 标成 deprecated（**但没删，仍然可用**）。本项目用的 Spring Data Redis API 底层发的还是老命令。

### 3.3 ⚠️ 参数顺序的大坑：`BYSCORE` 的两个变体是反的

```text
ZRANGEBYSCORE    key  min  max       # 小 → 大
ZREVRANGEBYSCORE key  max  min       # 大 → 小  ← 注意反了！
```

`ZREVRANGEBYSCORE` 的第一个分数是 **max**、第二个是 **min**，**跟 `ZRANGEBYSCORE` 正好反过来**。
写错了不是报错，而是**直接返回空**（因为 min > max 时区间为空），非常难查。

**Spring Data Redis 又反过来包了一层**：Java 里 `reverseRangeByScoreWithScores(key, min, max, offset, count)`
的参数是 **min 在前**，它内部帮你翻成 `ZREVRANGEBYSCORE key max min`。所以：

| | 第一个分数参数 | 第二个分数参数 |
| --- | --- | --- |
| Redis `ZREVRANGEBYSCORE` | **max** | min |
| Java `reverseRangeByScore` | **min** | max |

本项目 `reverseRangeByScoreWithScores(key, 0, lastId, offset, 2)` → 实际发出 `ZREVRANGEBYSCORE feed:{id} lastId 0 WITHSCORES LIMIT offset 2`。

### 3.4 边界语法

分数区间默认**闭区间**（含端点）。要开区间用 `(` 前缀；无穷用 `-inf` / `+inf`：

```text
ZRANGEBYSCORE k (1 5        # 1 < score <= 5
ZRANGEBYSCORE k -inf +inf   # 全部
ZREVRANGEBYSCORE k +inf -inf LIMIT 0 5   # 最新的 5 条
```

## 四、score 的语义：你自己定义的「排序依据」

同一个 ZSet 结构，`score` 可以是**时间**、**数量**、**热度**……语义完全由业务决定：

| 场景 | member | score | 排序效果 |
| --- | --- | --- | --- |
| 点赞榜（本项目） | 用户 id | **点赞时间毫秒** | `ZRANGE 0 4` → 最早点赞 TOP5 |
| 收件箱（本项目） | 笔记 id | **发布时间毫秒** | `ZREVRANGEBYSCORE` → 最新在前 |
| 热搜榜 | 词条 | **搜索次数** | `ZREVRANGE 0 9` → 热词 TOP10，`ZINCRBY` 累加 |
| 延迟队列 | 任务 id | **执行时间戳** | `ZRANGEBYSCORE 0 now` → 到点该执行的任务 |

> **为什么时间戳能当 score**：`score` 是 IEEE 754 `double`，**整数能精确表示到 2^53 ≈ 9×10^15**。
> 毫秒时间戳约 1.7×10^12，**远在精确范围内**，所以不会出现「相邻毫秒被四舍五入成同一个值」。
> 但如果换成**微秒 / 纳秒**时间戳（10^15、10^18），就会丢精度 —— 那就不能直接当 score 了。

## 五、为什么有序集合能当排行榜

### 5.1 结构决定了它又快又省

ZSet 底层是 **跳表（skiplist）+ 哈希表**：

- **哈希表**：`ZSCORE` / `ZADD` 定位成员是 O(1)。
- **跳表**：按 score 有序，插入 O(log N)，**按分数范围取一段是 O(log N + M)**（M = 取出的条数）。
- 所以「取 TOP5」`ZRANGE 0 4` 不用扫全表，直接从跳表头部走 5 步。
- 同时还自带 `ZRANK` 算排名，`ZINCRBY` 累加计数 —— 排行榜要的三个动作（写分数、取区间、取排名）都有原生命令。

对比用 MySQL 做排行榜：`ORDER BY score DESC LIMIT 5` 每次都要排序；`ZINCRBY` 对应 `UPDATE ... SET score = score + 1`，
并发下还得考虑行锁。热点榜单放 Redis 是常规操作。

### 5.2 排行榜/收件箱都要「封顶」

ZSet 不会自己淘汰元素。一个一直涨的榜单（比如某条爆款笔记的点赞集合）会**无限占内存**。
常见做法是定期裁剪：

```text
ZREMRANGEBYRANK key 0 -1001    # 只保留分数最高的 1000 个（删掉排名 0 到倒数第 1001 之间的）
```

或者给整个 key 设 `EXPIRE`。**本项目这两件事都没做** —— `blog:liked:{id}` 和 `feed:{userId}` 都是**永不过期**的，
长期跑下去是内存隐患（见第八节）。

## 六、Feed 流为什么用 ZSet 建模

Feed 流（关注推送）要的两个能力，正好是 ZSet 的两大强项：

1. **每个粉丝一个「收件箱」** → `feed:{粉丝id}`，天然按用户隔离。
2. **收件箱里按发布时间倒序，且要能翻页** → 用发布时间当 score，`ZREVRANGEBYSCORE ... LIMIT offset count` 直接翻页。

为什么**不把整个笔记对象塞进 ZSet**？因为推模式是**写扩散**：一个大 V 发一篇笔记要写给 N 个粉丝。
存 id 只写 `id + score`（几十字节）；存整个 JSON 就是 N 份完整对象，内存直接爆炸。

```text
发布笔记 → 查所有粉丝 → 对每个粉丝：
ZADD feed:{粉丝id} <当前毫秒> <笔记id>
```

读取时：

```text
ZREVRANGEBYSCORE feed:{粉丝id} <lastId> 0 WITHSCORES LIMIT <offset> 2
```

### 6.1 为什么不能像普通列表那样按页码翻

ZSet 的元素会**不断在头部插入**。传统「第 2 页 = 跳过前 5 条」的页码分页，在插入后**下标全部平移**，
第二页会重复读到第一页的尾巴。所以要「**滚动分页**」：**记录上次读到哪，而不是记录第几页**。

具体做法是用两个游标：

| 游标 | 含义 | 从哪来 |
| --- | --- | --- |
| `lastId`（=`minTime`） | 上次返回的**最小时间戳**，本次作为分数上界 | 上次结果的 `minTime` |
| `offset` | 在 `lastId` 这个分数上，**已经读过几条**，本次要跳过 | 上次结果的 `offset` |

### 6.2 `offset` 为什么必须存在 —— 同一毫秒多条

`score` 是**毫秒**时间戳，同一毫秒里完全可能有多条笔记（时间戳相同 → score 相同）。
当一页的边界正好落在某个毫秒上时，只带 `lastId` 去查下一回合，Redis 会把**这个毫秒的所有元素都返回**，
包括上一页已经给过的 —— **不跳过就重复**。

因此服务端要算两个数返回给前端：

- `minTime`：本页最小时间戳 → 下次的 `lastId`；
- `offset`：下次在 `minTime` 这个分数上**要跳过的条数**。

> ⚠️ 注意本项目代码把 `offset` 算成了「**本页末尾 score == minTime 的元素条数**」，
> **这个算法在同一毫秒的条数 ≥ 页大小时会算少**，导致下一页重复返回同一条。
> 详见证伪过程见 `黑马点评08-达人探店与好友关注.md` 第五节 —— 这里只记 API 语义，不背书那个实现。

**并发写带来的额外复杂度**：如果翻页期间那个毫秒又插进了新元素，`offset` 的语义会漂移 —— 这也是「滚动分页」在
写密集场景下仍可能抖动的根源。真实产品里通常改用「**按 id 游标**」（把单调递增、带时间信息的 id 当游标，
如本项目的 `RedisIdWorker` 生成的 id），可以避开同一毫秒的歧义。

## 七、Set 与 ZSet 的选型速查

| 你的问题 | 选择 |
| --- | --- |
| 这个用户在不在集合里？ | **Set**（`SISMEMBER`） |
| 两个集合的重合部分？ | **Set**（`SINTER`） |
| 要不要按时间/数量排个序？ | 要 → **ZSet** |
| 谁是第一名 / 前 N 名？ | **ZSet**（`ZRANGE`/`ZREVRANGE` + `ZRANK`） |
| 需要一个可累加的计数器？ | **ZSet**（`ZINCRBY`） |
| 只关心「有没有」、不关心顺序，且集合很大？ | **Set**（更省内存，没有 score） |

> 记忆点：**只要出现了「TOP N」「按时间」「排行榜」「第几名」，就选 ZSet**；
> 否则 Set 更省。本项目里点赞从 Set 改成 ZSet，唯一的驱动力就是 8.4 的「TOP5 排行榜」。

## 八、概念层面要注意的坑

1. **分数区间命令的参数顺序是反的**。`ZREVRANGEBYSCORE key max min` —— 先大后小，和 `ZRANGEBYSCORE` 相反；
   Spring 的 Java API 又把参数排回 `min, max`。见 3.3。这是最高频的低级错误，写错只会静默返回空。

2. **`ZSCORE` 返回 `nil` 代表「成员不存在」，不是「分数为 0」**。Java 里拿到的 `Double` 可能是 `null`，
   **直接拆箱会 NPE**。本项目 `likeBlog` 用的是 `if (score == null)`，是对的；但换成 `double s = ...` 就炸了。

3. **Set 的 `SMEMBERS` / `SINTER` 顺序不保证**。凡是要顺序的地方，Set 都不能胜任 ——
   这就是「点赞排行榜」必须换 ZSet 的根本原因。而带 `REV` 的命令（如 `ZREVRANGEBYSCORE`）在**同分内部按 member 的逆字典序**排（正向的 `ZRANGE*` 才是正字典序），
   「同分先来后到」在 Redis 里并不能靠 ZSet 本身保证，要么分数唯一、要么自己再排。

4. **ZSet 的 score 是 `double`**。整数在 2^53 以内精确，毫秒时间戳没问题；**微秒/纳秒会丢精度**，别拿它当 score。

5. **ZSet 不会自动淘汰**。榜单/收件箱要自己 `ZREMRANGEBYRANK` 裁剪或设 `EXPIRE`。
   **本项目两个 ZSet（`blog:liked:*`、`feed:*`）都没有过期时间也没有裁剪**，是长期内存隐患。

6. **写扩散（推模式）的内存代价随大 V 粉丝数线性膨胀**。一个大 V 一条笔记 = N 次 `ZADD`（N = 粉丝数）。
   量级上去之后必须走「**推拉结合**」：活跃粉丝写扩散、普通粉丝读扩散（上线时再去大 V 的发件箱拉）。
   本项目是**纯推模式**，只适合小规模学习场景。

7. **`SINTER` 不是免费的**：O(N×M)。关注列表很大时，「共同关注」这种接口要考虑分页/`SINTERCARD`/离线算。

8. **Redis 里的副本集合会漂移**。`Follow:{userId}` 是 `tb_follow` 的副本：
   只写库不写 Redis（或反之）都会让两者不一致；老数据（改造之前就存在的关注）也不会自动进 Redis。
   **DB 是真相源，Redis 只是加速结构** —— 一旦不一致，共同关注会静默算错（返回空集，不报错）。

9. **别用 `KEYS pattern` 去遍历这些集合**。线上会阻塞 Redis。要遍历用 `SCAN`，
   ZSet 按分数遍历用 `ZSCAN`。
