> **说明**：本文**只讲后端**，不涉及前端实现（前端 Vue 页面在课程资料里，本项目不含）。
>
> 对照代码：`BlogController`、`FollowController`、`BlogServiceImpl`、`FollowServiceImpl`、`IBlogService`、`IFollowService`、`Blog`、`Follow`、`User`、`ScrollResult`、`RedisConstants`、`SystemConstants`。

## 一、功能定位

两块业务，都围绕「用户 A 和用户 B 的关系」展开：

| 模块 | 业务 | 用到的 Redis 结构 |
| --- | --- | --- |
| 8.1 / 8.2 发布 / 查看笔记 | 写 `tb_blog`，查笔记时补上作者昵称头像 | 无（纯 DB） |
| 8.3 点赞 | 一人一赞，再点取消；详情页高亮「我点过没」 | **ZSet**（`blog:liked:{blogId}`） |
| 8.4 点赞排行榜 | 详情页展示**最早点赞的 TOP5** | **ZSet**（`ZRANGE 0 4`） |
| 9.1 关注 / 取关 | 写 `tb_follow`，顺带维护自己的关注集合 | **Set**（`Follow:{userId}`） |
| 9.2 共同关注 | 我和博主都关注了谁 | **Set 的交集**（`SINTER`） |
| 9.3 / 9.4 Feed 流 | 发笔记时推给所有粉丝的「收件箱」 | **ZSet**（`feed:{fanId}`，score = 毫秒时间戳） |
| 9.5 滚动分页 | 收件箱按时间倒序、无限下拉 | **ZSet 范围查询** |

两张表：

- `tb_blog` —— 探店笔记。**注意**：`icon`、`name`、`isLike` 三个字段在实体里标了 `@TableField(exist = false)`，是**只存在于内存、不入库**的展示字段（`Blog.java:46`、`Blog.java:51`、`Blog.java:56`）。
- `tb_follow` —— 关注关系，一行 = 「user_id 关注了 follow_user_id」。课程提示**主键要改成自增**，否则 `save(follow)` 拿不到主键。

两个值得注意的**分层现象**：

1. **`BlogServiceImpl` 把自己注入了自己**（`BlogServiceImpl.java:45` 的 `@Resource private IBlogService blogService;`），然后在 `queryHotBlog`（`:68`）、`saveBlog`（`:140`）、`queryBlogOfFollow`（`:192`）里用 `blogService.xxx()` 而不是 `this.xxx()`。这样写通常是为了**让方法经过 Spring 代理**（自调用的 `this.save()` 不走 AOP）。但这里 `saveBlog` **没有 `@Transactional`**，所以这个自注入**目前没有任何收益**，只是「以后加事务用得上」的伏笔。
2. **分页逻辑散落在 Controller 和 Service 两处**：`/blog/of/me`、`/blog/of/user` 写在 `BlogController.java:51`、`:81`，而 `/blog/hot` 写在 `BlogServiceImpl.java:68`。同一类操作两种写法。

真正的「补作者 + 判断点赞」都在私有方法里（`BlogServiceImpl.java:209`）：

```java
private Result queryBlogUser(Blog blog) {

    if(blog==null)
    {
        return Result.fail("博客不存在");
    }


    Long userId = blog.getUserId();
    User user = userService.getById(userId);
    blog.setName(user.getNickName());
    blog.setIcon(user.getIcon());

    return Result.ok(blog);
}
```

要点：

- 课程原版是**两段式**：`queryBlogById` 先判 null 返回 `Result.fail("笔记不存在！")`，再单独调一个 `void queryBlogUser(blog)`。本项目把它**合并成了一个返回 `Result` 的方法**，错误提示也从「笔记不存在」改成了「博客不存在」。
- 合并的**代价**：`queryBlogUser` 既负责「填用户」又负责「包 `Result`」。在 `queryHotBlog`（`:75`）和 `queryBlogOfFollow`（`:196`）里它在 `forEach` 中被调，**返回值被直接丢掉** —— 签名和用法对不上。
- **潜在 NPE**：`userService.getById(userId)` 为 null（作者注销/脏数据）时 `user.getNickName()` 空指针。课程原版也没防。

### 4.3 `likeBlog`（点赞 / 取消，**ZSet 版**）

```java
@Override
public Result likeBlog(Long id) {
    Blog blog = getById(id);
    String key =BLOG_LIKED_KEY+id;

    Long userId = UserHolder.getUser().getId();
    //判断set里是否有该用户
    Double score = stringRedisTemplate.opsForZSet().score(key, String.valueOf(userId));
    if(score==null)
    {
        //没有,在数据库中更新点赞数量,在set中添加
        boolean success = update().setSql("liked = liked + 1").eq("id", id).update();
        if(success)
        {
            stringRedisTemplate.opsForZSet().add(key, String.valueOf(userId),System.currentTimeMillis());
        }
    }
    else
    {
        //没有,在数据库中更新点赞数量,在set中添加
        boolean success = update().setSql("liked = liked - 1").eq("id", id).update();
        if(success)
        {
            stringRedisTemplate.opsForZSet().remove(key, String.valueOf(userId));
        }
    }
    return Result.ok();
}
```

要点：

- **判重用的不是 `SISMEMBER`，而是 `ZSCORE`**（`:89`）。返回 `Double`，`null` = 没点过。这正是 8.3 → 8.4 的演进点：**从 Set 换成了 ZSet**。
- **为什么非要用 ZSet 而不是 Set**：8.4 要按「点赞时间」出 TOP5 排行榜，`ZADD` 时 `score` 存 `System.currentTimeMillis()`，`ZRANGE` 天然按 score 排序；Set 无序，`SMEMBERS` 的顺序不可依赖，出不了带时间的排行榜。**Set 只能表达「谁点过」，ZSet 才能表达「谁先点过」**。
- **member = 用户 id（如 `"8"`），score = 时间戳**。所以 `ZSCORE` 拿到的是时间，`ZADD` 第三个参数必须是时间戳。
- **`Blog blog = getById(id);`（`:84`）是死代码**（课程原版没有），多跑一次 `SELECT`。
- 两句注释都写「…在set中添加」，但 else 分支其实是**取消**（-1 且 `ZREM`），注释是从上面复制忘了改。另外**先改库、再改 Redis，中间失败会不一致**（库里 -1 了但 Redis 没 `ZREM`），无事务无补偿。

### 4.4 `queryBlogLikes`（点赞排行榜 TOP5）

```java
@Override
public Result queryBlogLikes(Long id) {
    Blog blog = getById(id);
    String key = BLOG_LIKED_KEY + id;
    //获取用户
    Set<String> top5 = stringRedisTemplate.opsForZSet().range(key, 0, 4);
    if(top5==null||top5.isEmpty())
    {
        return Result.ok(Collections.emptyList());
    }
    //解析用户id
    List<Long> ids = top5.stream().map(Long::valueOf).collect(Collectors.toList());
    String strids = StrUtil.join(",", ids);

    //获取用户并转成安全类型
    List<UserDTO> userDTOS = userService.query()
            .in("id",ids).last("ORDER BY FIELD(id,"+strids+")").list()
            .stream().map(user -> BeanUtil.copyProperties(user, UserDTO.class))
            .collect(Collectors.toList());
    return Result.ok(userDTOS);
}
```

这是本节课**最值得嚼的一段**，三个点：

1. **`range(key, 0, 4)`** = `ZRANGE key 0 4`，**按 score 升序**取前 5 —— score 是点赞时间戳，升序 = **最早点赞的 5 个人**，正是课程要的「最早点赞 TOP5」。
2. **`WHERE id IN (5,1,3,...)` 不保证顺序**（MySQL 实际常按主键/执行计划返回）。所以必须补 `.last("ORDER BY FIELD(id, 5, 1, 3, ...)")` —— `FIELD()` 返回 id 在列表里的下标，按它排序就把 Redis 给的顺序**还原**回来；少了这句排行榜顺序就是乱的。
3. `strids` 是 `StrUtil.join(",", ids)` **拼进 SQL 的字符串**（`BlogServiceImpl.java:127`）。value 目前是我们自己 `ZADD` 的 userId，暂时安全，但字符串拼 SQL 本身是危险信号。

### 4.5 `follow` / `isFollow`（关注 / 取关 / 是否关注）

```java
@Override
public Result follow(Long id, Boolean isFollow) {
    //获取当前用户id
    Long userId = UserHolder.getUser().getId();
    if (isFollow) {
        //关注了,新增数据
        Follow follow = new Follow();
        follow.setUserId(userId);
        follow.setFollowUserId(id);
        boolean isSuccess = save(follow);
        if(isSuccess)
        {
            String key = "Follow:"+userId;
            stringRedisTemplate.opsForSet().add(key,String.valueOf(id));
        }

    }
    else
    {
        //没关注,删除数据
        boolean isSuccess = remove(new QueryWrapper<Follow>().eq("user_id", userId).eq("follow_user_id", id));
        if (isSuccess) {
            String key = "Follow:"+userId;
            stringRedisTemplate.opsForSet().remove(key,String.valueOf(id));
        }
    }

    return Result.ok();
}
```

```java
@Override
public Result isFollow(Long id) {
    //获取当前用户id
    Long userId = UserHolder.getUser().getId();
    //判断是否关注
    Integer count = query().eq("user_id", userId).eq("follow_user_id", id).count();

    return Result.ok(count>0);
}
```

要点：

- **DB 是主、Redis 是副本**：关注先 `save(follow)` 落库、**成功之后**才 `SADD`；取关先 `remove(...)`、**成功之后**才 `SREM`。与点赞「先库后缓存」一致。
- **key 是 `"Follow:" + userId`（大写 F），课程原版是 `"follows:"`** —— 与课程不一致，且没抽成常量，`follow` 和 `followCommons` 各硬编码一次（`:53`、`:63`、`:86`、`:87`）。两处互相一致所以功能是通的，但：① 和课程 key 对不上；② 违反本项目 key 一律走常量的约定；③ 一处大小写手抖，共同关注就静默查成空集。
- **`isFollow` 走数据库 `count(*)`** 而非 Redis，所以「是否关注」和「Redis 关注集合」是两套真相，极端并发下可能短暂不一致。另外**没校验「不能关注自己」**。

### 4.6 `followCommons`（共同关注，`SINTER`）

```java
@Override
public Result followCommons(Long id) {
    Long userId = UserHolder.getUser().getId();


    String key1 = "Follow:"+userId;
    String key2 = "Follow:"+id;
    //查找两个用户关注的交集
    Set<String> intersect = stringRedisTemplate.opsForSet().intersect(key1, key2);
    if(intersect==null||intersect.isEmpty())
    {
        return Result.ok(Collections.emptyList());
    }
    //解析用户id
    List<Long> ids = intersect.stream().map(user -> Long.valueOf(user)).collect(Collectors.toList());
    //转成安全类型
    List<UserDTO> userDTOS = iUserService.listByIds(ids).stream().map(user -> BeanUtil.copyProperties(user, UserDTO.class)).collect(Collectors.toList());

    return Result.ok(userDTOS);

}
```

- **`intersect(key1, key2)` = `SINTER Follow:{我} Follow:{博主}`** —— 一步拿到「我和他都关注的人」。这是选 Set「而不是每查一次写一段 SQL `JOIN`」的核心理由：**交集是 Set 的原生能力**。
- `listByIds(ids)` 的返回顺序不保证与交集一致 —— 展示列表不要求顺序可以接受；**若要排序就得像 4.4 那样补 `ORDER BY FIELD`**。
- 前提是「Redis 关注集合完整」：改造之前的旧关注关系不在 Redis 里，会漏。课程说的「改造关注列表」指的就是 4.5 那两个 `SADD`/`SREM`。

### 4.7 `saveBlog`（发布笔记 + 推送到粉丝收件箱）

```java
@Override
public Result saveBlog(Blog blog) {
    // 获取登录用户
    UserDTO user = UserHolder.getUser();
    Long userId = user.getId();
    blog.setUserId(user.getId());
    // 保存探店博文
    boolean isSuccess = blogService.save(blog);
    if (!isSuccess) {
        return Result.fail("新增博客失败");
    }
    //获取所有粉丝
    List<Follow> follows = followService.query().eq("follow_user_id", userId).list();
    for (Follow follow : follows) {
        //找到每个粉丝的收件箱
        String key = FEED_KEY+follow.getUserId();
        //存入博客id
        stringRedisTemplate.opsForZSet().add(key,String.valueOf(blog.getId()),System.currentTimeMillis());

    }

    // 返回id
    return Result.ok(blog.getId());
}
```

要点：

- **谁是粉丝**：`tb_follow` 里 `follow_user_id = 我` 的那些行，它们的 `user_id` 才是粉丝。课程注释里写得很清楚：`select * from tb_follow where follow_user_id = ?`。这一步是本接口的重头戏（**写扩散**）。
- **收件箱结构**：`feed:{粉丝id}` 是一个 **ZSet**，value = 笔记 id，score = `System.currentTimeMillis()`。存 id 不存整个 Blog 对象，是为了避免大 V 一发帖就往 N 个粉丝的 ZSet 里塞 N 份完整 JSON。
- **`System.currentTimeMillis()` 是「一条笔记对应一个时间戳」**：循环里每次都现取一次 `System.currentTimeMillis()`。所以同一条笔记推给不同粉丝时，**score 可能落在不同毫秒**，但这不影响单人收件箱内的排序。
- **`blogService.save(blog)` 用的还是自注入的代理**（`:140`），同样没有 `@Transactional`。**写库成功、但循环推到一半失败**（Redis 抖动），会留下「一部分粉丝有、一部分没有」的收件箱 —— 没有补偿机制。
- 变量 `userId`（`:137`）和 `user.getId()`（`:138`）重复，`userId` 后面只在 `:145` 用到，写 `Long userId` 是无害的冗余。

### 4.8 `queryBlogOfFollow`（收件箱滚动分页）

```java
@Override
public Result queryBlogOfFollow(Long lastId, Integer offset) {

    //查询当前用户id
    Long userId = UserHolder.getUser().getId();

    //查询用户收件箱,分页查询
    String key = FEED_KEY+userId;
    Set<ZSetOperations.TypedTuple<String>> typedTuples = stringRedisTemplate.opsForZSet().reverseRangeByScoreWithScores(key, 0, lastId, offset, 2);
    if(typedTuples==null||typedTuples.isEmpty())
    {
        return Result.ok();
    }
    //解析博客id和偏移量,最小的时间戳
    List<Long> ids = new ArrayList<>(typedTuples.size());
    long minTime = 0;
    Integer nextOffSet = 1;
    for (ZSetOperations.TypedTuple<String> tuple : typedTuples) {
        String blogId = tuple.getValue();
        ids.add(Long.valueOf(blogId));
        long time = tuple.getScore().longValue();
        if(time == minTime)
        {
            nextOffSet++;
        }
        else
        {
            minTime = time;
            nextOffSet = 1;
        }

    }
    //数据库查询博客
    String strIds = StrUtil.join(",", ids);
    List<Blog> blog = blogService.query()
            .in("id", ids).last("ORDER BY FIELD(id," + strIds + ")").list();

    for (Blog blog1 : blog) {
        queryBlogUser(blog1);
        isLike(blog1);
    }

    //封装结果
    ScrollResult r = new ScrollResult();
    r.setList(blog);
    r.setOffset(nextOffSet);
    r.setMinTime(minTime);

    return Result.ok(r);
}
```

这是全篇最绕的一段，拆开看。

**(1) 为什么滚动分页而不是 `Page`**：`feed:{我}` 会**不断被 `ZADD` 新元素**，「页码分页」在数据插入时会**错位**（第一页读到 `10~6`，期间来了 `11`，再读第 2 页就会重复读到 `6`）。滚动分页**不记页码，记「上次读到哪」**：拿上次的**最小时间戳 `minTime`** 当新上界，用 **`offset`** 跳过「与上界同一毫秒、但已读过」的那几条。

**(2) `reverseRangeByScoreWithScores(key, 0, lastId, offset, 2)`** —— 对应命令 **`ZREVRANGEBYSCORE feed:{id} lastId 0 WITHSCORES LIMIT offset 2`**。要点：

- 参数是 `(key, min, max, offset, count)` —— **min 在前、max 在后**；传 `(0, lastId)` 即取 score ∈ [0, lastId]、**降序**。
- `2` 是写死的页大小（课程也写死 2），没抽常量。
- **`WithScores` 必须有**：要拿 score 才能算出下次的 `minTime`。

**(3) `minTime` / `offset` 两个返回值各自解决什么**

| 返回值 | 解决什么 |
| --- | --- |
| `minTime` | 下次查询的**上界**（`lastId`），保证只往前翻、不回头 |
| `offset` | 下次查询要**跳过几条**，跳过的正是「score == minTime 且已读到过」的记录 |

**为什么需要 `offset`（关键在「同一毫秒多条数据」）**：`score` 是毫秒时间戳，同一毫秒完全可能有多条笔记；若按 `max = 上次的 minTime` 去查，Redis 会把那一毫秒的**所有**记录都返回，包括上一页已读的，不跳过就会重复。循环 `:175–189` 就是在数**末尾这段 score 都等于 minTime 的记录有几条**：`nextOffSet` 初值 1，遇到同 score `+1`，score 变小就重置为 1。

> **`nextOffSet` 初值 1 是个「死值」**：`minTime` 初值 0，真实时间戳永远是十几位数，所以**第一次循环必然走 `else` 把 `nextOffSet` 重置为 1** —— 初值写 1 还是写 100 结果都一样。它和 Controller 里 `offset` 默认值 `0`（`BlogController.java:87`）**不是一回事**：`offset=0` 是「第一页不跳过任何东西」，是真实语义；`nextOffSet=1` 只是循环初值。**但真正的问题在下一节 —— 这里漏抄了一行。**

**(4) `ORDER BY FIELD`** 又出现（`:193`），理由同 4.4。另外**收件箱空时返回 `Result.ok()`**（不是 `ScrollResult`），前端要能处理 `data` 为 null。

## 五、易错点

### 1. **`queryBlogOfFollow` 漏抄了课程的关键一行（会出错）**

课程原版在循环之后、`os = minTime == max ? os : os + offset;` 这一句（`Redis实战篇.md:3400`）：

```java
// 课程原版
os = minTime == max ? os : os + offset;
```

**本项目的代码里完全没有这一句**（`BlogServiceImpl.java:189` 之后直接进 `:191`）。后果是：**客户端传进来的 `offset` 只被用作本次 Redis 的 `LIMIT offset`，却从不被折进返回的 `nextOffSet` 里**。返回给前端的 `offset` 永远只是「本页末尾同毫秒的条数」。

推一遍语义（这才是 `offset` 该等于什么）：

```text
设 max = 客户端传进来的 lastId，offset = 客户端传进来的 offset，
   本次返回的末尾最小时间戳 = minTime，本页末尾同 score 的条数 = os。

「已经读过的、score == minTime 的记录数」应当作为下次的 offset：
  若 minTime == max（本页正好全落在上次那个毫秒桶里）：
        已读过 = offset(上次跳过的) + os(本页读的)  →  nextOffset = offset + os
  否则（minTime 是全新的、更小的毫秒）：
        已读过 = os                                  →  nextOffset = os
```

所以「正确」写法大致是 `nextOffset = (minTime == lastId) ? offset + nextOffset : nextOffset;` —— 注意**只有当 `minTime == lastId` 时才需要把上次的 offset 累加进去**。

> ⚠️ 有意思的是，**课程那行 `os = minTime == max ? os : os + offset;` 的两个分支方向和上面的推导正好相反**（它在 `minTime == max` 时不加、在不等时才加），这和课程自己的文字描述「跳过这些查询过的数据」也对不上。这一行**建议自己在 Redis 里造同一毫秒多条数据实测一遍再决定照谁写**，不要盲抄。

**什么时候会踩**：只要**同一毫秒内的条数达到页大小（这里 `count` = 2）**就会暴露 —— 此时一页装不下那个毫秒的数据，`offset` 必须把「之前几页在该毫秒已读过的条数」累加进去，否则下一页会**重复返回同一条**。（正常发帖很难触发，压测/批量导入才会，所以是个**潜伏 bug**。）

## 七、可以更好的地方

> 沿用 09-21 那篇的写法：**现状 → 问题 → 怎么改**。

### 7.1 把 `nextOffSet` 的 offset 累加逻辑补回来

**现状**：`BlogServiceImpl.java:174–189` 只算了「本页末尾同毫秒条数」，传入的 `offset` 被丢弃。**问题**：同一毫秒的条数达到页大小（2 条）时，翻页就会重复返回同一条。**改法**（循环之后补一行）：

```java
// 关键：只有本页的 minTime 仍是上次的上界时，才需要把上次的 offset 累加
nextOffSet = (minTime == lastId) ? nextOffSet + offset : nextOffSet;
```

> 落地前**先在 Redis 里造同一毫秒多条的数据实测**（见第六节步骤 5），确认分支方向再写死。
