# 全局唯一 ID 与分布式锁的引入

> **说明**：本文**只讲后端**，不涉及前端实现。
>
> 对照代码：`RedisIdWorker`、`ILock`、`HmDianPingApplication`。

## 一、功能定位

秒杀要下订单，订单需要一个主键。这个主键决定了后面一大堆事的难度，所以先把它解决掉。

| 产出 | 类型 | 作用 |
| --- | --- | --- |
| `RedisIdWorker` | 工具类 | 生成全局唯一、趋势递增、不泄漏业务量的订单 ID |
| `ILock` | 接口 | 给「分布式锁」定一个统一的门面，屏蔽具体实现 |
| `@EnableAspectJAutoProxy` | 启动类注解 | 让同类内部调用也能走代理（秒杀事务要用） |

## 二、调用契约

`RedisIdWorker` 不是一个 HTTP 接口，它是被 Service 层直接调用的工具类。所以这里的「契约」是**方法签名**：

```java
@Component
public class RedisIdWorker {
    /**
     * @param keyPrefix 业务前缀，如 "order"、"voucher"
     * @return 全局唯一的 Long 型 ID
     */
    public Long nextId(String keyPrefix)
}
```

调用方只需要关心「给个业务名、拿个唯一 ID」，不关心内部怎么实现的。

> 这是**接口隔离**的价值：以后要把 Redis 方案换成雪花算法，
> 只要 `nextId` 的签名不变，所有调用方一行都不用改。

`ILock` 的契约更明确 —— 它抽象的是「锁」这个动作：

```java
public interface ILock {
    boolean tryLock(Long timeout);   // 尝试获取锁，timeout 是锁的自动释放时间（秒）
    void releaseLock();              // 释放锁
}
```

## 三、后端分层调用链

```text
VoucherOrderController  (POST /voucher-order/seckill/{id})
   ↓
IVoucherOrderService
   ↓
VoucherOrderServiceImpl
   ├─ RedisIdWorker.nextId("order")   → Redis: INCR icr:order:yyyy:MM:dd:
   └─ ILock (SimpleRedisLock)         → Redis: SET NX EX / Lua DEL
```

> 注意这一天的两个产出**都不依赖 Spring MVC** —— 它们是纯粹的基础设施。
> 真正把它们串起来的是 09-28 的秒杀主流程。

## 四、关键代码

### 1. `RedisIdWorker` —— 唯一 ID 生成器

```java
@Component
public class RedisIdWorker {

    private static final Long BEGIN_TIMESTAMP = 1767225600L;
    private static final int COUNT_BITS = 32;

    @Resource
    private StringRedisTemplate stringRedisTemplate;

    public Long nextId(String keyPrefix) {
        LocalDateTime now = LocalDateTime.now();
        Long epochSecond = now.toEpochSecond(ZoneOffset.UTC);

        Long timeStamp = epochSecond - BEGIN_TIMESTAMP;

        String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));

        Long count = stringRedisTemplate.opsForValue().increment("icr:" + keyPrefix + ":" + date + ":");

        return timeStamp << COUNT_BITS | count;
    }
}
```

**逐段拆开看：**

**① `BEGIN_TIMESTAMP` 是「时间戳基准点」，不是随便写的**

```java
private static final Long BEGIN_TIMESTAMP = 1767225600L;
```

这个值是 **2026-01-01 00:00:00 UTC** 的 Unix 秒数（`20454 × 86400`，即 epoch 第 20454 天）。

为什么不用绝对时间戳？因为 ID 只有 64 位，高 32 位要留给时间戳，而 `2^32` 秒 ≈ 136 年。
但当前的 Unix 秒数已经是 17 亿（`1.7 × 10^9`），离 `2^32`（42.9 亿）只剩约 8 年可用。

**换个基准点，把「已经过去的时间」砍掉**，就能重新获得 136 年的空间。

**② `date` 决定「序号在多长时间内不重复」**

```java
String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));   // "2026:09:22"
```

注意格式串里用的是**冒号**而不是横线，是为了和 key 的层级风格统一：

```text
icr : order : 2026:09:22 :
 ↑     ↑          ↑
业务  前缀       日期
```

组出来的 key 是 `icr:order:2026:09:22:`。**按天分 key 意味着：序号只在「同一天内」保证不重复**，跨天会重新从 1 开始 —— 这不影响唯一性，因为高位的时间戳已经不一样了。

**③ `increment` 拿到的就是原子的自增序号**

```java
Long count = stringRedisTemplate.opsForValue().increment("icr:" + keyPrefix + ":" + date + ":");
```

`INCR` 是 Redis 原子命令，**并发调用不会拿到重复值**。

> 如果 key 不存在，Redis 会**先当成 0 再自增**，所以首次调用直接返回 1，不需要预先 `SET` 初始值。

**④ 位运算把两部分拼起来**

```java
return timeStamp << COUNT_BITS | count;
```

| 位段 | 存什么 | 容量 |
| --- | --- | --- |
| 高 32 位 | 距 2026-01-01 的秒数 | 2^32 秒 ≈ 136 年 |
| 低 32 位 | 当天第几单 | 2^32 ≈ 42.9 亿 |

- `<< 32`：时间戳整体左移，**低 32 位腾空**
- `| count`：因为低位全是 0，按位或就等于**直接填入**

> **这里必须是 `|` 不能是 `+`**。低位不进位时两者结果一样，
> 但一旦 `count` 溢出就会进位污染时间戳 —— 一个极难排查的 bug。

### 2. `ILock` —— 给分布式锁定一个门面

```java
public interface ILock {
    boolean tryLock(Long timeout);
    void releaseLock();
}
```

只有两个方法，但这两个方法就是「锁」的完整语义：

- `tryLock` 返回 `boolean`，表示**是否抢到**（而不是阻塞等待 —— 后面会看到，抢不到时业务层自己决定是重试还是报错）
- `releaseLock` 负责释放，且**必须能应对「锁已经不是我自己的」这种情况**

为什么要抽接口？因为实现会换：

| 实现 | 特点 |
| --- | --- |
| `SimpleRedisLock` | 自己用 `SET NX` + Lua 手写，理解原理用 |
| `Redisson` 的 `RLock` | 生产可用，支持可重入、重试、看门狗 |

> 有了 `ILock`，「下单」这段业务代码就不需要知道用的是哪一种锁。
> 这也是为什么 09-28 从 `SimpleRedisLock` 切到 `Redisson` 时，业务代码只改了一行。

### 3. `HmDianPingApplication` —— 提前打开一个开关

```java
@MapperScan("com.hmdp.mapper")
@SpringBootApplication
@EnableAspectJAutoProxy(exposeProxy = true)     // ← 这一天加的
public class HmDianPingApplication {
    public static void main(String[] args) {
        SpringApplication.run(HmDianPingApplication.class, args);
    }
}
```

这一天只是把开关打开，**真正用它是在 09-28 的秒杀事务里**（`AopContext.currentProxy()`）。

简单说：`@Transactional` 靠 Spring 的**代理对象**生效。但在同一个类里 `this.method()` 调用，**绕过了代理**，事务就失效了。`exposeProxy = true` 让当前代理对象可以被取出来，用 `AopContext.currentProxy().method()` 调用就能重新走代理。

## 五、为什么需要分布式锁（引出）

截止到现在，下单逻辑还没有并发保护。**在单机环境下**，这可以用 `synchronized` 解决：

```java
// 课程里的写法（本项目已注释）
synchronized (userId.toString().intern()) {
    IVoucherOrderService o = (IVoucherOrderService) AopContext.currentProxy();
    return o.creatVoucherOrder(voucherId);
}
```

> `intern()` 是为了拿到**同一个字符串对象** —— 因为 `synchronized` 锁的是**对象**，
> 如果每次 `userId.toString()` 都产生新对象，锁就形同虚设。

但**一旦部署多台 Tomcat，`synchronized` 立刻失效**：

```text
        nginx
       /     \
   Tomcat A   Tomcat B      ← 各自有各自的 JVM
      ↓           ↓
   synchronized  synchronized    ← 两个锁是「各自的锁」，互不相识
      ↓           ↓
   同一个用户发了两次请求，两边都抢到了「锁」，都去下单 → 一人两单
```

`synchronized` 是 **JVM 级别**的锁，只能管住自己这个进程。多进程/多机之间要靠**进程之外**的东西来互斥 —— 这就是**分布式锁**。

**为什么选 Redis 做分布式锁**：

| 方案 | 说明 |
| --- | --- |
| 数据库行锁 | 性能差，且和业务库耦合 |
| ZooKeeper | 一致性强但性能不如 Redis，且要额外维护一个组件 |
| **Redis** | **已经有 Redis 了，`SET NX` 天然就是「抢锁」语义，性能好** |

`SET key value NX` 的语义是「key 不存在才设置成功」，配合 Redis 单线程，**保证同一时刻只有一个客户端能设置成功** —— 这就是互斥。

> 这就是下一篇（`2026-09-24/黑马点评05`）要展开的内容。

## 六、易错点

1. **位运算必须用 `|` 不能用 `+`**。见第四节的说明，`count` 溢出时会进位污染时间戳。
2. **`BEGIN_TIMESTAMP` 换了就等于所有历史 ID 的语义变了**，这个值一旦上线不能改。
3. **`LocalDateTime.now()` 配 `toEpochSecond(ZoneOffset.UTC)` 是个隐患**：

   ```java
   LocalDateTime now = LocalDateTime.now();                 // 本地时间（东八区）
   Long epochSecond = now.toEpochSecond(ZoneOffset.UTC);    // 却按 UTC 解释
   ```

   正确写法应该是 `Instant.now().getEpochSecond()`，或者 `LocalDateTime.now().toEpochSecond(ZoneOffset.ofHours(8))`。
   当前写法会让时间戳**整体偏移 8 小时**。因为 `BEGIN_TIMESTAMP` 是固定值，偏移量是常数，所以 **ID 仍然单调递增、仍然唯一**，功能上不出错 —— 但这是个「不报错但不对」的地方，值得知道。

4. **`INCR` 的 key 没有设过期时间**。`icr:order:2026:09:22:` 这类 key 会永久留在 Redis 里，日积月累堆积。见第七节。
5. **`COUNT_BITS = 32` 意味着「一天不超过 42.9 亿单」**。实际业务不可能超，但这是个隐式假设，值得写下来。
6. **`ILock` 缺少「重试」语义**。`tryLock` 抢不到就返回 `false`，调用方要自己决定重试策略。Redisson 的 `tryLock(waitTime, leaseTime, unit)` 才有等待重试能力。

## 七、不依赖前端的验证方法

`RedisIdWorker` 不是 HTTP 接口，直接用单元测试验证：

```java
@SpringBootTest
class HmDianPingApplicationTests {

    @Resource
    private RedisIdWorker redisIdWorker;

    @Test
    public void testIdWorker() throws InterruptedException {
        CountDownLatch latch = new CountDownLatch(300);

        Runnable task = () -> {
            for (int i = 0; i < 100; i++) {
                long id = redisIdWorker.nextId("order");
                System.out.println("id = " + id);
            }
            latch.countDown();
        };

        long begin = System.currentTimeMillis();
        for (int i = 0; i < 300; i++) {
            es.submit(task);          // 300 线程 × 100 次 = 30000 个 ID
        }
        latch.await();
        long end = System.currentTimeMillis();
        System.out.println("耗时：" + (end - begin) + "ms");
    }
}
```

验证要点：

1. **把 30000 个 ID 丢进 `Set`，看 `size()` 是不是也等于 30000** —— 这是验唯一性
2. **看耗时** —— 3 万个 ID 应该在几百毫秒级，这是验性能
3. 直接看 Redis：

```bash
redis-cli -h 192.168.231.132 -a 123456
> GET icr:order:2026:09:22:
"30000"          # 序号部分，正好等于生成的个数
```

> 第 3 步和代码对照着看最有价值：**Redis 里的值应该等于「当天生成的 ID 个数」**，
> 因为每个 ID 对应一次 `INCR`。

## 八、可以更好的地方

### 8.1 时间戳换成 `Instant`

**现状**：`LocalDateTime.now().toEpochSecond(ZoneOffset.UTC)` 有 8 小时偏移。

**改法**：

```java
long timeStamp = Instant.now().getEpochSecond() - BEGIN_TIMESTAMP;
```

对应的 `date` 部分也用 `LocalDate.now()` 即可，两者互不影响。

### 8.2 给序号 key 加过期时间

**现状**：`icr:order:2026:09:22:` 永久驻留。

**改法**：首次 `INCR` 之后补一个 `EXPIRE`（或者直接接受，因为 Redis 会按 `maxmemory` 策略淘汰）。

```java
Long count = stringRedisTemplate.opsForValue().increment(key);
if (count == 1) {                     // 只有第一次才设过期，避免每次请求都写
    stringRedisTemplate.expire(key, Duration.ofDays(3));
}
```

> `count == 1` 这个判断很关键 —— 只在 key 刚被创建时设一次过期，
> 否则每个请求都要多发一条 `EXPIRE`，白白增加写放大。

### 8.3 `ILock` 补一个带等待时间的重载

**现状**：抢不到锁只能立刻失败，调用方自己写重试。

**改法**：参考 Redisson 的签名，加一个带 `waitTime` 的重载：

```java
public interface ILock {
    boolean tryLock(Long timeout);
    boolean tryLock(Long waitTime, Long timeout);   // 等 waitTime 秒，抢不到才返回 false
    void releaseLock();
}
```

### 8.4 优先级

| 改动 | 成本 | 收益 | 建议 |
| --- | --- | --- | --- |
| 时间戳换 `Instant` | 一行 | 中（消除隐式偏移） | 建议做 |
| 序号 key 加过期 | 三行 | 中（避免内存堆积） | 建议做 |
| `ILock` 加等待重载 | 十行 | 低（已有 Redisson 兜底） | 看情况 |
