

- ## 保护性暂停与信箱模式 (类生产者-消费者) 

  ### 一、 核心机制总结

  - **保护性暂停模式 (Guarded Suspension)**：主要用于**一个线程等待另一个线程的执行结果**（一对一通信模型）。例如线程 A 需要等待线程 B 产生的结果，线程 A 挂起（`wait`），直到线程 B 赋值并唤醒（`notifyAll`）。
  - **信箱模式 (类生产者-消费者)**：当需要多个线程等待多个结果时，引入中间层（信箱映射表 Map）进行**解耦**。
    - **生产者（Postman）**：只管把信件（数据）塞进对应的 ID 信箱，并通知。
    - **消费者（收信人）**：只管监控属于自己的 ID 信箱，没有就等待。打破了一对一的硬绑定。

  ### 二、 核心要点

  - **中间媒介隔离**：线程不直接交互，必须通过共享的中间对象（`GuardObject` 或 `MailBoxes`）来加锁并交换数据。
  - **条件变量轮询**：无论是等结果还是等信件，**必须配合 `while` 循环**进行条件检查（如 `while(this.object==null)`），以此决定是否调用 `wait()`。
  - **超时等待计算**：带超时的 `get` 方法中，必须使用 `begin` 和 `now` 来计算剩余需要等待的时间 `time2Wait = timeout - (now - begin)`，保证经历多次虚假唤醒后，总等待时间依然精准。
  - **及时清理资源**：消费者拿到信件后，必须将其从 Map 中移除（如 `boxes.remove(id)`），防止内存泄漏。

  ### 三、 易错点排雷 (⚠️ 极易踩坑)

  - ❌ **错用 `if` 代替 `while` (虚假唤醒)**：当线程被 `notifyAll()` 唤醒时，如果用 `if`，线程不会再次检查条件就直接向下执行。如果数据已被其他线程抢走，直接执行会报错。**必须用 `while` 重新判断**。
  - ❌ **锁对象不一致**：`wait()` 和 `notifyAll()` 必须在 `synchronized` 代码块内部调用，且调用的主体必须与 `synchronized(锁对象)` 是同一个对象，否则抛出 `IllegalMonitorStateException`。
  - ⚠️ **大范围唤醒 (惊群效应)**：只要有一个生产者放入数据，调用 `this.notifyAll()` 会唤醒所有正在等待的消费者去检查 Map，但只有 1 个人能拿到数据，其他人白白醒来一次又继续 `wait`，损耗性能。（进阶方案：使用 `Condition` 实现精准唤醒）。

  #### 1. 保护性暂停标准实现 (带精准超时机制)

  package com.itheima.Thread.test1;
  
  import lombok.extern.slf4j.Slf4j;
  
  @Slf4j(topic = "c.test1")
  public class test1 {
      public static void main(String[] args) {
          GuardObject guardObject = new GuardObject();
          String s = "内容";
  
          new Thread(()->{
              log.debug("等待结果");
              Object o = guardObject.get(1000);
              log.debug("获取到结果  {}",o);
          },"t1").start();
  
          new Thread(()->{
              try {
                  Thread.currentThread().sleep(3000);
              } catch (InterruptedException e) {
                  throw new RuntimeException(e);
              }
              guardObject.complete(s);
              log.debug("已完成");
          },"t2").start();
      }
  }
  
  @Slf4j(topic = "c.GuardObject")
  class GuardObject{
      private Object object;
  
      public void complete(Object complete) {
          synchronized (this) {
              this.object=complete;
              this.notifyAll();
          }
      }
  
      public Object get() {
          synchronized (this) {
              while(this.object==null) { // 必须用 while 防止虚假唤醒
                  try {
                      this.wait();
                  } catch (InterruptedException e) {
                      e.printStackTrace();
                  }
              }
          }
          return this.object;
      }
  
      public Object get(long timeout) {
          synchronized (this) {
              long begin = System.currentTimeMillis();
              long now = System.currentTimeMillis();
              while(this.object==null) {
                  // 计算剩余需要等待的时间，防止中途被唤醒导致等待时间重新计算
                  long time2Wait = timeout - ( now - begin);
                  if(time2Wait<=0)
                      break;
                  try {
                      this.wait(time2Wait);
                  } catch (InterruptedException e) {
                      e.printStackTrace();
                  }
                  now = System.currentTimeMillis();
              }
          }
          return this.object;
      }
  }

          synchronized (this) {

              ID++;
              this.notifyAll(); // 唤醒所有等待的收信人 (会产生惊群效应)
          }

          synchronized (this) {
              while (boxes.get(id)==null) { // 轮询检查自己的信件
                  try {
                      this.wait();
                  } catch (InterruptedException e) {
                      throw new RuntimeException(e);
                  }
              }
              return boxes.remove(id); // 拿到信件后必须从 Map 移除，防止内存泄漏
          }
      }

# 📚 LockSupport 之 park 与 unpark 核心笔记

## 模块一：基本概念与反常识特性

### 1. 核心作用

- `park()` 和 `unpark(Thread)` 是 `java.util.concurrent.locks.LockSupport` 类提供的静态方法。
- 主要用于暂停（阻塞）**当前线程和**恢复（唤醒）指定的线程。

### 2. 💡 反常识特性：顺序的自由度

与传统的同步机制不同，`park` 和 `unpark` 支持一种反常识的操作顺序：**即使先调用了 `unpark`，随后再调用 `park`，线程也不会被阻塞，而是继续顺畅执行。**

## 模块二：底层原理揭秘 (通行证与收费站类比)

每个 Java 线程在 C++ 底层都映射着一个 `Parker` 对象，该对象包含三个核心组件：`_mutex`（互斥锁）、`_condition`（条件变量）和 **`_counter`（计数器，核心！）**。

我们可以用“汽车过收费站”的生动类比来理解其工作机制：

- **线程** = 行驶的汽车
- **`park()`** = 到达收费站栏杆前
- **`_counter`** = 通行证（取值只能是 0 或 1，最多只有 1 张）
- **`_mutex` / `_condition`** = 收费站的安保室和休息区

### 1. park() 的运行逻辑 (到达收费站检查)

当线程调用 `park()` 时，会检查自己身上是否有“通行证”(`_counter`)：

- **无通行证 (`_counter == 0`)**：汽车被拦下，必须进入休息区等待（线程进入底层 `_condition` 阻塞挂起）。
- **有通行证 (`_counter == 1`)**：收费站直接收走通行证（将 `_counter` 置为 0），栏杆抬起，汽车开走（线程不阻塞，直接向下运行）。

### 2. unpark(Thread) 的运行逻辑 (发放通行证)

当调用 `unpark(指定线程)` 时，相当于交警**给该车辆发放 1 张通行证**（将目标线程的 `_counter` 置为 1）：

- 如果车子正停在休息区睡觉（线程处于 `park` 阻塞中），交警会叫醒司机（`_condition.signal()`），司机上交通行证，开车驶离。
- **（解释反常识点）\**如果先调用了 `unpark`，相当于\**提前把通行证发给了司机**。等这辆车稍后开到收费站调用 `park()` 时，直接交出通行证即可放行，自然就不会发生阻塞了。

## 模块三：与 wait / notify 的深度对比

虽然二者都是用于线程的等待与唤醒，但在设计理念上有本质区别。这通常是高频面试考点：

| **对比维度**         | **wait() / notify() (Object 机制)**                          | **park() / unpark() (LockSupport 机制)**                     |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **Monitor 锁的依赖** | ❌ **强制绑定**。必须配合 `synchronized` (获取对象 Monitor 锁) 一起使用，否则抛出 `IllegalMonitorStateException` 异常。 | ✅ **完全解绑**。不需要在任何同步代码块中调用，随时随地可以使用，极其轻量级。 |
| **唤醒的精确度**     | ❌ **随机盲叫 / 惊群效应**。`notify()` 只能在 WaitSet 中随机挑一个唤醒，`notifyAll()` 则会吵醒所有人，无法精确控制。 | ✅ **精准打击**。`unpark(Thread t)` 必须传入指定的线程对象，指名道姓地唤醒目标线程。 |
| **调用的先后顺序**   | ❌ **严格的先后要求**。必须**先 `wait` 再 `notify`**。如果先发送了 `notify` 通知，之后线程才去 `wait`，通知将永久丢失，导致线程死等。 | ✅ **顺序自由**。可以**先 `unpark` 再 `park`**。因为 `unpark` 提前发放了“通行证”（修改了 `_counter`），保证了后续的 `park` 会直接放行。 |

## 多把锁

### 1. 锁粒度细分：增强并发度

当一个类中存在多个不相干的临界区时，使用同一把锁（如 `synchronized(this)`）会导致极其严重的性能瓶颈。

- **场景比喻**：假设有一个大房间（`BigRoom`），里面既有床可以睡觉（`sleep`），也有书桌可以学习（`study`）。
- **粗粒度锁（锁 `this`）**：相当于给整个大房间的大门上了一把锁。有人在里面睡觉时，另一个人连进去学习都不行，并发度极低。
- **细粒度锁（多把锁）**：在类中声明两个独立的成员变量 `Object bedRoom = new Object();` 和 `Object studyRoom = new Object();`。睡觉时 `synchronized(bedRoom)`，学习时 `synchronized(studyRoom)`。两者互不干扰，并发度瞬间拉满。

### 2. 多把锁的代价：死锁 (Deadlock)

锁虽然拆分了，但当业务逻辑变得复杂，一个线程需要**同时获取多把锁**才能完成任务时，极易引发死锁。

- **经典场景（哲学家就餐/转账问题）**：
  - 线程 t1 获取了对象 A 的锁，准备去获取对象 B 的锁。
  - 与此同时，线程 t2 获取了对象 B 的锁，准备去获取对象 A 的锁。
- **结果**：双方互相捏着对方想要的“钥匙”且都不肯撒手（进入 `BLOCKED` 状态），导致程序逻辑彻底卡死，无法向下推进。这就是典型的“活跃性问题”。







## 活跃性问题

### 1. 死锁 (Deadlock)

- **概念**：两个或多个线程互相持有对方所需的锁，并且都在等待对方释放资源，导致所有相关线程都进入阻塞状态，程序彻底卡死。  
- **产生原因**：当一个线程需要**同时获取多把锁**时，就容易发生死锁。例如，线程 1 获得了 A 对象锁，接下来想获取 B 对象的锁；同时线程 2 获得了 B 对象锁，接下来想获取 A 对象的锁。双方互不相让，形成死循环。（经典的“哲学家就餐问题”就是典型的死锁场景）。  

### 2. 活锁 (Livelock)

- **概念**：线程并没有被阻塞（状态仍为 `RUNNABLE`），它们都在不断地运行并尝试解决问题，但由于彼此的动作相互抵消，导致最终谁也无法完成任务。  
- **产生原因**：活锁通常出现在**两个线程互相改变对方的结束条件**时。例如，线程 1 的结束条件是共享变量 `count` 减到 0，线程 2 的结束条件是 `count` 加到 20。如果两个线程同时运行，一个不断减，一个不断加，导致 `count` 永远无法达到任何一个线程的退出条件，两个线程都会陷入无休止的死循环中。  

### 3. 饥饿 (Starvation)

- **概念**：某个线程因为某些原因，迟迟得不到 CPU 的执行时间片，或者一直获取不到需要的锁资源，导致其任务始终无法进展或结束。  
- **产生原因**：
  1. 线程的**优先级太低**，导致操作系统的任务调度器始终优先调度其他高优先级线程。  
  2. 在某些锁机制（如非公平锁）或特定的加锁策略（如为了解决死锁而采用的顺序加锁法）中，某个线程每次尝试获取多把锁时都因为竞争失败而被迫退回，导致它永远抢不到执行的机会。  





## ReentrantLock



### 0. 基本语法规范

使用 `ReentrantLock` 时，最标准、最安全的写法是**必须在 `finally` 块中释放锁**，以防止临界区内发生异常导致死锁。

Java

```
ReentrantLock lock = new ReentrantLock();

lock.lock(); // 获取锁
try {
    // 临界区：执行业务逻辑
} finally {
    lock.unlock(); // 释放锁（必须放在 finally 中保证一定执行）
}
```

### 1. 可重入 (Reentrancy)

**特点**：同一个线程如果首次获得了这把锁，那么它就有权利再次获取这把锁（锁的计数器累加），不会被自己阻塞。

Java

```
static ReentrantLock lock = new ReentrantLock();

public static void main(String[] args) {
    lock.lock();
    try {
        System.out.println("进入主方法，获取了锁");
        method1(); // 调用同类中需要同一把锁的方法
    } finally {
        lock.unlock();
    }
}

public static void method1() {
    lock.lock(); // 已经拥有锁的线程，可以再次重入，不会死锁
    try {
        System.out.println("进入 method1，再次获取了锁");
    } finally {
        lock.unlock();
    }
}
```

### 2. 可打断 (Interruptibility)

**特点**：如果一个线程在等待锁的过程中，不想死等下去了，其他线程可以调用 `interrupt()` 方法打断它的等待。必须使用 `lockInterruptibly()` 方法获取锁。

Java

```
ReentrantLock lock = new ReentrantLock();

Thread t1 = new Thread(() -> {
    try {
        System.out.println("t1 尝试获取锁...");
        // 使用可打断的方式获取锁
        lock.lockInterruptibly(); 
        try {
            System.out.println("t1 拿到了锁");
        } finally {
            lock.unlock();
        }
    } catch (InterruptedException e) {
        System.out.println("t1 等锁的过程中被打断了，直接返回，不再死等！");
    }
});

lock.lock(); // 主线程先抢占锁
t1.start();  // t1 启动，此时 t1 会被阻塞等待

try {
    Thread.sleep(1000);
    System.out.println("主线程觉得 t1 等太久了，打断 t1");
    t1.interrupt(); // 打断 t1 的等待，t1 会抛出 InterruptedException
} catch (InterruptedException e) {
    e.printStackTrace();
} finally {
    lock.unlock(); // 主线程释放锁
}
```

### 3. 锁超时 (Timeout)

**特点**：尝试获取锁，如果拿不到，不立刻阻塞，而是等一段时间。如果超过时间还拿不到，就放弃。通常搭配 `if` 使用。

Java

```
ReentrantLock lock = new ReentrantLock();

Thread t1 = new Thread(() -> {
    try {
        // 尝试获取锁，最多等待 1 秒。如果拿到返回 true，拿不到返回 false
        if (!lock.tryLock(1, TimeUnit.SECONDS)) {
            System.out.println("等了 1 秒还是拿不到锁，不等了，去干别的事！");
            return;
        }
    } catch (InterruptedException e) {
        e.printStackTrace();
        return;
    }
    
    // 如果走到这里，说明在 1 秒内拿到了锁
    try {
        System.out.println("拿到了锁，开始执行任务");
    } finally {
        lock.unlock();
    }
});

lock.lock(); // 主线程先抢占锁，且故意不释放
t1.start();
```

### 4. 公平锁 (Fairness)

**特点**：`ReentrantLock` 默认是非公平锁（谁抢到算谁的）。如果在构造函数中传入 `true`，则开启公平锁（先排队先得），但会降低并发度，一般不推荐使用。

Java

```
// 传入 true，表示创建一个公平锁（排队机制：先来后到）
ReentrantLock fairLock = new ReentrantLock(true);

// 传入 false 或无参，表示非公平锁（默认，允许插队，性能更高）
ReentrantLock unfairLock = new ReentrantLock();
```

### 5. 支持多个条件变量 (Condition)

**特点**：相当于拥有多个“休息室”（WaitSet）。可以把不同等待条件的线程分门别类地放到不同的休息室中，唤醒时也可以精准唤醒某个特定休息室里的线程，避免了 `synchronized` 的惊群效应。

Java

```
ReentrantLock lock = new ReentrantLock();
// 创建两个不同的休息室（条件变量）
Condition waitCigaretteQueue = lock.newCondition(); // 等烟的休息室
Condition waitBreakfastQueue = lock.newCondition(); // 等早餐的休息室

boolean hasCigarette = false;

// 等烟的线程
new Thread(() -> {
    lock.lock(); // 1. await 前必须先获得锁
    try {
        while (!hasCigarette) {
            try {
                System.out.println("没烟，进专属休息室等待...");
                // 2. 释放锁，进入 waitCigaretteQueue 休息室等待
                waitCigaretteQueue.await(); 
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }
        // 4. 被唤醒并重新竞争到锁后，从这里继续执行
        System.out.println("拿到烟了，开始干活！");
    } finally {
        lock.unlock();
    }
}).start();

// 送烟的线程 (1 秒后执行)
new Thread(() -> {
    lock.lock();
    try {
        hasCigarette = true;
        System.out.println("送烟来了，唤醒等烟休息室里的人");
        // 3. 精准唤醒等烟休息室里的线程，不会吵醒等早餐的人
        waitCigaretteQueue.signal(); 
    } finally {
        lock.unlock();
    }
}).start();
```



## 同步模式之顺序控制



在并发编程中，**同步模式之顺序控制**是一个非常经典的实战场景。由于多个线程的执行顺序是由 CPU 调度器决定的（无序的），我们需要通过底层的锁机制和条件变量，人为地强行干预，让它们按照我们期望的顺序（例如 A -> B -> C）交替执行。

既然刚刚学习了 `ReentrantLock` 的多条件变量（多间休息室）特性，使用它来解决“三个线程循环打印 ABC”是最优雅的。

### 一、 代码实现 (ReentrantLock + Condition)

核心思路：

1. 设置一个**状态变量**（如 `flag`），用来指示当前该哪个线程执行（1代表A，2代表B，3代表C）。
2. 为三个线程分别分配**三个专属的条件变量**（休息室）。
3. 线程进入执行时，先检查 `flag`。如果不是自己的回合，就去自己的专属休息室 `await()` 等待；如果是自己的回合，执行打印后，修改 `flag`，并**精准唤醒**下一个线程专属休息室里的人。

Java

```
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public class SequentialControlDemo {
    public static void main(String[] args) {
        SyncPrinter printer = new SyncPrinter(5); // 循环 5 遍

        // 线程 A：只负责打印 A，考查 flag == 1
        new Thread(() -> printer.print("A", 1, 2), "t1").start();
        // 线程 B：只负责打印 B，考查 flag == 2
        new Thread(() -> printer.print("B", 2, 3), "t2").start();
        // 线程 C：只负责打印 C，考查 flag == 3
        new Thread(() -> printer.print("C\n", 3, 1), "t3").start(); 
    }
}

class SyncPrinter {
    private int flag = 1; // 状态标志，1表示该A执行，2表示该B，3表示该C
    private int loopNumber; // 循环打印的遍数

    private ReentrantLock lock = new ReentrantLock();
    // 建立三个专属休息室
    private Condition conditionA = lock.newCondition();
    private Condition conditionB = lock.newCondition();
    private Condition conditionC = lock.newCondition();

    public SyncPrinter(int loopNumber) {
        this.loopNumber = loopNumber;
    }

    /**
     * 通用的打印方法
     * @param content  打印的内容 (A/B/C)
     * @param currentFlag 当前线程应该匹配的标志
     * @param nextFlag 打印完毕后，下一个应该执行的线程标志
     */
    public void print(String content, int currentFlag, int nextFlag) {
        for (int i = 0; i < loopNumber; i++) {
            lock.lock();
            try {
                // 1. 判断是否该自己执行，不是则去对应的休息室等待
                while (flag != currentFlag) {
                    if (currentFlag == 1) conditionA.await();
                    else if (currentFlag == 2) conditionB.await();
                    else conditionC.await();
                }

                // 2. 该自己执行了，干活
                System.out.print(content);

                // 3. 干完活，修改标志位，并精准唤醒下一个线程
                flag = nextFlag;
                if (nextFlag == 1) conditionA.signal();
                else if (nextFlag == 2) conditionB.signal();
                else conditionC.signal();

            } catch (InterruptedException e) {
                e.printStackTrace();
            } finally {
                lock.unlock(); // 必须在 finally 中释放锁
            }
        }
    }
}
```

### 二、 关键点总结

- **状态标志驱动 (State Machine)**：顺序控制的核心是**状态机**。单靠锁只能保证互斥，无法保证顺序。必须引入 `flag` 这种共享变量，明确规定在什么状态下哪个线程具有执行权。
- **精准唤醒 (Condition)**：使用 `ReentrantLock.newCondition()` 的最大优势在于，A 线程执行完后，可以直接调用 `conditionB.signal()` 精准叫醒 B，而不会吵醒 C。这彻底消除了 `synchronized` + `notifyAll()` 带来的惊群效应和无效竞争。
- **通用方法抽离**：在实际开发中，尽量将获取锁、判断状态、执行业务、唤醒下家、释放锁的逻辑封装到一个通用方法中（如代码中的 `print` 方法），通过参数传递差异化数据，避免代码冗余。

### 三、 易错点排雷 (⚠️)

- ❌ **状态判断使用 `if` 而不是 `while`** 在多条件变量的等待中，虽然 `signal()` 是精准唤醒的，但依然强烈建议使用 `while(flag != currentFlag)`。如果使用 `if`，在某些极端情况或代码遭到修改被意外唤醒时，线程会绕过状态检查直接向下执行，破坏打印顺序。
- ❌ **忘记初始状态的设定** 程序能够运转的先决条件是有一个“引子”。在这个例子中，`private int flag = 1;` 使得启动时只有线程 A 能够跳过 `while` 循环直接执行，从而拉开整个链条的序幕。如果初始值设错（如设为 0），三个线程都会进入死等。
- ❌ **循环结束时的死锁隐患** 注意循环控制的边界。A、B、C 三个线程的循环次数必须完全一致。如果 A 循环 5 次，B 循环 4 次，那么在最后一次交接时，A 打印完尝试唤醒 B，但 B 已经结束了，导致 A 和 C 最终全部卡死在 `await()` 上。
- ❌ **解锁位置不在 `finally` 中** 如果 `System.out.print(content)` 抛出了异常，且 `unlock()` 没有放在 `finally` 块中，该线程将永远持有锁，导致其他所有等待的线程永久饥饿（死锁）。

掌握了这套范式，无论面试中要求写交替打印 1到100 还是交替打印奇偶数，都可以直接套用这个模板。
