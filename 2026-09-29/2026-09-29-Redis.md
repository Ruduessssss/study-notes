# Redis 知识点：消息队列与 Stream

> 承接 `2026-09-24-Redis.md`（Lua 脚本与原子性）。那篇讲的是「怎么把多条命令做成一条原子命令」，
> 这篇讲的是**把一条命令的结果交给另一个进程慢慢处理** —— 也就是消息队列。
>
> 本篇聚焦**消息队列本身**：List / PubSub / Stream 三种方案的命令、语义、各自的坑。
> 代码落地（`seckillOrder.lua`、`VoucherOrderServiceImpl` 的消费者）写在 `黑马点评07-秒杀优化与Redis消息队列.md`。

## 一、消息队列要解决什么

一句话：**生产者 → 队列（Broker） → 消费者**。核心价值是**解耦 + 异步** ——
生产者丢完消息就走，不用等消费者处理完。放到秒杀里就是「请求线程只负责发消息，落库交给后台线程」。

专业的 MQ（Kafka、RabbitMQ）功能全，但要额外部署。**Redis 自带三种能当队列用的结构**，
部署成本为零，这是本项目选它的原因：**List、PubSub、Stream**。

---

## 二、List 做队列：`LPUSH` / `BRPOP`

Redis 的 List 是双向链表，入口和出口不在同一边，天然是队列：

```text
LPUSH queue A        # 生产者从左边进
LPUSH queue B
LPUSH queue C        # 队列内容: [C, B, A]

BRPOP queue 5        # 消费者从右边出 → C   （FIFO：先进先出）
```

也可以反过来 `RPUSH` + `BLPOP`，效果一样。

### 2.1 关键命令

| 命令 | 作用 |
| --- | --- |
| `LPUSH key v...` / `RPUSH key v...` | 左 / 右侧推入（一个或多个） |
| `LPOP key` / `RPOP key` | 弹出；**队列空时返回 `nil`，不阻塞** |
| `BLPOP key timeout` / `BRPOP key timeout` | 阻塞版：空队列时**最多等 timeout 秒**，超时返回 `nil` |

> 为什么必须用阻塞版？普通 `LPOP` 空队列时立刻返回 `null`，消费者就得「轮询」空转浪费 CPU。
> `BRPOP` 让消费者**睡在 Redis 里等**，消息一到立刻唤醒。

### 2.2 优缺点

**优点**：

- 数据存在 Redis，**不受 JVM 内存上限**约束（对比 `ArrayBlockingQueue`）
- 有 Redis 持久化（RDB/AOF）兜底
- 能保证消息的**有序性**

**缺点**：

- **无法避免消息丢失**：`BRPOP` 是「取走」，消息一旦弹出就从 List 消失，
  消费者处理到一半崩了 → **这条消息找不回来**，没有任何补偿机制
- **只支持单消费者**（严格说是「一条消息只能被一个消费者取走」，做不到 PubSub 的广播）

### 2.3 一句话总结

List 解决了「内存」和「持久化」，**没解决「可靠」** —— 它没有 ACK。

## 三、PubSub：`SUBSCRIBE` / `PUBLISH`

PubSub（发布订阅）是 Redis 2.0 引入的模型：生产者往 **channel** 发，所有订阅该 channel 的消费者都收到。

| 命令 | 作用 |
| --- | --- |
| `SUBSCRIBE channel [channel...]` | 订阅一个或多个频道 |
| `PUBLISH channel msg` | 向频道发消息（返回收到消息的订阅者数量） |
| `PSUBSCRIBE pattern...` | 按通配符订阅，如 `PSUBSCRIBE news.*` |

### 3.1 优缺点

**优点**：支持**多生产、多消费**（真正的广播，一条消息所有订阅者都能收到）。

**缺点**：

- **不支持数据持久化** —— 消息发出去就没了，Redis 里不留痕
- **无法避免消息丢失** —— 订阅者掉线的瞬间发消息，就彻底丢了
- **消息堆积有上限**，超出后订阅者的缓冲区溢出、消息直接丢
- 没有 ACK，没有回溯

### 3.2 本质

PubSub 是「**实时广播**」不是「队列」，它假设消费者**一直在听**；只要「消费者离线一段时间」这个场景存在，它就不适合当业务队列。

## 四、Stream 基础：`XADD` / `XLEN` / `XREAD` / `XDEL`

Stream 是 **Redis 5.0** 引入的新数据类型，定位就是「**真正的消息队列**」。
它把消息**追加**到一个只增不减的日志里，每条消息带一个**唯一 ID**。

### 4.1 发送：`XADD`

```text
XADD key [NOMKSTREAM] [MAXLEN ~ n] *|ID field value [field value ...]

XADD stream.orders * voucherId 1 userId 100 id 999   # 返回消息 ID，如 "1526919030474-55"
```

- `*` 让 Redis **自动生成 ID**（格式见第六节）；也可以自己指定 ID，但必须**比队列里现有的都大**，否则报错
- `MAXLEN ~ 1000` 可以近似地限制队列长度（自动裁掉老消息，防止无限增长）

### 4.2 长度：`XLEN`

```text
XLEN stream.orders        # 返回消息条数
```

### 4.3 读取：`XREAD`（单消费者，非组）

```text
XREAD [COUNT n] [BLOCK ms] STREAMS key [key ...] id [id ...]
```

| 起始 ID 写法 | 含义 |
| --- | --- |
| `0` | 从**最早**的消息开始读 |
| `$` | 只读**这条命令之后**新来的消息（不管历史） |
| 具体 ID（如 `1526919030474-55`） | 读 ID **大于**它的消息 |

`BLOCK ms` 是阻塞读：没有消息时最多等 `ms` 毫秒。业务里常写成循环 `while(true): XREAD BLOCK 2000 ... $ → 非空则处理`。

### 4.4 删除：`XDEL`

```text
XDEL key id [id ...]      # 标记删除指定消息
XRANGE key start end      # 按 ID 范围查看消息（含两端），- / + 表示最小/最大
```

> ⚠️ **`XDEL` 不会立刻回收内存**（底层基数树节点要等整块空了才释放），想控内存应该用 `XADD MAXLEN` 从源头限长。

### 4.5 `XREAD` 的漏读问题（重要）

**用 `$` 做起始 ID 会漏读。** 场景：

```text
时刻 T0: XREAD ... $                  → 「现在最后一条」= 100
时刻 T1/T2: 来了消息 101、102
时刻 T3: 再 XREAD ... $                ← $ 解析成「此刻最后一条」= 102 → 只返回 102，101 被跳过！
```

只要「**两次读取之间有超过 1 条消息到达**」，中间的就被漏掉。所以 `XREAD`（单消费者）虽然「可回溯、可阻塞」，但**有漏读风险**。

**规避办法**：不要用 `$`，而是**记住上一条处理过的 ID**，下次用它当起点（消费者组把这件事自动化了 —— 见第五节）。

| Stream 单消费者（`XREAD`）的特点 | |
| --- | --- |
| 消息可回溯 | ✅ |
| 一个消息可被多个消费者读 | ✅（各自用自己的 ID 游标） |
| 可阻塞读取 | ✅ |
| **有漏读风险** | ⚠️ 用 `$` 时 |
| 消息确认机制 | ❌ 没有 |

## 五、消费者组：`XGROUP` / `XREADGROUP` / `XACK` / `XPENDING`

消费者组（Consumer Group）把「游标 + 确认」这件事**交给 Redis 管**，是 Stream 作为可靠队列的完整形态。

### 5.1 建组：`XGROUP CREATE`

```text
XGROUP CREATE key groupName id|$ [MKSTREAM]
```

| 参数 | 含义 |
| --- | --- |
| `key` | 队列名（stream 名） |
| `groupName` | 组名 |
| `id` | 起始 ID：`$` = 只消费**建组之后**的新消息；`0` = 从头消费**全部历史** |
| `MKSTREAM` | 队列不存在时**自动创建**（不加则报错） |

其它组管理命令：`XGROUP CREATECONSUMER`（显式加消费者，一般不用，`XREADGROUP` 会自动建）、
`XGROUP DELCONSUMER`（删消费者，**它 PEL 里的消息会被一并丢弃**）、`XGROUP DESTROY`（删整个组，stream 本身还在）。

### 5.2 读消息：`XREADGROUP`

```text
XREADGROUP GROUP group consumer [COUNT n] [BLOCK ms] [NOACK] STREAMS key id [key id ...]
```

| 参数 | 含义 |
| --- | --- |
| `group` | 组名（必须已存在） |
| `consumer` | 消费者名，**不存在会自动创建** |
| `COUNT n` | 本次最多取几条 |
| `BLOCK ms` | 无消息时最长阻塞 |
| `NOACK` | 取到即**自动确认**（跳过 PEL，等于放弃可靠性） |
| `id` | **只有两种语义，见下** |

**`id` 的两种语义是整个 Stream 最关键的分水岭：**

| `id` | 从哪读 | 用途 |
| --- | --- | --- |
| **`>`** | **从未投递给本组任何消费者**的新消息 | 正常消费（对应 Java 的 `ReadOffset.lastConsumed()`） |
| **任意具体 ID（常用 `0`）** | 从**本消费者的 PEL** 里读「ID 大于它」的、**已投递但未 ACK** 的消息 | 异常重试（对应 Java 的 `ReadOffset.from("0")`） |

### 5.3 `XREADGROUP` vs `XREAD` 的本质区别

`XREAD` 是「读」，读完就没记录。`XREADGROUP` 是「**投递**」——
消息一旦被投递给某个消费者，就登记进**组的 PEL（Pending Entries List，待确认清单）**，
在 `XACK` 之前**一直留着**。

### 5.4 确认：`XACK`

```text
XACK key group id [id ...]
```

- 执行 `XACK` 后，这条消息**才从 PEL 移除**
- **`XACK` 不删消息本体** —— 消息还在 stream 里（可回溯就靠它），只是「不再算作待确认」

### 5.5 查看待确认：`XPENDING`

```text
XPENDING key group                                  # 概要：总数、最小/最大 ID、各消费者的待确认数
XPENDING key group minId maxId count [consumer]     # 明细
XPENDING key group IDLE 60000 - + 10                 # 只看「闲置超过 60 秒」的（排查卡住的消息）
```

`XPENDING` 给出的**投递次数（delivery count）**是识别**毒消息**的唯一线索 —— 某条消息被投递了几百次还没 ACK，基本就是它永远处理不成功。

### 5.6 三种方案对比

消费者组的五个特点（记住这张表就够）：**消息可回溯、多消费者争抢、可阻塞读、没有漏读、有 ACK 保证至少消费一次**。

| | List（`LPUSH`+`BRPOP`） | PubSub | Stream（消费者组） |
| --- | --- | --- | --- |
| 持久化 | ✅ | ❌ | ✅ |
| 多消费者 | 竞争取，一条只给一个 | ✅ 广播，人人都有 | ✅ 组内竞争 + 可多组 |
| 可阻塞读 | ✅ | ✅ | ✅ |
| 消息回溯 | ❌（弹出即消失） | ❌ | ✅ |
| 漏读 | 无（取到就没了） | 无（在线才有） | ✅ 组模式无漏读 |
| **消费确认 / 重试** | ❌ | ❌ | ✅ `XACK` / PEL |
| 内存/堆积 | Redis 内存 | 有上限，超了丢 | Redis 内存，可 `MAXLEN` 限长 |

## 六、消息 ID 与 `lastConsumed`

### 6.1 ID 的格式

Stream 的消息 ID 形如 **`<毫秒时间戳>-<序号>`**，例如 `1526919030474-55`：前段是写入时的 Unix 毫秒，后段是**同一毫秒内的第几条**（从 0 开始）。

**它单调递增，但不是「数字」** —— 比较规则是「先比毫秒部分，相等再比序号」，不能当成一个整数。
`XADD ... *` 让 Redis 用「当前毫秒 + 自增序号」生成，永远递增。

### 6.2 组里的 `last-delivered-id`

消费者组内部维护一个 **`last-delivered-id`**，记「本组已经投递到哪条了」。两种读取语义都靠它解释：

| 读取写法 | 相对 `last-delivered-id` 的位置 |
| --- | --- |
| `>`（Java：`ReadOffset.lastConsumed()`） | 严格**大于** `last-delivered-id` 的、且没投递过的 |
| `0`（Java：`ReadOffset.from("0")`） | 从 PEL 里找 ID > 0 的（即**本消费者**所有未确认的） |

> **`>` 为什么不会重复给同一条？** 因为组每次投递后就把 `last-delivered-id` 前移了。
> 想「重放」已投递的消息，用 `>` 是**做不到**的 —— 必须走具体 ID / PEL。
> 这正是本篇要传达的核心：**`>` 和 pending list 是两条完全不同的入口。**

### 6.3 `XINFO` 查看内部状态（排障必用）

```text
XINFO STREAM stream.orders      # ID、长度、radix tree 信息、组数量……
XINFO GROUPS stream.orders      # 每个组的 pending 数、last-delivered-id、消费者数
XINFO CONSUMERS stream.orders g1  # 每个消费者各自的 pending 数、空闲时长
```

排查「消息没被消费」时，`XINFO GROUPS` 是第一站。

## 七、概念层面要注意的坑

1. **`XREAD` 用 `$` 会漏读**。两次读取之间来了多条消息，中间的会被跳过（4.5）。
   要持续消费要么**记住上一条 ID**，要么**直接用消费者组**。

2. **`>` 和「具体 ID / 0」语义完全不同**，别混用：
   `>` = 新消息，`0` = 我自己的待确认（PEL）。想知道「为什么异常时要读 pending list」——
   因为失败的消息已经投递过、`>` 不会给第二次，只能从 PEL 捞。（`黑马点评07` 第 4.4 节）

3. **PEL 不会自动清理**。每条投递未 ACK 的消息都留在里面。**忘了 `XACK` = 内存慢性泄漏**，
   而且 `XPENDING` 计数会一直涨。可靠队列的代价就是「你必须确认」。

4. **`XACK` 删的是 PEL 记录，不是消息本体**。消息仍在 stream 里，靠 `XDEL` 或
   `XADD MAXLEN` 清。**「已确认」≠「已删除」**。

5. **组必须先创建**。`XREADGROUP` 不会隐式建组，组不存在会抛 `NOGROUP`。
   建组时 `id` 选 `$` 还是 `0` 决定了「历史消息消不消费」—— 选错了会**重复消费建组前的全部消息**。

6. **`NOACK` 等于放弃可靠**。它跳过 PEL，消息取到就再也无法重试 —— 只在「丢了也无所谓」时用。

7. **消费者崩了，它的 PEL 不会自动转移给别的消费者**。
   别的消费者用 `>` 读的是「未投递」的消息，看不到那条卡住的。
   要接管，得用 `XCLAIM` 主动把消息「认领」过来（本项目没做，`黑马点评07` 易错点 2 有讨论）。

8. **阻塞的 `XREADGROUP` 会独占连接**。用 `BLOCK 0`（永久阻塞）时，这条连接就废了，
   不能再发别的命令 —— 生产环境要用**独立连接**，别和主业务的连接池混用。

9. **消息 ID 不保证全局唯一**（两台机器同一毫秒发的消息，ID 前缀会相同），
   但**对同一个 stream 一定唯一且递增** —— 业务 id（本项目里的 `orderId`）要自己另外生成，
   不能拿消息 ID 当业务主键。

10. **「至少一次」是默认语义，不是「恰好一次」**。消费者组只能保证 **at-least-once**：
    处理完但没来得及 `XACK` 就崩了，消息会被重投。所以**消费逻辑必须幂等**
    （本项目的兜底是落库前再查一遍「一人一单」）。

11. **别把 Redis 队列当 Kafka**。PubSub 和 Stream 别搞混（一个广播不持久、一个队列持久可确认）；
    Redis 也没有分区、offset 管理、天然集群 HA。它能胜任「秒杀削峰」这种量级，再往上就该换专业 MQ —— 认清边界，别硬扛。
